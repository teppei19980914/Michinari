## 10. バリデーション方針

| 対象 | 方針 |
| --- | --- |
| 必須項目 | 入力欄単位で即時検証し、未入力を明示する |
| 数値範囲 | 品質指標は0〜100、負荷係数は正の数、総量および完了量は0以上、予定周回数は1以上の整数 |
| 日付整合 | 教材の開始日が締切より後の場合、保存を拒否する |
| 日付整合 | 受験日の期間開始日が期間終了日より後の場合、保存を拒否する |
| 周回整合 | 予定周回数を、既に完了した周回数を下回る値に変更できない |
| 完了量 | 累積完了量が総作業量を超える入力を警告する。保存は許容する（見積もり誤差の吸収のため） |
| リソース | 配分時間は0以上の整数（分）とする。スロットごとの配分合計がそのスロットの連続時間を超える保存を拒否する（NT-04）。ただしスロット側の短縮・削除による事後的な超過は警告のみとし保存を許容する（NT-09） |
| 時間表示 | 分から時間へ換算して表示する箇所は、小数第2位以下を切り捨てて小数第1位まで表示する（四捨五入しない）。算出には常に分（整数）を用いる |
| 遡及入力 | 前日を超える過去日への入力を拒否する |
| 変更不可 | 報告済の日およびクローズ済の目標への更新要求を拒否する |
| 時刻 | 1日の境界時刻は0時から11時の範囲とする |
| 読書：書籍 | 総ページ数は必須とし、1以上の整数とする |
| 読書：想起 | 想起本文は必須、現在ページは0以上・総ページ数以下の整数とする（任意入力） |
| 読書：冊数 | 1目標に対して書籍を2件以上登録できない |
| 仕事：案件情報 | 想定業務内容・着手日は必須。取引先・案件の呼称は任意 |
| 仕事：業務記録 | 業務内容の自由記述は必須（数値項目は持たないため他の数値バリデーションは適用対象外） |
| 仕事：案件数 | 1目標に対して案件情報を2件以上登録できない |
| ひとこと記録：気分 | 1〜5の整数とする（サーバ側で二重検証：schema層のge/le、service層の範囲チェック）。通常入力モードでは送信しない（null） |
| ひとこと記録：1行メモ | 最大文字数（`quick_record.note_max_chars`）はフロントエンドの入力欄制約（文字数カウンタ・maxLength）として用いる。保存先は既存の自由記述欄（`diary_learned`／`recall_body`／`body`）と同じであり、サーバ側では上限なしの既存バリデーションのまま扱う |
| スケジュール：作業項目 | 作業項目は必須（空白のみ不可）。予定開始日・予定終了日は必須で、予定開始日≦予定終了日。状況は必須（初期値は未着手） |
| スケジュール：実績日の条件付き必須 | 未着手は実績日入力不可。進行中は実績開始日必須・実績終了日入力不可。完了は実績開始日・実績終了日ともに必須。中止は実績日任意だが実績終了日のみの入力は不可。実績日は実績開始日≦実績終了日、かつどちらも本日（サーバーの論理日）以前 |
| スケジュール：上限 | 追加列は10列（`schedule.max_custom_columns`）、行は100行（`schedule.max_items`）まで |
| スケジュール：文字数上限 | 作業項目200文字（`schedule.item_title_max_chars`）、作業内容2000文字（`schedule.item_description_max_chars`）、追加列の名前200文字（`schedule.column_name_max_chars`）、セルの値2000文字（`schedule.cell_value_max_chars`）まで（DoS対策） |
| スケジュール：追加列の名前 | 必須（空白のみ不可）。同じ目標の中で重複不可 |
| スケジュール：所有者・状態 | 一括保存で送られてきた行・列のIDは対象の目標に属すること（他の目標に属する場合は保存を拒否し、1件も反映しない）。終了した目標（CLOSED_WITH_RESULT・CLOSED_WITHOUT_RESULT）への書き込みは拒否する |
| スケジュール：競合 | 一括保存は版数（revision）で同時編集を検知し、送信時と現在値が一致しない場合は保存を拒否する（409） |
| スケジュール：検証の置き場所 | 上記ルールはサービス層の1か所（`schedule_service.validate_item_fields`等）に集約し、スケジュール画面の一括保存と、単位4で追加する日次報告・SC-07からの更新で共通に使う（データ構造編6.2） |
| AI修正案：生成リクエスト | `trigger`が`AUTO`の場合は`record_date`を必須とする（省略時は検証エラー）。`MANUAL`では`record_date`を使わない（開発Todo_スケジュール・ガントチャート_v1.1 13.7、単位5） |
| AI修正案：AI応答（CHANGE行） | 行IDが対象の目標に属すること、行の状況が未着手または進行中であること、進行中の行は予定開始日を変更しないこと、新しい予定開始日≦予定終了日、新しい予定日が本日以降（未着手は予定開始日も本日以降）、目標に期限がある場合は新しい予定終了日が期限を超えないこと（D-62）、理由が必須かつ上限文字数（`schedule.revision.reason_max_chars`）以内、現在の値と少なくとも1項目が異なること、のいずれかに反するブロックは個別に捨てる（D-61、他のブロックの処理には影響させない） |
| AI修正案：AI応答（WARNING行） | 行IDが対象の目標に属すること、理由が必須かつ上限文字数（`schedule.revision.reason_max_chars`）以内であることのみを課す（CHANGE行向けの状況・日付・期限の制約は適用しない） |
| AI修正案：判断リクエスト | 判断対象の行が当該修正案に属し未判断（PENDING）であること。`ACKNOWLEDGED`はWARNING行のみ、`APPROVED`／`REJECTED`はCHANGE行のみ有効（組み合わせ違反は保存を拒否する）。1回のリクエスト内で同一の`proposal_item_id`を重複指定することも拒否する（二重判断の防止、コミット前チェックで追加） |
| AI修正案：承認時の日付 | 利用者が日付を修正して承認する場合、第6章の検証ルール（進行中の行は予定開始日を変更不可、予定開始日≦予定終了日、新しい予定日は本日以降）を適用する。期限（D-62）は利用者の判断を優先し適用しない（13.7） |
| AI修正案：変更前の値の一致 | 承認・却下できるのは、行の生成時点の値（`before_planned_start_date`等）が現在のスケジュール行の値と一致する行のみ。一致しない行は「変更されたため承認できません」として、その行だけ処理をスキップする（D-59、他の行の処理は継続） |
