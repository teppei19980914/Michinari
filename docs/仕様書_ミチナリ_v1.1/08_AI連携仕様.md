### 8.2 会話の管理方針

**制約**

開発キットでは、メッセージ送信前に会話を作成し、その識別子を指定する必要がある。会話はAI基盤側に永続化される。

**方針：用途と日付ごとに会話を分離する**

| 用途 | 会話の単位 | 会話のタイトル |
| --- | --- | --- |
| 日次報告 | 1日1会話（複数目標にまたがりうるため目標非依存） | `{日付} 日次報告` |
| 週次要約 | 1週1会話（目標ごと） | `{週開始日}週 週次要約` |
| 今日の一言 | 1日1目標につき1会話（ACTIVEな目標が無い日のみ目標非依存の1件） | `{日付} 今日の一言 {目標名}` |
| 総括レポート | 目標ごと1会話 | `総括レポート` |
| 仕事日次報告 | 1日1会話（読書と同様、目標非依存。資格試験の日次報告とは別会話） | `{日付} 仕事日次報告` |
| 月次報告 | 1か月1会話（目標ごと・対象月ごと） | `{対象月} 月次報告` |
| 半期評価 | 1半期1会話（目標ごと・対象半期ごと） | `{対象半期} 半期評価` |

**方針の理由**

会話を用途ごとに分離することで、異なる目的のプロンプトが文脈として混入することを防ぐ。日次報告のフィードバックが、朝に生成した「今日の一言」の文脈に引きずられる事態を構造的に排除する。

今日の一言は目標ごとに独立した会話・プロンプト呼び出しとする（未決事項L-04）。複数目標が同時進行している場合に、他目標の情報を一切混ぜないことで、順調な目標に引っ張られて停滞している目標の実態と乖離した一言が生成されることを構造的に防ぐ。

日をまたぐ文脈は、会話の継続によってではなく、週次要約をプロンプトに注入することで実現する。この方式であれば、注入する情報量をアプリケーション側で完全に制御できる。

**フォルダによる整理**

すべての会話をフォルダ配下に作成する。目標に紐づく会話（週次要約・総括レポート・今日の一言・月次報告・半期評価）はフォルダ名「`{接頭辞}_{目標名}`」の目標別フォルダに、目標に紐づかない会話（日次報告、仕事日次報告、およびACTIVEな目標が無い日の今日の一言）は接頭辞そのものを名前とする共通フォルダに配置する。接頭辞は設定から変更可能とする。共通フォルダをAI基盤側で削除するだけで、アプリ由来の会話を一括で解放できる。

**会話識別子の保持**

作成した会話の識別子はローカルに保持する。一覧取得APIを毎回呼び出さない。

### 8.3 メッセージ送信の指定

| パラメータ | 指定値 | 理由 |
| --- | --- | --- |
| Web検索 | 無効 | 既定値が有効のため明示指定が必須。試験対策の文脈に無関係な検索結果が混入することを防ぐ |
| ナレッジ検索 | 無効 | 本アプリはアシスタントのナレッジを使用しない |
| 親メッセージ順序 | 送信するが文脈維持には用いない（8.3.1参照） | 同一日内の複数往復における文脈維持は対話履歴の注入（8.4）で実現する |
| 画像・文書・音声 | 使用しない | MVPの範囲外 |

#### 8.3.1 親メッセージ順序に関する既知の制約（要検証）

導入したAI基盤の開発キット（NewtonX ADK v0.10.5）を実際にソースコードで確認したところ、`send_message()`のメソッドシグネチャに親メッセージ順序を指定する引数が存在せず、送信内容には常に固定値0が設定されることを確認した。バンドルされた公式ドキュメント（APIリファレンス、利用ガイド、トラブルシューティング）はすべてこのパラメータが機能する前提で書かれており、ドキュメントと実装が矛盾している。

**この制約を前提に、本アプリは以下の方針を取る。**

- AI基盤側の会話スレッド機能（親メッセージ順序による文脈継承）には依存しない
- 同一日内の複数往復における文脈維持は、本アプリが独自に保持する対話履歴（`chat_message`）を毎回のプロンプトへ全文注入する方式（8.4「対話履歴」）で実現する。この方式はAI基盤側の実装状況によらず機能する
- `ai_conversation.last_parent_order` の値は将来の開発キット改修に備えて記録は継続するが、現状は文脈維持の実効性を持たない
- 回答が出力上限で途切れた場合の継続取得（開発キット側が推奨する「終端マーカー方式」）も親メッセージ順序に依存するため、本アプリでは代わりに直前の応答本文をプロンプトに含めて「続きを出力してください」と自己完結した指示で送信する方式を取る

この制約は導入したADKのバージョン（v0.10.5）に起因するものであり、将来のバージョンアップで解消される可能性がある。解消された場合は、親メッセージ順序による文脈継承を主とし、対話履歴の全文注入を縮退時のみに用いる構成へ最適化してよい。

**アシスタントへのナレッジ登録は行わない。** アシスタントが組織内で共有される可能性があり、個人の学習記録を登録することは不適切である。

### 8.5 プロンプトの段階的縮退

**制約**

AI基盤の入力上限は明示されていない。

**方針（S04、2026-10-17改訂）**

AI-01（資格試験）・AI-06（読書）・AI-08（仕事）の日次報告フィードバックは、過去の記録の対象期間を目標開始日（AI-06はbook.start_date）から対象日の前日までの全期間とし、件数・週数の上限は設けない。プロンプトを組み立てた後、文字数が設定値（`ai.max_prompt_chars`）を超える場合、以下の順序で情報を削減する。

| 順位 | 削減対象 | 理由 |
| --- | --- | --- |
| 1 | 古い週次要約から順に除外（下限なし） | 直近ほど関連性が高い |
| 2 | 週次要約がまだ無い過去日の生ログを古い日から順に除外（下限なし） | 同上 |
| 3（AI-01のみ） | 教材情報の詳細度を下げる | 締切が遠い教材を集約表示にする |

上記を使い切ってもなお超える場合、当日の入力（本日の実績・日記・対話）は切り詰めず、送信を中止する（画面には「本日の入力が上限文字数を超えているため、送信できませんでした」と表示する）。これに至らず送信できた場合は、縮退が発生した旨を画面上に控えめに表示する。利用者が「なぜ言及されない情報があるのか」を把握できるようにするためである。

AI-01・AI-06・AI-08いずれも、週次要約が生成済みの期間は圧縮表現、未生成の期間は生ログとして扱う（AI-11・AI-12の週次要約、L-11で新設）。詳細はロジック・プロンプト編16.5・17.2・21.4・22.4・L-12参照。

**AI-04・AI-07・AI-09・AI-10（総括レポート・読了レポート・月次報告・半期評価）は本改訂の対象外**で、従来どおり①週次要約を古い週から除外→②生ログを古い日から除外、の2段階＋末尾切り詰めのフェイルセーフで縮退する（詳細はロジック・プロンプト編17.5・21.4・22.4）。特にAI-10（半期評価）は最大6ヶ月分の生ログ注入となる設計のため、週次要約による圧縮の効果が最も大きい（2026-09-15時点で識別した「対象期間の前半の実績が人事評価から漏れる」副作用への根本対応、2026-09-16実装、ロジック・プロンプト編L-11）。

AI-15〜AI-17（目標相談、S09でAI-15を導入、S10でAI-16・AI-17を追加）も同じ2段階（①週次要約→②生ログ）＋末尾切り詰めなしで縮退するが、総括レポート等と異なり対話形式のため、質問文・指示文・目標概要等の固定変数（カテゴリ別の概要を含む）は一切縮退しない。固定変数だけで上限を超える場合は送信せず、利用者には「この質問には回答できません」と表示する（末尾切り詰めのフェイルセーフには到達しない設計、ロジック・プロンプト編26章）。根拠検証（R-106）のため、縮退後にプロンプトへ実際に含めた週次要約・生ログの一覧を保持する仕組みを共通エンジン（`app/ai/prompt_builder.py`の`build_with_degradable_entries`）へ追加した。この追加はAI-04・AI-07・AI-09・AI-10・AI-13の既存の挙動には影響しない（戻り値への追加フィールドのみ、既定`None`）。

### 8.6 応答に対する要求

定型プロンプトは、以下を満たす応答を得るように構成する。

| 要求 | 内容 |
| --- | --- |
| 状況の解釈 | 数値実績と自然言語記述を統合し、進捗の背景要因を推定する |
| 成長の指摘 | 過去の記述との比較により、説明の解像度や構造化の変化を指摘する |
| 行動の提案 | 翌日以降の具体的な行動を提案する |
| 双方向の調整 | 負荷を増やす提案と減らす提案の双方を選択肢として持つ |

**負荷を減らす提案の段階**

| 段階 | 提案内容 |
| --- | --- |
| 軽 | 特定期間の負荷係数の引き下げ |
| 中 | 教材の優先順位変更、学習範囲の絞り込み、予定周回数の削減 |
| 重 | 受験日の後ろ倒し、目標の一時停止 |
| 即時 | 当日の休息 |

### 8.7 認証

**認証方式はPersonal Access Token（PAT）を主とする。** 導入した開発キット（NewtonX ADK）の現行の公式利用ガイドは、Host（サブドメイン）とPATによる認証を標準的な方法として案内しており、ブラウザ経由のOAuth／デバイスコード認証はEntraID構成時のフォールバック経路として内部に残るのみである。当初の設計はブラウザ認証を主経路と想定していたが、公式情報にあわせて以下のとおり改める。

| 項目 | 方針 |
| --- | --- |
| 認証情報の管理 | 開発キットの仕組みに委ねる。独自の資格情報管理を実装しない。Host（例: `xxx.newton-x.net`）とPATは、設定画面（SC-11）から開発キットの設定へ反映する |
| PATの発行 | NewtonXのWeb版アカウント画面で利用者自身が発行する（本アプリからは発行できない）。設定画面に発行手順への案内を表示する |
| 起動時 | Host・PATが設定済みかを確認する。開発キットはPAT設定時、他の認証手段より優先してこれを使用する |
| 未設定・無効時 | 設定画面でHostとPATの入力を促す。フォールバックとしてブラウザ経由の認証フロー（バックグラウンドスレッドで実行）を提供するが、主経路としては使用しない |
| 認証状態の公開 | クライアントには真偽値のみを返す。PAT・トークンは送出しない |
| リダイレクト先（フォールバック時のみ） | 開発キットの既定値（ローカル8400番）を使用する。アプリケーションサーバは別ポート（8100）で起動する |

### 8.8 エラー処理

| エラー種別 | 応答コード | 画面での扱い |
| --- | --- | --- |
| 未認証・トークン期限切れ | AI_AUTH_REQUIRED | 設定画面での再認証を促すメッセージを表示 |
| タイムアウト | AI_TIMEOUT | 再送ボタンを表示。実績入力の内容は保持する |
| 通信エラー・頻度制限 | AI_ERROR | エラー内容を表示。再送ボタンを表示 |
| 会話操作の失敗 | AI_ERROR | 同上 |
| 設定不備 | AI_CONFIG_ERROR | 設定画面への遷移を促す |

**実装上の注意（タイムアウトの判定方法）**

導入した開発キットの例外クラスは `NewtonXError` / `AuthenticationError` / `APIError` / `ConfigurationError` / `FileUploadError` / `ChatError` の6種であり、タイムアウト専用の例外クラスは存在しない。通信タイムアウトも内部的に `APIError` へ一律ラップされるため、型による判定はできない。本アプリでは、呼び出し側で計測した経過時間が設定値（`ai.timeout_seconds`）を超えているか、またはエラーメッセージにタイムアウトを示す文字列が含まれるかによって `AI_TIMEOUT` を判定する。

**重要な制約**

AI呼び出しの失敗により、実績入力の内容が失われてはならない。日次報告画面では、実績と日記の入力内容をクライアント側の状態として保持し、AI応答の成否とは独立させる。

AI応答が得られない状態でも、報告の確定を許容する。AIとの対話は本アプリの中核だが、それが利用できないことを理由に記録自体が失われるのは本末転倒である。

**非エンジニア向けエラー表示の方針（2026-09-19）**

全エラーコードの画面文言は、①何が起きたか（1文）②何をすればいいか（1文）の形式に統一し、技術的なエラーコードは表示しない（データ構造編6.3参照）。教材・書籍・案件情報の削除拒否（実績が紐づく場合）はエラーコード自体を増やさず、レスポンスの`details`に理由を含めて画面側で文言を出し分ける。

ドメイン例外・入力検証エラー以外の未分類の例外（バグ等の想定外エラー）も、必ず`INTERNAL_ERROR`として本アプリ標準の応答形式で返す（API層の最終防波堤のハンドラ）。フロントエンドにも画面全体のエラー境界を設け、予期しない描画エラーで画面が真っ白になることを防ぐ。エラーの画面表示は、失敗した操作の見出し（何をしようとして失敗したか。例：「月次報告を生成できませんでした」）と、本文（何が起きたか＋何をすればいいか）で構成する。全てのトーストは一定時間で自動的に消える（情報4秒、エラー8秒。通知の積み重なりで画面を塞がないため）。エラーは二文を読む時間を確保するため情報より長く表示し、利用者はいつでも×で閉じられる。技術的な詳細（エラーコード・相関ID）は折りたたみで残し、サポートへの報告に使えるようにする。AI生成や自動処理と保存が重なった場合は、専用のコード（DATABASE_BUSY）で「1〜2分待ってから再試行」を案内する（2026-10-04の障害を受けた改善）。

### 8.9 呼び出し頻度の制御

頻度制限が存在する可能性があるため、連続する呼び出しの間隔に下限を設ける。既定値は2秒とする。

週次要約の遡及生成では複数回の呼び出しが連続するため、この制御が特に重要となる。
