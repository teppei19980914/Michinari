## 1. 本計画の方針

### 1.1 分割の原則

| 原則 | 内容 |
| --- | --- |
| 依存順に進める | 前フェーズの成果物に依存するものを後に置く |
| ロジックを先に固める | 中核算出ロジックは画面より先に実装し、テストで検証する |
| AI連携を独立させる | AI基盤が不安定でも他の開発が止まらないよう、依存を後段に集約する |
| 1フェーズを1セッションで完結させる | コンテキストの飽和を避ける |

### 1.2 各フェーズに渡す文書

全フェーズで CLAUDE.md および運用設計ルールを常時参照させる。加えて、フェーズごとに必要な設計文書のみを投入する。**4文書を毎回全部渡さない。**

### 1.3 完了条件の考え方

各フェーズには検証可能な完了条件を定める。条件を満たさないまま次フェーズへ進まない。特に Phase 2 は、以降の全機能が依存するため厳格に検証する。

### 1.4 AI基盤の疎通確認について

当初は「AI基盤の開発キットは他アプリケーションで既に利用実績があるため、事前の疎通確認は行わない」としていたが、2026-08-23にNewtonX ADK（v0.10.5）を実際に導入し、ソースコード確認と実機テスト（アシスタント9種のうち8種で送受信を試行）を行った結果、以下を確認した。

**確認済みの事実**

- 公式ドキュメントが案内する親メッセージ順序（`parent_order`）は、実際にインストールされたコードでは機能しない（`send_message()`のシグネチャに引数が存在せず常に固定値0で送信される）。実機テストでも、これにより複数往復の文脈が自動的には維持されないことを確認した。→ 対応済み。文脈維持は`chat_message`の全文注入方式に一本化した（ロジック・プロンプト編16.3.1）
- ホスト`seraku-ex.newton-x.net`（本番相当として使用中）で、**特定のアシスタント2種（GPT-4o mini、GPT-4o）のみ**`send_message`が常に404で失敗することを確認した。**それ以外の7種のアシスタント（GPT-5系、Gemini系）は正常に送受信できることを実機確認済み。** 当初はテナント全体の疎通問題と誤認したが、原因はアシスタント個別の問題（廃止済みモデルの可能性）に切り分けられた。→ 対応済み。用途別の既定アシスタントを、動作確認済みの7種から選定した（5.2、仕様書8.9.1）

**この経緯を踏まえた運用方針**：「他アプリでの利用実績」は接続性一般の裏付けにはなるが、個別のアシスタント・APIメソッドの動作までは保証しない。**新しいアシスタントを既定値に追加する場合や、開発キットをバージョンアップする場合は、実装への組み込み前に軽量な疎通テスト（チャット作成→メッセージ送信→削除）を行うことを標準の手順とする。**

| 確認項目 | 状態 | 確認するフェーズ |
| --- | --- | --- |
| 認証フローの動作（PAT主経路） | 確認済み（2026-08-23） | Phase 5前に完了 |
| チャット作成・送受信・削除の動作 | 確認済み（対応アシスタントでは正常。5.2の除外リスト対象は使用不可） | Phase 5前に完了 |
| Web検索の無効化が有効に働くこと | 未確認 | Phase 5 完了後 |
| アシスタント一覧の取得と選択 | 一覧取得・個別の疎通は確認済み。選択UIは未実装 | Phase 5〜7 |
| フォルダおよび会話の作成 | 未確認 | Phase 5 完了後 |
| 長文プロンプトの送信可否と入力上限の実測 | 未確認 | Phase 5 完了後 |
| 呼び出し頻度制限の有無 | 未確認 | Phase 5 完了後 |

このうち入力上限の実測値は、設定値 `ai.max_prompt_chars` の調整に用いる。通信ログに送信文字数と縮退の有無を記録する設計としているため、運用の中で自然に把握できる。

**テスト（先に書く）**

設計書 ロジック・プロンプト編 第20章の検証観点をテストケース化する。特に以下は必須とする。

| 観点 | 検証内容 |
| --- | --- |
| 周回 | 1周目完了時に残量が0にならず、2周目のノルマが算出されること |
| 周回 | 現在周回が累積完了量から正しく導出されること |
| 周回別速度 | 2周目の速度が1周目と分離して算出されること |
| 周回別速度 | サンプル3件未満のとき直近周回の値で代替されること |
| 残量再配分 | 7日連続未達時、ノルマが全量繰越（8倍）ではなく再配分（約2.2倍）になること |
| バッファ非対称性 | バッファ日に実績が無くても翌日のノルマが増えないこと |
| バッファ非対称性 | バッファ日に実績があると翌日のノルマが減ること |
| 境界時刻 | 境界時刻より前の時刻において論理日が前日になること |
| 時間未入力 | 実効速度の分母・分子から除外されること |
| 日種別優先順位 | 個別指定が祝日設定を上書きすること |
| 負荷係数 | 係数変更で総量が保存されること |
| 境界値 | 残計画日0、実績0件、締切超過の各ケースで例外が発生しないこと |

**完了条件**

- 全テストが通過する
- 上記12観点が明示的にテストされている
- サービス層がHTTPに関する知識を一切持たない
- 日次ノルマ、残量、現在周回のいずれもデータベースに保存されていない

**注意点**

- **テストを後回しにしない。** ここの誤りは全機能に波及し、後から発見すると修正コストが跳ね上がる
- 残量の算出において、総量ではなく総作業量を用いること。この誤りは運用開始から数週間で顕在化する

### Phase 5：AI連携

| 項目 | 内容 |
| --- | --- |
| 目的 | AI基盤との連携を実装する |
| 投入文書 | CLAUDE.md、運用設計ルール、設計書 ロジック・プロンプト編（第15〜18章、特に16.1〜16.3・16.3.1）、データ構造編（第5.5節、第5.8節）、**`newtonx_adk/docs/`配下のADK公式ドキュメント一式**（`API_REFERENCE.md`、`USAGE_GUIDE.md`、`auth_setup_guide.md`）および導入済みパッケージのソースコード（`myvenv/Lib/site-packages/newtonx_adk/`） |

**Phase 5着手時の前提（2026-08-23時点で確認済み。実機テスト実施済み）**

- 導入済みのNewtonX ADK（v0.10.5）は、公式ドキュメント上は親メッセージ順序（`parent_order`）による会話文脈の維持を案内しているが、実際にインストールされたパッケージのソースコード（`client.py`）を確認したところ、`send_message()`に当該パラメータは存在せず常に固定値0で送信される。実機テストでも、これにより文脈が自動維持されないことを確認した。**対応済み**：文脈維持は`chat_message`の全文注入方式に一本化した。詳細は設計書 ロジック・プロンプト編 16.3.1を参照
- 認証方式は、当初想定していたブラウザ経由のOAuthフローではなく、**PAT（Personal Access Token）が現行の公式な標準方式**であることを確認済み（`USAGE_GUIDE.md`のクイックスタート、`auth_setup_guide.md`）。この環境でも実際にPATが設定済みであることを確認した
- ホスト`seraku-ex.newton-x.net`で、アシスタント9種のうち8種（GPT-4o mini以外の全て）で実際にチャット作成・メッセージ送信・応答受信が正常に成功することを実機確認済み。**GPT-4o mini・GPT-4o の2種のみ**`send_message`が常に404で失敗することを確認したため、この2種は既定値・選択肢から除外する（5.2、仕様書8.9.1）。テナント全体の疎通は問題ない
- 上記を踏まえ、本フェーズの実装要件・完了条件は既にPAT前提・親メッセージ順序非依存・動作確認済みアシスタント前提の内容に更新済みである（以下参照）

**実装対象**

- 開発キットのラッパ（`ai/client.py`）
- 認証状態の管理（`ai/auth.py`）
- 会話とフォルダの管理（`ai/conversation.py`）
- プロンプト組み立てと段階的縮退（`ai/prompt_builder.py`）
- 呼び出し間隔の制御（`ai/rate_limiter.py`）
- 通信ログ（`ai/logger.py`）
- 日次報告フィードバックの呼び出し
- 週次要約の生成判定と遡及実行
- 今日の一言の生成判定と実行
- 例外のマッピング

**AI基盤の実仕様に基づく実装要件**

**開発キットの仕様は変更できない。以下は所与の制約として実装する。**

| 項目 | 要件 |
| --- | --- |
| Web検索 | メッセージ送信時に**必ず明示的に無効化する**。既定値が有効のため省略不可 |
| ナレッジ検索 | 明示的に無効化する |
| 会話の作成 | メッセージ送信前に会話を作成し、識別子を `ai_conversation` に保存する |
| 会話の単位 | 用途と日付ごとに分離する（日次報告、週次要約、今日の一言、総括レポート） |
| フォルダ | 目標ごとにフォルダを作成する。名前指定での会話作成機能を用い、存在しない場合は自動作成する |
| 親メッセージ順序 | 送信はするが文脈維持には使用しない（v0.10.5では機能しないことを確認済み）。`last_parent_order`は将来の改修に備えた記録として更新する |
| 文脈維持（同一日内の複数往復） | `chat_message`テーブルの対話履歴をプロンプトへ全文注入する方式（`{{conversation_history}}`）で実現する。親メッセージ順序には依存しない |
| 会話識別子の取得 | ローカルに保存した値を用いる。一覧取得APIを毎回呼ばない |
| タイムアウト | 設定値（既定60秒）を開発キットの設定に反映する |
| 再試行回数 | 設定値（既定1）を開発キットの設定に反映する。アプリ側の再送と二重にしない |
| 呼び出し間隔 | 設定値（既定2秒）の下限を守る |
| 認証 | **PATを主経路とする。** Host・PATが設定済みかを起動時に確認する。未設定・無効時のみ、設定画面からブラウザ経由の認証フロー（バックグラウンドスレッド実行）を提供する |
| リダイレクト先（フォールバック時のみ） | 開発キットの既定値を使用する。サーバは別ポートで起動する |
| 稼働確認 | 起動時にモデルの利用可否を取得する |
| ナレッジ登録 | **使用しない。** 共有アシスタントに個人の学習記録を登録しない |
| ファイル添付 | 使用しない |

**例外マッピング**

| 開発キットの例外 | APIエラーコード |
| --- | --- |
| 認証関連の例外 | AI_AUTH_REQUIRED |
| API通信関連の例外 | AI_ERROR |
| チャット関連の例外 | AI_ERROR |
| 設定エラー | AI_CONFIG_ERROR |

**タイムアウトの判定方法**：導入済みADKの例外クラスは`NewtonXError`/`AuthenticationError`/`APIError`/`ConfigurationError`/`FileUploadError`/`ChatError`の6種（ソースコード確認済み）で、タイムアウト専用の型は存在しない。通信タイムアウトも`APIError`へ一律ラップされるため、型による判定はできない。経過時間の実測またはエラーメッセージの文字列判定で`AI_TIMEOUT`を判定する。

**プロンプト縮退の実装**

設計書 ロジック・プロンプト編 16.5 の4段階を実装する。縮退が発生した場合、`ai_log.was_truncated` を true として記録し、応答とともに画面へ通知する。

**完了条件**

- 日次報告でフィードバックが取得できる
- Web検索の無効化が明示的に指定されている（コード上で確認可能）
- 会話識別子が保存され、同一日の再送で再利用される
- フォルダが目標ごとに作成される
- **同一日内で複数往復した際、2回目以降の応答が1回目までの内容を踏まえたものになる**（`{{conversation_history}}`による文脈維持が実際に機能することを、実機での複数往復テストで確認する）
- PATによる認証で日次報告フィードバックの疎通ができる
- AI呼び出しが失敗しても実績入力が失われない
- AI応答なしで報告確定ができる
- 週次要約が起動時に遡及生成される
- 遡及生成時に呼び出し間隔の下限が守られる

- プロンプトが閾値超過時に段階的に縮退する

**注意点**

- **プロンプトはデータベースから読む。** ソースコードに埋め込まない
- 会話がAI基盤側に蓄積されるため、フォルダによる整理を必ず実装する
- 親メッセージ順序に依存する機能（開発キット推奨の「終端マーカー方式」による回答継続取得）は使用しない。回答が途切れた場合は直前の応答本文を含めた自己完結メッセージで継続取得する（ロジック・プロンプト編16.3.1参照）
- **GPT-4o mini・GPT-4oの2アシスタントは使用しないこと。** `send_message`が常に404で失敗することを実機確認済み（5.2、仕様書8.9.1）。既定値は動作確認済みの7アシスタントから選定済みだが、`ai.assistant_uid.*`を設定画面から変更できる仕様のため、新しいアシスタントを選択肢に追加する際は軽量な疎通テスト（チャット作成→送信→削除）を先に行う
- `delete_chat`はテスト対象の全アシスタントで一貫して`False`（削除失敗）を返すことを確認済みである。一方、`get_chats()`で確認する限り、メッセージを送信していない・または一往復のみのチャットは一覧に残らない（自然に消える）挙動も確認した。削除UIを実装する場合、`delete_chat`の戻り値を過信せず、`get_chats()`等で実際の削除結果を確認するか、削除失敗時の扱い（エラー表示／無視）を設計段階で決めておくこと

### Phase 11：実環境検証

| 項目 | 内容 |
| --- | --- |
| 目的 | 実環境での動作を確認し、設定値を調整する |
| 実施 | テッペイさんの手元で実施する |

**確認項目**

| 項目 | 確認内容 | 調整先 |
| --- | --- | --- |
| 認証 | PATによる認証で疎通できること。フォールバックのブラウザ認証フローも動作すること | — |
| ポート | 8100と8400が衝突しないこと（フォールバック認証使用時） | `server.port` |
| アシスタント | 一覧が取得でき、用途ごとに選択できること | `ai.assistant_uid.*`（4キー） |
| Web検索 | 無効化が有効に働くこと（検索結果が混入しないこと） | — |
| フォルダ | 目標名のフォルダが作成されること | `ai.folder_prefix` |
| 応答時間 | タイムアウト60秒が妥当か | `ai.timeout_seconds` |
| 入力上限 | 長文プロンプトが送信できるか。縮退が過剰に発生しないか | `ai.max_prompt_chars` |
| 頻度制限 | 週次要約の連続生成でエラーが出ないか | `ai.min_interval_seconds` |
| 応答品質 | フィードバックが期待した構成と深さを持つか | プロンプトテンプレート |
| 文脈維持 | 複数往復での対話が、対話履歴の全文注入によって成立していること（親メッセージ順序は機能しない前提） | — |
| チャット操作の安定性 | チャット作成直後のメッセージ送信・削除が安定して成功すること（Phase5冒頭のスモークテストで`seraku-ex`テナントにて404を確認済み。本番相当テナントで再検証） | — |

**入力上限の測定方法**

通信ログに送信文字数と縮退の有無を記録しているため、以下で判断する。

- 縮退が一度も発生していない場合、閾値を引き上げて情報量を増やす
- 通信エラーが発生した際の送信文字数を確認し、閾値を引き下げる

**応答品質の調整**

プロンプトの初期文面は暫定である。実際の応答を見て、以下の観点で調整する。

- 負荷を減らす提案が適切な頻度で出るか（出すぎ、出なさすぎのいずれも問題）
- 成長の指摘が具体的か、当たり障りのない内容になっていないか
- 行動提案が実行可能な粒度か

## 5. 各フェーズ共通の指示事項

```
# 共通指示
```

## 6. リスクと対応

| リスク | 影響 | 対応 |
| --- | --- | --- |
| Phase 2 のロジック誤り | 全機能に波及 | テストを先に書き、境界値を網羅する |
| 周回対応の実装漏れ | 運用開始数週間で計画が破綻 | Phase 2 の完了条件に明示的に含める |
| Web検索の無効化漏れ | フィードバック品質の劣化 | Phase 5 の完了条件でコード上の確認を求める |
| 入力上限の想定違い | 対話の失敗 | 縮退機構を先に実装し、実測で閾値を調整する |
| 頻度制限への抵触 | 週次要約の遡及生成が失敗 | 呼び出し間隔の下限を実装する |
| プロンプト応答品質の不足 | 中核価値の毀損 | Phase 11 で反復調整する前提とする |
| コンテキスト飽和による品質低下 | 実装の一貫性喪失 | 1フェーズ1セッションを厳守する |
| 設計書の未決事項の放置 | 実装時の判断ぶれ | 各フェーズ着手前に該当する未決事項を解消する |
