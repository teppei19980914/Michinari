## 1. 本計画の方針

### 1.1 分割の原則

| 原則 | 内容 |
| --- | --- |
| 依存順に進める | 前フェーズの成果物に依存するものを後に置く |
| ロジックを先に固める | 中核算出ロジックは画面より先に実装し、テストで検証する |
| AI連携を独立させる | AI基盤が不安定でも他の開発が止まらないよう、依存を後段に集約する |
| 1フェーズを1セッションで完結させる | コンテキストの飽和を避ける |

### 1.2 各フェーズに渡す文書

全フェーズで CLAUDE.md および運用設計ルールを常時参照させる。加えて、フェーズごとに必要な設計文書のみを投入する。**4文書を毎回全部渡さない。**

### 1.3 完了条件の考え方

各フェーズには検証可能な完了条件を定める。条件を満たさないまま次フェーズへ進まない。特に Phase 2 は、以降の全機能が依存するため厳格に検証する。

### 1.4 AI基盤の疎通確認について

AI基盤の開発キットは他アプリケーションで既に利用実績があるため、事前の疎通確認は行わない。**実装完了後、実環境での動作検証において以下を確認する。**

| 確認項目 | 確認するフェーズ |
| --- | --- |
| 認証フローの動作 | Phase 5 完了後 |
| Web検索の無効化が有効に働くこと | Phase 5 完了後 |
| アシスタント一覧の取得と選択 | Phase 5 完了後 |
| フォルダおよび会話の作成 | Phase 5 完了後 |
| 長文プロンプトの送信可否と入力上限の実測 | Phase 5 完了後 |
| 呼び出し頻度制限の有無 | Phase 5 完了後 |

このうち入力上限の実測値は、設定値 `ai.max_prompt_chars` の調整に用いる。通信ログに送信文字数と縮退の有無を記録する設計としているため、運用の中で自然に把握できる。

### Phase 2：コアロジック

**本フェーズが最も重要である。以降の全機能がここに依存する。**

| 項目 | 内容 |
| --- | --- |
| 目的 | 算出ロジックを実装し、テストで正しさを保証する |
| 投入文書 | CLAUDE.md、運用設計ルール、設計書 ロジック・プロンプト編（第2〜14章）、データ構造編（第5章のみ） |

**実装対象**

| サービス | 内容 |
| --- | --- |
| calendar_service | 1日の境界時刻の解決（論理的な本日の算出） |
| calendar_service | 日種別の解決（個別指定 → 祝日 → 曜日既定の順） |
| calendar_service | 負荷係数の解決 |
| cycle_service | 総作業量、残量、現在周回の導出 |
| slot_service | スロットの取得、教材への割当、充足検証 |
| quota_service | 日次ノルマの算出 |
| speed_service | 実効速度の周回別算出、必要速度、完了予測日 |
| threshold_service | 警告判定、強制リプラン判定、締切超過判定 |
| baseline_service | 計画基準値の記録と取得 |
| metrics_service | バッファ消費率、進捗率、報告率、連続報告日数、リプラン回数 |

**テスト（先に書く）**

設計書 ロジック・プロンプト編 第20章の検証観点をテストケース化する。特に以下は必須とする。

| 観点 | 検証内容 |
| --- | --- |
| 周回 | 1周目完了時に残量が0にならず、2周目のノルマが算出されること |
| 周回 | 現在周回が累積完了量から正しく導出されること |
| 周回別速度 | 2周目の速度が1周目と分離して算出されること |
| 周回別速度 | サンプル3件未満のとき直近周回の値で代替されること |
| 残量再配分 | 7日連続未達時、ノルマが全量繰越（8倍）ではなく再配分（約2.2倍）になること |
| バッファ非対称性 | バッファ日に実績が無くても翌日のノルマが増えないこと |
| バッファ非対称性 | バッファ日に実績があると翌日のノルマが減ること |
| 境界時刻 | 境界時刻より前の時刻において論理日が前日になること |
| 時間未入力 | 実効速度の分母・分子から除外されること |
| 日種別優先順位 | 個別指定が祝日設定を上書きすること |
| 負荷係数 | 係数変更で総量が保存されること |
| 境界値 | 残計画日0、実績0件、締切超過の各ケースで例外が発生しないこと |

**完了条件**

- 全テストが通過する
- 上記12観点が明示的にテストされている
- サービス層がHTTPに関する知識を一切持たない
- 日次ノルマ、残量、現在周回のいずれもデータベースに保存されていない

**注意点**

- **テストを後回しにしない。** ここの誤りは全機能に波及し、後から発見すると修正コストが跳ね上がる
- 残量の算出において、総量ではなく総作業量を用いること。この誤りは運用開始から数週間で顕在化する

**実装対象**

- 通信ログ（`ai/logger.py`）
- 日次報告フィードバックの呼び出し
- 週次要約の生成判定と遡及実行
- 今日の一言の生成判定と実行
- 例外のマッピング

**AI基盤の実仕様に基づく実装要件**

**開発キットの仕様は変更できない。以下は所与の制約として実装する。**

| 項目 | 要件 |
| --- | --- |
| Web検索 | メッセージ送信時に**必ず明示的に無効化する**。既定値が有効のため省略不可 |
| ナレッジ検索 | 明示的に無効化する |
| 会話の作成 | メッセージ送信前に会話を作成し、識別子を `ai_conversation` に保存する |
| 会話の単位 | 用途と日付ごとに分離する（日次報告、週次要約、今日の一言、総括レポート） |
| フォルダ | 目標ごとにフォルダを作成する。名前指定での会話作成機能を用い、存在しない場合は自動作成する |
| 親メッセージ順序 | 同一会話内の連続往復で増加させる。`last_parent_order` を更新する |
| 会話識別子の取得 | ローカルに保存した値を用いる。一覧取得APIを毎回呼ばない |
| タイムアウト | 設定値（既定60秒）を開発キットの設定に反映する |
| 再試行回数 | 設定値（既定1）を開発キットの設定に反映する。アプリ側の再送と二重にしない |
| 呼び出し間隔 | 設定値（既定2秒）の下限を守る |
| 認証 | 起動時に自動認証を試行する。手動認証はバックグラウンドスレッドで実行する |
| リダイレクト先 | 開発キットの既定値を使用する。サーバは別ポートで起動する |
| 稼働確認 | 起動時にモデルの利用可否を取得する |
| ナレッジ登録 | **使用しない。** 共有アシスタントに個人の学習記録を登録しない |
| ファイル添付 | 使用しない |

**例外マッピング**

| 開発キットの例外 | APIエラーコード |
| --- | --- |
| 認証関連の例外 | AI_AUTH_REQUIRED |
| API通信関連の例外 | AI_ERROR |
| チャット関連の例外 | AI_ERROR |
| 設定エラー | AI_CONFIG_ERROR |
| タイムアウト | AI_TIMEOUT |
| 基本例外（上記以外） | AI_ERROR |

**プロンプト縮退の実装**

設計書 ロジック・プロンプト編 16.5 の4段階を実装する。縮退が発生した場合、`ai_log.was_truncated` を true として記録し、応答とともに画面へ通知する。

**完了条件**

- 日次報告でフィードバックが取得できる
- Web検索の無効化が明示的に指定されている（コード上で確認可能）
- 会話識別子が保存され、同一日の再送で再利用される
- フォルダが目標ごとに作成される
- AI呼び出しが失敗しても実績入力が失われない
- AI応答なしで報告確定ができる
- 週次要約が起動時に遡及生成される
- 遡及生成時に呼び出し間隔の下限が守られる
- 今日の一言が同日中に再生成されない
- プロンプトが閾値超過時に段階的に縮退する
- 通信ログに送信文字数と縮退の有無が記録される
- AI基盤が利用不可でも記録機能が動作する

**注意点**

- **プロンプトはデータベースから読む。** ソースコードに埋め込まない
- 会話がAI基盤側に蓄積されるため、フォルダによる整理を必ず実装する

### Phase 11：実環境検証

| 項目 | 内容 |
| --- | --- |
| 目的 | 実環境での動作を確認し、設定値を調整する |
| 実施 | テッペイさんの手元で実施する |

**確認項目**

| 項目 | 確認内容 | 調整先 |
| --- | --- | --- |
| 認証 | ブラウザ経由の認証フローが完了すること | — |
| ポート | 8100と8400が衝突しないこと | `server.port` |
| アシスタント | 一覧が取得でき、選択できること | `ai.assistant_uid` |
| Web検索 | 無効化が有効に働くこと（検索結果が混入しないこと） | — |
| フォルダ | 目標名のフォルダが作成されること | `ai.folder_prefix` |
| 応答時間 | タイムアウト60秒が妥当か | `ai.timeout_seconds` |
| 入力上限 | 長文プロンプトが送信できるか。縮退が過剰に発生しないか | `ai.max_prompt_chars` |
| 頻度制限 | 週次要約の連続生成でエラーが出ないか | `ai.min_interval_seconds` |
| 応答品質 | フィードバックが期待した構成と深さを持つか | プロンプトテンプレート |

**入力上限の測定方法**

通信ログに送信文字数と縮退の有無を記録しているため、以下で判断する。

- 縮退が一度も発生していない場合、閾値を引き上げて情報量を増やす
- 通信エラーが発生した際の送信文字数を確認し、閾値を引き下げる

**応答品質の調整**

プロンプトの初期文面は暫定である。実際の応答を見て、以下の観点で調整する。

- 負荷を減らす提案が適切な頻度で出るか（出すぎ、出なさすぎのいずれも問題）
- 成長の指摘が具体的か、当たり障りのない内容になっていないか
- 行動提案が実行可能な粒度か

## 4. 並行実行の可否

```
Phase 1
   ↓
Phase 2 ────────────────┐
   ↓                    │
Phase 3 ──────┬─────────┤
   ↓          ↓         ↓
Phase 4    Phase 6   （テスト拡充）
   ↓          ↓
Phase 5 ──────┤
   ↓          ↓
   └──→ Phase 7, 8, 9（順不同）
              ↓
          Phase 10
              ↓
          Phase 11
```

Phase 6 は Phase 3 完了後に着手可能であり、Phase 4・5 と並行できる。ただし単独作業のため、実際には順次実行が現実的である。

## 5. 各フェーズ共通の指示事項

Claude Code へ渡す際、各フェーズの冒頭に以下を明示する。

```
# 共通指示

1. CLAUDE.md および運用設計ルールを必ず先に読むこと
2. 本フェーズのスコープ外を実装しないこと
3. 設計書に記載のない仕様を勝手に決めないこと。
   判断が必要な箇所は実装を止めて確認すること
4. 文字列リテラルおよび数値リテラルをソースコードに
   直接記述しないこと
5. サービス層にHTTPに関する知識を持ち込まないこと
6. 日次ノルマ、残量、現在周回をデータベースに保存しないこと
7. AI基盤の開発キットの仕様は変更できない。
   制約はアプリケーション側の設計で吸収すること
8. 実装完了後、完了条件を自己検証し結果を報告すること
```

特に3は重要である。設計書に未記載の箇所を推測で埋められると、後から発見が困難な仕様の齟齬が生まれる。

## 6. リスクと対応

| リスク | 影響 | 対応 |
| --- | --- | --- |
| Phase 2 のロジック誤り | 全機能に波及 | テストを先に書き、境界値を網羅する |
| 周回対応の実装漏れ | 運用開始数週間で計画が破綻 | Phase 2 の完了条件に明示的に含める |
| Web検索の無効化漏れ | フィードバック品質の劣化 | Phase 5 の完了条件でコード上の確認を求める |
| 入力上限の想定違い | 対話の失敗 | 縮退機構を先に実装し、実測で閾値を調整する |
| 頻度制限への抵触 | 週次要約の遡及生成が失敗 | 呼び出し間隔の下限を実装する |
| プロンプト応答品質の不足 | 中核価値の毀損 | Phase 11 で反復調整する前提とする |
| コンテキスト飽和による品質低下 | 実装の一貫性喪失 | 1フェーズ1セッションを厳守する |
| 設計書の未決事項の放置 | 実装時の判断ぶれ | 各フェーズ着手前に該当する未決事項を解消する |
