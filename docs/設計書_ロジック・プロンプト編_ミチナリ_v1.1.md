## 1. 本文書の目的と範囲

本文書は、ミチナリの算出ロジック、判定条件、およびAIプロンプトの設計を定義する。

データ構造、テーブル定義、API構成は「設計書 データ構造編」に記載する。

**第3〜14章は、`goal.category = EXAM`（資格試験）の目標を対象とした算出ロジックである。** `category = READING`（読書）および `category = WORK`（仕事）の目標は、日次ノルマ・実効速度・警告判定などの定量的な計画管理（要件定義書R-71、R-74）を持たないため、これらの章を適用しない。読書目標が用いるロジックは第21章に、仕事目標が用いるロジックは第22章に集約する。

## 3. 1日の境界時刻の解決

### 3.1 論理的な本日の算出

```
boundary = 設定値 calendar.day_boundary_hour（0〜11、既定値 0）

現在時刻の時が boundary 未満の場合：
    T = システム日付 − 1日
それ以外：
    T = システム日付
```

### 3.2 適用範囲

論理的な本日は、以下の全てにおいて用いる。

| 適用箇所 | 内容 |
| --- | --- |
| 日次ノルマの算出 | 基準日 |
| 日次記録の対象日 | `record_date` の決定 |
| 遡及入力の判定 | 「前日」の基準 |
| 完了予測の起点 | 累積開始日 |
| 今日の一言の生成判定 | 対象日 |
| 週次要約の生成判定 | 完了週の判定 |

### 3.3 設計意図

深夜まで学習する習慣がある場合、システム日付をそのまま用いると、午前1時の学習が翌日分として計上される。その結果、当日は未達、翌日は達成という実態と乖離した記録が生じる。

境界時刻を設定可能にすることで、この乖離を利用者の生活リズムに合わせて解消する。

**クライアント側でシステム日付から論理日を判断しない。** サーバが `GET /records/today` で返す値を用いる。設定値の解釈をサーバに一元化するためである。

## 4. 日種別の解決

### 4.1 解決順序

日 `d` の日種別は以下の順序で決定する。先に一致した規則を採用し、以降は評価しない。

```
1. calendar_day_override に d のレコードが存在する
   → その day_type を採用
   
2. holiday に d のレコードが存在し、
   かつ設定 holiday.treat_as_buffer が true
   → BUFFER を採用
   
3. day_type_default における d の曜日の設定を採用
```

**設計意図**

個別指定を最優先とすることで、「この土曜は勉強日にする」「この水曜は出張で不可」という実運用上の調整が、既定値の設定を変更せずに行える。除外日（OFF）は個別指定でのみ設定でき、既定値としては設定できない。

### 4.2 日種別ごとの扱い

| 日種別 | 日次ノルマ | ノルマ算出の分母 | 実効速度の算出 | 実績登録 |
| --- | --- | --- | --- | --- |
| PLAN | 算出する | 算入する | 対象 | 可能 |
| BUFFER | 0 | 算入しない | 対象 | 可能 |
| OFF | 0 | 算入しない | 対象外 | 可能 |

**BUFFER と OFF の差異**

いずれも日次ノルマの分母から除外されるが、実効速度の扱いが異なる。BUFFER 日は学習した場合にその実績を速度算出に反映する。OFF 日は「学習が不可能と事前に判明していた日」であり、仮に実績が登録されても速度算出から除外する。

この非対称性により、バッファ日の学習は翌日以降の日次ノルマを引き下げる形で即座に報われる。一方で、バッファ日に学習しなかったことによる負債は発生しない。

## 5. 負荷係数の解決

### 5.1 解決規則

```
w(g, d) = load_profile のうち、goal_id = g かつ
          date_from ≤ d ≤ date_to を満たすレコードの coefficient
          
          該当するレコードが存在しない場合は 1.0
```

`load_profile` は同一目標内で期間が重複しないよう制約されているため、該当レコードは0件または1件となる。

### 5.2 検証規則

負荷プロファイルの登録・更新時に以下を検証する。

| 検証項目 | 条件 |
| --- | --- |
| 期間の妥当性 | `date_from ≤ date_to` |
| 係数の妥当性 | `coefficient > 0` |
| 期間の重複 | 同一 goal 内の既存レコードと期間が重複しないこと |

## 6. 周回の導出

### 6.1 算出式

```
TW(m) = A(m) × N(m)

C(m)  = Σ study_log.amount_completed  （教材 m の全レコード）

R(m)  = max(0, TW(m) − C(m))

              ⎧ N(m)                        （C(m) ≥ TW(m)）
k(m) =        ⎨
              ⎩ min(N(m), floor(C(m) / A(m)) + 1)
```

### 6.2 現在周回内の進捗

```
現在周回の完了量 = C(m) − A(m) × (k(m) − 1)
現在周回の進捗率 = 現在周回の完了量 / A(m)
全体進捗率       = C(m) / TW(m)
```

### 6.3 設計意図

v1.0では残量を `A(m) − C(m)` としていたため、**1周目が完了した時点で残量が0となり、日次ノルマが消滅していた。** 資格学習では複数周回が前提であるため、この設計では運用開始から数週間で破綻する。

総作業量を基礎とすることで、周回をまたいだ計画が連続する。850問を3周する計画であれば、総作業量2550問に対して残量が算出され、1周目の完了は単なる通過点となる。

### 6.4 予定周回数の変更

予定周回数の変更は計画に大きな影響を与えるため、以下を行う。

| 項目 | 処理 |
| --- | --- |
| 検証 | 新しい予定周回数が、既に完了した周回数を下回る場合は拒否する |
| 基準値 | 変更時に `plan_baseline` へ `CYCLE_CHANGED` の理由でレコードを追加する |

予定周回数の削減は、AIによる「中度」の負荷軽減提案に含まれる。3周の計画を2周に減らすことは、範囲を絞る有効な手段である。

### 6.5 周回番号の入力

`study_log.cycle_number` は利用者が入力する。入力欄には `k(m)` を既定値として提示するが、上書きを許容する。

これは「1周目を完全に終える前に、苦手分野だけ2周目に入る」といった運用に対応するためである。算出値を強制すると、実態と記録が乖離する。

## 7. 日次ノルマの算出

### 7.1 中核の式

```
P(m) = { d | T ≤ d ≤ D(m) かつ type(d) = PLAN }

W(m) = Σ_{d ∈ P(m)} w(g, d)

               ⎧ R(m) × w(g, T) / W(m)   （S(m) ≤ T かつ type(T) = PLAN かつ W(m) > 0）
quota(m, T) =  ⎨
               ⎩ 0                        （それ以外）
```

`S(m) ≤ T` （今日が教材の学習期間開始日以降）は当初この式には含まれておらず、7.3の一覧条件
にのみ存在していたが、学習期間開始前の教材を「今日時点では未着手」として一貫して扱うため
式本体に追加した。この条件は `quota(m, T)` を参照するすべての箇所（本日のノルマ一覧・7.3、
警告判定・11.1、基準値記録・12.2、AI向け状況出力）に共通適用される。

### 7.2 設計の要点

**未達分を加算しない**

日次ノルマは保存されず、毎日この式で再評価される。前日に未達があった場合、`C(m)` が想定より小さいため `R(m)` が大きくなり、同時に `P(m)` が1日分減少する。結果として翌日のノルマは緩やかに上昇する。

この方式（残量再配分）と、未達分を翌日に加算する方式（全量繰越）の差は決定的である。

| 経過 | 全量繰越 | 残量再配分（採用） |
| --- | --- | --- |
| 初日 | 10 | 10 |
| 1日未達 | 20 | 約12 |
| 2日未達 | 30 | 約15 |
| 7日未達 | 80 | 約22 |

全量繰越では1週間の停滞で心理的限界を超えるが、残量再配分では緩やかに上昇するのみである。したがって負債の上限設定（キャップ）は不要となる。

**負荷係数による配分**

`w(g, d)` を分子と分母の双方に用いることで、総量は変化せず配分のみが変わる。ある期間の係数を下げれば、その分は自動的に他の計画日へ寄せられる。「今月は減らす」と「計画を諦める」が明確に区別される。

**W(m) = 0 の場合**

締切までに計画日が1日も残っていない状態を意味する。この場合ノルマは0とし、締切超過警告（NT-06）の対象とする。

### 7.3 目標単位の集約

ダッシュボードにおける「本日のノルマ」は、進行中の全目標に属する全教材について、以下の条件を満たすものを列挙する。

```
S(m) ≤ T ≤ D(m) かつ material.is_active = true
      かつ goal.status = ACTIVE
```

## 8. 実効速度の算出

### 8.1 周回別の算出

```
V(m, c) = { study_log | material_id = m
                        かつ cycle_number = c
                        かつ minutes_spent IS NOT NULL
                        かつ minutes_spent > 0
                        かつ type(record_date) ≠ OFF }

                 Σ_{v ∈ V(m,c)} amount_completed
speed(m, c) = ────────────────────────────────────
               Σ_{v ∈ V(m,c)} minutes_spent / 60
```

単位は「分量／時間」である。

### 8.2 完了予測に用いる速度

```
                ⎧ speed(m, k(m))          （V(m, k(m)) のサンプル数 ≥ 3）
speed_eff(m) =  ⎨ speed(m, k(m) − 1)      （現在周回が不足し、直近周回に実績がある）
                ⎩ 算出不能                 （いずれも不足）
```

### 8.3 設計意図

**周回によって速度は大きく変化する。** 2周目は既知の問題を解くため処理が速く、1周目の2倍以上になることも珍しくない。

全周回を混合して平均を取ると、1周目の後半において、まだ経験していない2周目の速度が混入することはないが、逆に2周目の予測に1周目の遅い速度が混入する。結果として2周目の完了予測が過度に悲観的となり、不要な警告が発生する。

周回別に算出し、現在周回の値を用いることで、予測の精度が保たれる。

**サンプル数の下限を3とした理由**

周回の切り替わり直後は実績が1〜2件しかなく、外れ値の影響を強く受ける。3件以上を要求し、それまでは直近周回の速度で代替する。

### 8.4 除外規則

| 除外対象 | 理由 |
| --- | --- |
| `minutes_spent` が NULL または 0 | 分母が不明。0時間として扱うと速度が不当に高く算出される |
| 日種別が OFF の日 | 学習不可日として事前登録された日であり、例外的な実績は代表値にならない |

進捗のみ登録において投下時間を任意入力としたのは、うっかり忘れの吸収を優先したためである。その結果として時間が不明な日が生じるが、それらを速度算出から除外することで、「サボりは残量に正しく反映されるが、実力の推定値は汚染されない」状態を作る。

### 8.5 サンプル不足時の扱い

`speed_eff(m)` が算出不能の場合、以下の扱いとする。

| 項目 | 扱い |
| --- | --- |
| 完了予測日 | null |
| 強制リプラン判定 | 実施しない |
| UI表示 | 「実績データが不足しています」を表示 |

## 9. 必要速度の算出

### 9.1 利用可能時間の算出

日 `d` において目標 `g` が確保できる時間は以下とする。

```
slots(d) = resource_slot のうち、
           resource_slot_weekday に d の曜日を含み、
           かつ is_active = true であるもの

duration(s)      = end_time(s) − start_time(s)          （分）
total_minutes(d) = Σ_{s ∈ slots(d)} duration(s)

alloc(g, s) = goal_slot_allocation の minutes
              （行が存在しない場合は 0）

H(g, d) = Σ_{s ∈ slots(d)} min( alloc(g, s), duration(s) )   （分）
```

算出は常に分（整数）で行う。時間（hour）は表示時にのみ `分 / 60` を小数第2位以下切り捨てで換算した値を用いる（仕様書6.3、10章）。ただし実効速度・必要速度は「分量／時間」を単位とするため（8.1）、これらの算出に用いる時間は切り捨てずに `分 / 60` をそのまま使う。

`min` を取るのは、配分の設定後にスロットを短縮した場合に `alloc(g, s) > duration(s)` となりうるためである（仕様書NT-09。この状態は警告のみで保存を許容するため、算出側で安全に丸める必要がある）。

**設計意図**

配分を「目標に対する1つの比率」ではなく「スロットごとの分数」として持つことで、時間の総量だけでなく**どの形の時間をどの目標に割り当てるか**を利用者が明示できる。比率方式では全スロットから一律の割合を取るため、「通勤時間は英単語に充て、夜の机上時間は過去問に充てる」という区別が表現できなかった。

### 9.2 教材へのスロット割当

目標に複数の教材がある場合、スロットの割当は以下の規則で決定する。

```
手順1：各スロット s について、適合する教材の集合 M(s) を求める
       m ∈ M(s) ⟺ (required_environment(m) = ANY
                    または required_environment(m) = environment(s))
                   かつ (required_block_minutes(m) が NULL
                         または required_block_minutes(m) ≤ duration(s))
                   かつ S(m) ≤ d ≤ D(m)
                   かつ R(m) > 0

手順2：M(s) が空でない場合、スロット s の時間を
       M(s) の各教材へ「必要時間比」で按分する

       必要時間(m) = R(m) / speed_eff(m)
       ただし speed_eff(m) が算出不能の場合は R(m) を代替値として用いる

手順3：M(s) が空の場合、そのスロットは未割当とする
```

**設計意図**

環境タグと必要連続時間による適合判定を先に行うことで、「移動中に携帯端末で解く教材」と「連続90分のPC作業を要する教材」が自動的に別のスロットへ振り分けられる。時間の総量ではなく、時間の形状が管理対象となる。

### 9.3 必要速度

```
available_hours(m) = Σ_{d ∈ P(m)} (H(g, d) に占める m への割当時間) × w(g, d)

required_speed(m) = R(m) / available_hours(m)
```

`available_hours(m)` が 0 の場合、必要速度は算出不能とし、締切超過警告の対象とする。

### 9.4 スロット充足の検証

教材登録時および目標の進行中への遷移時に以下を検証する。

```
教材 m について、
  ∃ s ∈ (全ての有効なスロット) :
      (required_environment(m) = ANY
       または required_environment(m) = environment(s))
      かつ (required_block_minutes(m) が NULL
            または required_block_minutes(m) ≤ duration(s))
      かつ (s の適用曜日に、教材期間内の PLAN 日が1日以上存在する)
```

充足しない場合、警告を表示する。保存は許容する。

**警告文の例**

```
教材「{教材名}」は{必要連続時間}分の連続した時間を必要としますが、
現在のリソース設定における最長スロットは{最長時間}分です。
時間の総量は足りていても、この教材に必要な形の時間が
確保されていない可能性があります。
```

これは時間量のみを管理するシステムでは検知できない状態であり、本アプリ固有の検証項目である。

## 10. 完了予測日の算出

### 10.1 算出手順

```
required_hours(m) = R(m) / speed_eff(m)

accumulated = 0
d = T

while accumulated < required_hours(m):
    if type(d) = PLAN:
        accumulated += (H(g, d) に占める m への割当時間) × w(g, d)
    d = d + 1日
    
    if d > D(m) + 365日:
        return 算出打ち切り（大幅超過）

forecast_date(m) = d − 1日
```

### 10.2 バッファ日を除外する理由

計画日のみを累積するため、予測は常に悲観方向へ振れる。実際にはバッファ日の学習によって前倒しされるため、「警告は出るが実際には間に合う」方向の誤差となる。

学習計画において、間に合わないものを間に合うと予測する誤りは致命的であるが、その逆は許容できる。したがってこの非対称性は意図的なものである。

### 10.3 乖離日数

```
overrun_days(m) = forecast_date(m) − D(m)
```

正の値は締切超過を意味する。

## 11. 判定ロジック

### 11.1 警告判定（NT-01）

```
baseline(m) = plan_baseline のうち material_id = m かつ
              effective_from ≤ T を満たすレコードの中で
              effective_from が最大のもの

条件： quota(m, T) / baseline_daily_quota(baseline(m))
       ≥ 設定値 threshold.warning_ratio（初期値 1.20）
```

`type(T)` が PLAN でない日は判定しない。バッファ日にはノルマが存在しないためである。

### 11.2 強制リプラン判定（NT-02）

```
条件： overrun_days(m) > 設定値 threshold.replan_overrun_days（初期値 3）
```

`speed_eff(m)` が算出不能な場合は判定しない。

### 11.3 二段階構成の意図

| 段階 | 検知対象 | 意味 |
| --- | --- | --- |
| 警告（NT-01） | ノルマの上昇率 | ペースの乱れ。まだ挽回可能な段階 |
| 強制リプラン（NT-02） | 完了予測日の超過 | 合格可能性の毀損。計画の修正が必要 |

警告は「遅れている」ことを、強制リプランは「このままでは間に合わない」ことを示す。前者はバナー表示にとどめ、後者はモーダルで目標編集画面へ誘導する。

実効速度が向上すれば、負債があっても強制リプランは発火しない。逆に毎日ノルマを達成していても、初期の総量見積もりが甘ければ発火する。判定基準を「合格に間に合うか」に置いているためである。

### 11.4 締切超過判定（NT-06）

```
条件： T > D(m) かつ R(m) > 0 かつ material.is_active = true
```

## 12. 計画基準値の再設定

### 12.1 再設定の契機

以下の操作により `plan_baseline` に新しいレコードを追加する。

| 契機 | reason |
| --- | --- |
| 目標の進行中への遷移 | INITIAL |
| リプラン操作の実行 | REPLAN（予約値、下記参照） |
| 受験日の確定日への変更 | EXAM_DATE_FIXED |
| 教材の追加・総量変更・締切変更 | MATERIAL_CHANGED |
| 予定周回数の変更 | CYCLE_CHANGED |

**REPLAN が予約値である理由（1.1（改13））**：仕様書は「リプラン」を独立した操作としては定義していない。警告・強制リプランの条件を満たした場合の導線は、警告バナーおよびモーダル（仕様書6.1・5.3 MD-01）から**目標編集画面へ誘導**し、利用者がそこで教材・予定周回数・受験日を修正することで基準値が再設定される、というものである。したがって実際に記録される reason は MATERIAL_CHANGED・CYCLE_CHANGED・EXAM_DATE_FIXED のいずれかであり、REPLAN が記録される経路は現時点では存在しない。将来「現在の計画をそのまま引き直す」独立操作を設ける場合に備えて enum の値としては残すが、それまでは記録されない予約値として扱う。

### 12.2 記録内容

```
T' = max(T, S(m))

effective_from             = T
baseline_daily_quota       = quota(m, T')（再設定後の値）
remaining_at_baseline      = R(m)
plan_days_at_baseline      = |{ d | T' ≤ d ≤ D(m) かつ type(d) = PLAN }|
planned_cycles_at_baseline = N(m)
reason                     = 上記の契機に対応する値
```

`baseline_daily_quota`・`plan_days_at_baseline` の算出にはいずれも T ではなく `T' = max(T, S(m))`
を起点として用いる（`effective_from` 自体は基準値の検索に使う実際の記録日 T のまま変えない）。
再設定の契機（12.1）はすべてユーザー操作であり、教材の学習期間開始日到来を契機とした自動
再設定は存在しない。そのため T をそのまま用いると、学習期間開始前（T < S(m)）に基準値が
記録された教材は quota(m, T) = 0（7.1のS(m)≤T条件）が基準値として固定されてしまい、開始日を
迎えてペースが乱れても11.1の警告判定条件（`baseline_daily_quota <= 0` の場合は判定しない）
により警告が永久に発火しなくなる。学習期間開始時点で見込まれるノルマを基準値とすることで
これを避ける。`plan_days_at_baseline` も同じ T' を起点にしないと、`baseline_daily_quota ×
plan_days_at_baseline = remaining_at_baseline` という関係が崩れ、リプラン履歴表示・AI向け
状況出力の数値が矛盾するため、両者は同じ起点で揃える。

### 12.3 設計意図

リプラン後は新しい計画が基準となるため、リプラン前の乖離を引きずらない。

基準値を履歴として保持することで、「何回リプランしたか」「各リプラン時点でどの程度の負荷だったか」を後から検証できる。**この履歴は総括レポートにおける最重要の分析材料となる。**

## 13. 補助指標の算出

### 13.1 バッファ消費率

```
経過バッファ日 = { d | goal.start_date ≤ d < T かつ type(d) = BUFFER }

実績あり日 = 経過バッファ日のうち、goal g 配下の教材の study_log が
             1件以上存在する日

buffer_usage_rate = |実績あり日| / |経過バッファ日|
```

**目標による絞り込み（1.1（改13））**：実績あり日の判定は、対象目標 g 配下の教材（material.goal_id = g.id）に紐づく `study_log` のみを数える。目標で絞り込まないと、同時進行している別目標の実績によってバッファ日が消費済みと判定され、目標ごとの余裕度を表さない値になる。

**適用範囲**：本指標は `category = EXAM` の目標にのみ適用する。読書・仕事目標は日種別（第4章）による計画運用の対象外であり（要件定義書R-71・R-74、21.1・22.1）、バッファという概念自体を持たないため算出しない（算出結果は「なし」とし、画面にも表示しない）。

なお、週次要約の `{{week_metrics}}`（17.3）が示すバッファ消費状況は、集計窓が「週内」である点だけが本指標と異なる同一の算出であり、実装は共通化する。

**意味**

余裕度の直接指標である。バッファをほとんど使わずに計画通り進んでいれば余裕があり、毎週末フルに使ってようやく維持している状態であれば計画自体が過密である。

この指標はAIへの入力に含める。数値実績のみからは「計画が重すぎる」という判断は困難だが、バッファ消費率が高止まりしていれば、それは計画の設計そのものに問題があることを示す。

### 13.2 進捗率

```
progress_rate(m) = C(m) / TW(m)
```

教材の単位が「問」「ページ」「回」と異なるため、目標単位の進捗率は単純合算では意味を持たない。ダッシュボードでは教材別に表示し、目標単位では「教材ごとの進捗率の平均」を参考値として表示する。

### 13.3 報告率（KPI）

```
report_rate(g) = (goal g のカテゴリに対応する記録状態列（exam/reading/work_record_state）が
                   REPORTED の日数)
                 / (goal.start_date から T までの日数)
```

要件定義書に定めたKPIである。記録状態はカテゴリ（資格試験／読書／仕事）ごとに独立しているため（データ構造編5.4、1.1（改16））、目標gの報告率は必ずgのカテゴリに対応する列のみを参照する。他カテゴリの確定状況は混入させない（例: 資格試験を確定していない日でも、その日に仕事を確定していれば仕事目標の報告率にはカウントする）。

### 13.4 連続報告日数

```
T から遡り、goal g のカテゴリに対応する記録状態列が REPORTED である日が連続する日数。
type(d) = BUFFER または OFF の日は、報告がなくても連続を中断しない。
```

バッファ日に報告しないことは想定された行動であり、それによって連続記録が途切れるのは設計思想（バッファの非対称性）に反する。

### 13.5 リプラン回数

```
replan_count(g) = plan_baseline のうち、goal 配下の material に属し、
                  reason ≠ INITIAL であるレコード数
```

総括レポートおよびエクスポートに含める。

## 14. 品質指標の正規化

### 14.1 変換規則

| 方式 | 入力 | 保存値 |
| --- | --- | --- |
| OBJECTIVE | 0〜100の数値 | そのまま |
| SELF_SCORED | 0〜100の数値 | そのまま |
| SUBJECTIVE | 1〜5の選択 | 1→20, 2→40, 3→60, 4→80, 5→100 |
| NONE | — | NULL |

### 14.2 集約規則

| 粒度 | 算出方法 |
| --- | --- |
| 日別 | その日の値をそのまま表示 |
| 週別 | 週内の値の単純平均 |
| 月別 | 月内の値の単純平均 |

分量による加重平均ではなく単純平均とする。「10問解いて80%」と「100問解いて60%」を加重平均すると後者に引きずられるが、推移の可視化においては各測定機会を等価に扱うほうが変化を読み取りやすい。

### 14.3 周回別の系列分離

品質指標の推移表示では、`cycle_number` ごとに系列を分離する。**2周目以降は記憶による正答が混入するため、1周目と同一系列で表示すると成長を過大評価する。**

グラフ上では、周回の切り替わり時点に区切り線を表示する。

### 14.4 合格基準線

紐づく `exam_subject` の合格点を推移グラフ上に水平線として重畳する。`passing_score_type` が RAW_SCORE（点数入力）の場合は `passing_score / passing_score_max * 100` で百分率へ正規化してから用いる（データ構造編5.3）。教材が複数科目に紐づく場合、正規化後の値が最も高いものを採用する。

### 14.5 SELF_SCORED の位置づけ

記述式など、システムが正誤を判定できない領域では自己採点を用いる。完全な客観性は担保されないが、同一人物が同一基準で採点する限り、**推移としての傾向は十分に有意である**。

正答率が算出できない領域を「測定不能」として放置すると、要件定義書に記した課題3（合格への接近を実感できない）が未解決のまま残る。近似的であっても数値化することに価値がある。

## 15. 週次要約の生成

### 15.1 週の定義

月曜日を週の開始日、日曜日を終了日とする。

### 15.2 生成判定

アプリケーション起動時に以下を評価する。

```
手順1：直近の完了週を求める
       last_sunday = T 以前で最も近い日曜日
                     （T が日曜の場合は T 自身）

手順2：遡及対象の週を列挙する
       設定値 summary.lookback_weeks（初期値 4）の範囲で、
       完了しているが weekly_summary が未生成の週を抽出

手順3：抽出された各週について、
       その週に study_log が1件以上存在する目標を対象に生成
       （category=READING の目標は study_log を持たないため、
        変更なしに自動的に対象外となる。21.1参照）

手順4：生成は呼び出し間隔の下限（既定2秒）を守って逐次実行する
```

**設計意図**

「日曜日に必ずアプリを起動するとは限らない」という前提に立つ。生成判定を起動時の遡及方式とすることで、バックグラウンドジョブを持たないローカル環境でも確実に生成される。

遡及上限を設けるのは、長期間の未起動後に大量のAI呼び出しが発生することを防ぐためである。

### 15.3 対話への注入

日次報告のプロンプトには、設定値 `summary.inject_weeks`（初期値 4）で指定された週数分の要約を新しい順に含める。全期間の日記原文は含めない。

## 16. AI連携の実装仕様

本章は、AI基盤の開発キットが提供する実仕様に基づく。**開発キットの仕様は変更できない**ため、制約を前提としたアプリケーション側の実装を定義する。

### 16.1 初期化と設定

**認証はPAT（Personal Access Token）を主とする。** 詳細は16.2を参照。

| 設定項目 | 値の出所 |
| --- | --- |
| Host（接続先サブドメイン） | `app_setting: ai.host`（例: `xxx.newton-x.net`） |
| PAT | 開発キットの設定ファイルに委ねる。`app_setting` には保存しない |
| クライアント識別子・テナント識別子 | `app_setting: ai.client_id` / `ai.tenant_id`（EntraIDフォールバック時のみ使用。通常は空でよい） |
| 接続先URL | Hostから自動導出（`https://{host}/api`）。`app_setting: ai.api_base_url` を明示指定した場合はそちらを優先 |
| タイムアウト | `app_setting: ai.timeout_seconds`（既定60） |
| 再試行回数 | `app_setting: ai.max_retries`（既定1） |
| リダイレクト先（フォールバック時のみ） | 開発キットの既定値（ローカル8400番） |

**再試行回数を1とする理由**

開発キットの既定値は3である。アプリケーション側でも再送を提供するため、既定のままでは実質的に多重の再試行となり、頻度制限に抵触するリスクが高まる。開発キット側を1に抑え、再送の判断を利用者に委ねる。

**ポートの衝突回避**

認証フローがローカル8400番を使用するため、アプリケーションサーバは別ポートで起動する。`app_setting: server.port` の既定値を8100とする。

### 16.2 認証

**開発キットの現行の公式利用ガイドは、Host＋PATによる認証を標準の方法として案内している。** ブラウザ経由のOAuth／デバイスコード認証（EntraID）は、開発キット内部にフォールバック経路として残るのみであり、PATが設定されていれば優先して使用される。当初の設計はブラウザ認証を主経路としていたが、公式情報に基づき以下のとおり改める。

```
起動時：
    Host・PATが設定済みかを確認する（開発キットの設定を参照）
    設定済み → PATによる認証ヘッダーが利用可能かを確認し、認証済みとする
    未設定・無効 → 未認証として扱い、設定画面でのHost・PAT入力を促す

設定画面からのPAT登録：
    NewtonX Web版で発行したPATとHostを入力し、
    開発キットの設定（ConfigManager）へ反映する
    以降、追加の認証操作は不要

フォールバック（PAT未設定時のみ）：
    設定画面からブラウザ経由の認証フローを起動できる
    バックグラウンドスレッドで実行する
    （ブラウザ起動と待機を伴うため、APIスレッドをブロックしない）
    クライアントは認証状態をポーリングして完了を検知する
```

トークン・PATの保存は開発キットに委ねる。アプリケーション側で独自に保管しない。

### 16.3 会話の管理

**制約：メッセージ送信前に会話を作成し、その識別子を指定する必要がある。**

**方針：用途と日付ごとに会話を分離する。**

```
手順1：会話を格納するフォルダを確保する
       目標に紐づく会話（週次要約・総括レポート）：
           フォルダ名 = "{ai.folder_prefix}_{目標名}"
       目標に紐づかない会話（今日の一言・日次報告）：
           フォルダ名 = "{ai.folder_prefix}"（共通フォルダ）
       名前指定でのフォルダ内会話作成機能を用い、
       存在しない場合は自動作成する

手順2：ai_conversation テーブルから、
       (goal_id, scope, scope_key) に一致するレコードを検索する

手順3：存在する場合 → conversation_uid を使用する
       存在しない場合 → 会話を新規作成し、識別子を保存する

手順4：メッセージを送信する
       Web検索：明示的に無効化する（既定値が有効のため必須）
       ナレッジ検索：無効化する
       親メッセージ順序：last_parent_order を送信する（16.3.1参照）

手順5：送信後、last_parent_order を更新する（将来の開発キット改修に備えた記録。16.3.1参照）
```

#### 16.3.1 親メッセージ順序に関する既知の制約（要検証）

導入済みの開発キット（NewtonX ADK v0.10.5）を実際にソースコードで確認したところ、`send_message()`のメソッドシグネチャに親メッセージ順序を指定する引数が存在せず、送信内容には常に固定値0が設定される（バンドルされた公式ドキュメントとの矛盾を確認済み）。したがって、`last_parent_order` を送信しても現状は文脈維持に寄与しない。

**この制約を前提に、同一日内の複数往復における文脈維持は17.2の `{{conversation_history}}`（本アプリが `chat_message` テーブルに保持する対話履歴の全文注入）で実現する。** この方式はAI基盤側のスレッド機能の実装状況に依存しないため、上記の制約があっても文脈維持は成立する。

`ai_conversation.last_parent_order` の記録自体は将来の開発キット改修に備えて継続するが、実装時点では実効性を持たない値として扱う。開発キット側でこの制約が解消された場合は、対話履歴の全文注入を縮退時のみに用いる構成へ最適化してよい（22.未決事項に追記）。

**回答が出力上限で途切れた場合の継続取得について**：開発キットのベストプラクティスは「終端マーカー方式」（親メッセージ順序を指定して続きを要求する）を推奨しているが、これも親メッセージ順序に依存するため本アプリでは使用しない。代わりに、直前の応答本文（またはその末尾）をプロンプトへ含めて「以下の続きを出力してください」と自己完結した指示で新規に送信する方式を取る。

**会話の単位**

| 用途 | scope_key | 会話タイトル |
| --- | --- | --- |
| 日次報告 | 対象日 | `{日付} 日次報告` |
| 週次要約 | 週開始日 | `{週開始日}週 週次要約` |
| 今日の一言 | 対象日 | `{日付} 今日の一言` |
| 総括レポート | 固定値 "main" | `総括レポート` |

**設計意図**

会話を用途ごとに分離することで、異なる目的のプロンプトが文脈として混入することを防ぐ。日次報告のフィードバックが、同日朝に生成した「今日の一言」の文脈に引きずられる事態を構造的に排除する。

目標に紐づかない会話（今日の一言・日次報告）も、goal_idはNULLのまま共通フォルダ（ai.folder_prefix）配下に作成する。これにより、NewtonX側でユーザがこの共通フォルダを削除するだけでアプリ由来の会話をまとめて解放できる。フォルダ配下に日付ごとの会話が複数蓄積されることは許容する（会話の分離方針とは独立した要件のため）。

日をまたぐ文脈は、会話の継続によってではなく、週次要約をプロンプトに注入することで実現する。この方式であれば、注入する情報量をアプリケーション側で完全に制御でき、会話の肥大化による入力上限の超過も回避できる。

**アシスタントへのナレッジ登録は行わない。** アシスタントが組織内で共有される可能性があり、個人の学習記録を登録することは不適切である。

### 16.4 呼び出し頻度の制御

```
直近の呼び出し時刻を保持し、
経過時間が設定値 ai.min_interval_seconds（既定2秒）未満の場合、
差分だけ待機してから送信する
```

週次要約の遡及生成では複数回の呼び出しが連続するため、この制御が特に重要となる。

### 16.5 プロンプトの段階的縮退

**制約：入力上限は明示されていない。**

**方針：組み立て後の文字数が閾値を超える場合、優先度の低い情報から削減する。**

```
手順1：全情報を含むプロンプトを組み立てる

手順2：文字数が設定値 ai.max_prompt_chars（既定30000）以下なら
       そのまま送信する

手順3：超過する場合、以下の順序で削減し、
       各段階で再度文字数を評価する

  段階1：週次要約を古い順に1件ずつ除外する（最低1件は残す）
  段階2：締切が遠い教材の情報を集約表示に置き換える
  段階3：当日の対話履歴を古い往復から除外する
  段階4：日記本文を末尾優先で切り詰める（先頭から削る）

手順4：縮退が発生した場合、
       ai_log の was_truncated を true として記録し、
       応答とともに縮退の発生を画面に通知する
```

**段階4で「先頭から削る」理由**

日記は時系列で書かれるため、末尾ほど直近の状況を反映している。切り詰める場合、末尾を残すほうが情報価値が高い。

**運用による上限の把握**

`ai_log.prompt_chars` と `was_truncated` を記録することで、実際にどの文字数で問題が生じたかを運用の中で把握できる。閾値の初期値30000は暫定であり、実測に基づいて調整する。

### 16.6 例外処理

| 開発キットの例外 | APIエラーコード | 画面での扱い |
| --- | --- | --- |
| 認証関連の例外 | AI_AUTH_REQUIRED | 設定画面での再認証を促す |
| API通信関連の例外 | AI_ERROR | エラー内容と再送ボタンを表示 |
| チャット関連の例外 | AI_ERROR | 同上 |
| 設定エラー | AI_CONFIG_ERROR | 設定画面への遷移を促す |
| タイムアウト | AI_TIMEOUT | 再送ボタンを表示 |
| 基本例外（上記以外） | AI_ERROR | エラー内容を表示 |

**API通信関連の例外は、頻度制限に起因する可能性がある。** この場合、エラーメッセージに「時間をおいて再試行してください」を含める。

**実装上の注意（タイムアウトの判定方法）**：導入した開発キットの例外クラスは `NewtonXError` / `AuthenticationError` / `APIError` / `ConfigurationError` / `FileUploadError` / `ChatError` の6種であり（ソースコードで確認済み）、タイムアウト専用の例外クラスは存在しない。通信タイムアウトも内部的に `APIError` へ一律ラップされるため、型による判定はできない。呼び出し側で計測した経過時間が `ai.timeout_seconds` を超えているか、またはエラーメッセージにタイムアウトを示す文字列が含まれるかによって `AI_TIMEOUT` を判定する。

### 16.7 障害時の動作保証

**AI呼び出しの失敗により、実績入力の内容が失われてはならない。**

| 保証項目 | 実装方針 |
| --- | --- |
| 入力内容の保持 | 日次報告画面では、実績と日記をクライアント側の状態として保持する。AI応答の成否と独立させる |
| 確定の許容 | AI応答が得られない状態でも報告の確定を許容する。`chat_message` は空となる |
| 記録機能の継続 | AI基盤が利用不可でも、実績登録、閲覧、分析は全て動作する |
| 状態の表示 | AI基盤の稼働状況を起動時に確認し、利用不可の場合はダッシュボードに表示する |

AIとの対話は本アプリの中核だが、それが利用できないことを理由に記録自体が失われるのは本末転倒である。

### 16.8 通信ログ

設定 `log.ai_enabled` が有効な場合、全ての呼び出しについて `ai_log` にレコードを追加する。

記録項目には、送信文字数と縮退の有無を含める。これにより、入力上限の実測値を運用の中で把握できる。

保持期間を超過したレコードは起動時に削除する。

# フィードバックの構成

以下の四点を、この順序で述べてください。

## 1. 状況の解釈
数値実績と記述内容を突き合わせ、本日の学習がどのような状態
だったかを解釈してください。数値だけを繰り返すのではなく、
記述内容から読み取れる背景要因（業務の繁忙、疲労、集中度、
理解の詰まり）を数値と関連付けて述べてください。

## 2. 成長の指摘
「学んだこと」の記述を、過去の週次要約に含まれる同一主題の
記述と比較してください。説明の解像度、用語の正確さ、
構造化の度合いに変化があれば、具体的に指摘してください。

これは正答率では測定できない成長です。
変化が見られない場合は無理に指摘せず、この項目を省略して
構いません。

## 3. 明日以降の行動提案
具体的で実行可能な提案を、多くとも三点に絞ってください。
「頑張りましょう」のような抽象的な激励は不要です。

## 4. 計画に関する提案（必要な場合のみ）
計画そのものに問題があると判断した場合のみ、以下から
適切な段階を選んで提案してください。

【軽度】特定期間の負荷係数を下げる
【中度】教材の優先順位を変更する、学習範囲を絞り込む、
        予定周回数を減らす
【重度】受験日を後ろ倒しにする、目標を一時停止する
【即時】本日は休息を取る

計画に問題がなければ、この項目は省略してください。

# 重要な原則

**負荷を減らす提案を、増やす提案と同等に扱ってください。**

遅れが出ているとき、ノルマを引き上げる提案は最も安易な選択肢
ですが、多くの場合それは正しくありません。学習者が疲弊して
学習を中断すれば、合格の可能性はゼロになります。

以下の場合、負荷を減らす提案を積極的に検討してください。
- 記述内容から疲労や余裕のなさが読み取れる
- バッファ日の消費率が継続的に高い
- 分量は達成しているが品質指標が停滞している
- 必要速度が実効速度を大きく上回っており、
  現実的な努力では埋まらない

品質指標が停滞している場合、量を増やすことは逆効果である
可能性が高いことに留意してください。同じ教材を漫然と周回する
のではなく、誤答分野への集中や理解の確認といった、
やり方の変更を提案してください。

周回数についても同様です。3周する計画が過大であるなら、
2周に減らして1周あたりの精度を上げるほうが、
合格の可能性は高まります。

**「今日は休みましょう」と言うことを躊躇しないでください。**
それが合格への最短経路である場合があります。

### 18.1 生成手順

```
手順1：出力対象の目標がクローズ済みであることを確認する

       週次要約と総括レポートの匿名化版を生成する
       （既に存在する場合は再利用する）
       category=READINGの目標には週次要約が存在しないため、
       読了レポート（goal_retrospective）の匿名化版のみ生成する（18.2）
       category=WORKの目標には週次要約が存在しないため、

手順4：選択された項目のみを収集する

手順5：Markdown形式とJSON形式の双方を生成する

手順6：出力ディレクトリに保存し、パスを返す
```

### 18.2 匿名化の処理

| 対象 | 処理 |
| --- | --- |
| 日記本文 | 出力から除外する |
| AI対話履歴 | 出力から除外する |
| 週次要約 | 匿名化指示を付与して再生成する |
| 総括レポート | 匿名化指示を付与して再生成する |
| 実績数値 | そのまま出力する（個人特定情報を含まないため） |
| リプラン履歴 | そのまま出力する |

匿名化版は元の版とは別レコードとして保持し、元の版を削除しない。

**読書目標（category=READING）の場合**：「日記本文」は`reading_log.recall_body`に読み替えて除外する。「週次要約」は対象外（存在しないため）。「総括レポート」は読了レポートに読み替え、匿名化指示を付与して再生成する。「実績数値」「リプラン履歴」も対象外（存在しないため）。

**仕事目標（category=WORK）の場合**：「日記本文」は`work_log.body`に読み替えて除外する。「週次要約」は対象外（存在しないため）。「総括レポート」は月次報告・半期評価に読み替え、対象goalに紐づく全`goal_retrospective`（period_type問わず）それぞれに匿名化指示を付与して再生成する。「実績数値」「リプラン履歴」も対象外（存在しないため）。

### 18.3 生成時の注意

匿名化版の生成には、週数分のAI呼び出しが発生する。呼び出し間隔の下限を守り、進捗を画面に表示する。読書目標では週次要約が存在しないため、匿名化版生成に伴うAI呼び出しは読了レポート1回のみとなる。仕事目標も週次要約が存在しないため、匿名化版生成に伴うAI呼び出しは、対象goalに紐づく生成済みの月次報告・半期評価の件数分（period_type問わず）となる。

## 19. 算出処理の性能設計

### 19.1 課題

ダッシュボードの初期表示要件は2秒以内である。しかし日次ノルマ、実効速度、完了予測日の算出には、日種別の解決を締切までの全日について行う必要がある。

### 19.2 対策

| 対策 | 内容 |
| --- | --- |
| 日種別の一括解決 | 期間内の `holiday`、`calendar_day_override`、`day_type_default` を一度に読み込み、メモリ上で辞書化する |
| 実績の一括集計 | 教材ごと周回ごとの累積完了量と実効速度を、単一の集計クエリで全教材分を取得する |
| 完了予測の反復上限 | 反復回数に上限を設ける（締切+365日）。超過時は「大幅超過」として打ち切る |
| リクエスト内キャッシュ | 同一リクエスト内で同じ日の日種別を再解決しない |
| AI呼び出しの分離 | 今日の一言をダッシュボードのエンドポイントに含めず、別途取得する |

### 19.3 キャッシュを行わない箇所

日次ノルマの算出結果はキャッシュしない。日付をまたいだ際の不整合や、実績登録後の再算出漏れを防ぐためである。算出コストは上記の対策により十分に低い。

## 21. 読書目標の扱い

### 21.1 適用範囲

本文書の第3〜14章は、`goal.category = EXAM`（資格試験）の目標を対象とした算出ロジックである。`category = READING`（読書）の目標には適用しない（要件定義書R-71、仕様書6.10）。読書目標が用いる算出ロジックは本章にまとめる。

第3章（1日の境界時刻の解決）は日次記録全体に関わる共通基盤であり、読書目標にもそのまま適用する。「今日」の判定は `GET /records/today` に一元化されており、読書に限って例外を設けない。

第15章（週次要約の生成）の対象判定（15.2手順3「その週にstudy_logが1件以上存在する目標を対象に生成」）は、読書目標にはstudy_logが存在しないため、ロジックの変更なしに自動的に読書目標を対象外とする。

**資格試験用AI機能との切り分け**：日次報告フィードバック（17.2 DAILY_FEEDBACK）・今日の一言（17.4 DAILY_MESSAGE）が対象とする「進行中の目標」は、`ai_context_service.list_active_exam_goals`によりEXAMのみへ限定する（Phase15で対応）。限定しない場合、`{{goal_summary}}`に読書目標が「試験科目未登録」という誤った文脈で混入するためであり、読書用のDAILY_FEEDBACK_READING（17.6）が別途存在する以上、DAILY_FEEDBACK・DAILY_MESSAGEは恒常的にEXAM専用として扱う（読書用の「今日の一言」相当機能は設けない設計、要件定義書6.10）。**この「DAILY_MESSAGEはEXAM専用」という方針は、2026-09-03の仕事目標追加により見直された。仕事目標はDAILY_MESSAGEの対象に含める（要件定義書R-77）。詳細は22.1参照。**

`POST /goals/{id}/retrospective`（`retrospective_service.generate_retrospective`）はPhase16で `goal.category` に応じてGOAL_RETROSPECTIVE（17.5）／GOAL_RETROSPECTIVE_READING（17.7）へ分岐する実装とした。Phase15時点で暫定的に設けていた「READING目標への呼び出しをVALIDATION_ERRORで拒否するガード」はこの分岐に置き換えて解消済みである（書籍が未登録のREADING目標に対する呼び出しのみ、引き続きVALIDATION_ERRORとする）。

**対話履歴の分離（chat_message.purpose、Phase16）**：資格試験（DAILY_FEEDBACK）と読書（DAILY_FEEDBACK_READING）の対話は、同一日の同一`daily_record`に混在しうる。会話自体はAiPurpose／ConversationScopeが異なるため`ai_conversation`側では自然に分離されるが、`chat_message`はdaily_record単位のフラットな一覧であるため、`purpose`列（データ構造編5.4）を追加し、対話履歴（`{{conversation_history}}`）への注入時にpurposeで絞り込むことで、用途間の文脈混入を防いでいる。AI対話の実行エンドポイントも`POST /records/{date}/chat`（資格試験）と`POST /records/{date}/reading-chat`（読書）に分離した（データ構造編6.2「AI対話エンドポイントの分離について」）。

### 21.2 読書進捗（BookRead）の算出

教材の派生値（総作業量・現在周回・残量・進捗率）が独立エンドポイントではなく`MaterialRead`に
埋め込まれているのと同じ方針で、書籍の派生値も独立エンドポイントを設けず`BookRead`
（`GET /goals/{id}`、`PATCH /books/{id}`等の応答）に埋め込む（データ構造編6.2、Phase15実装）。

```

last_reading_date = MAX(daily_record.record_date)
                     （対象bookのreading_logが存在する daily_record のうち）

current_streak = 21.3で定義する

page_progress（book.total_pages が設定されている場合のみ）：
    current_page = 直近の reading_log.current_page（NULLでない最新値）
    progress_rate = current_page / total_pages
```

日次ノルマ・実効速度・完了予測日・締切との乖離（第7〜10章）は算出しない。

### 21.3 連続記録日数（読書版）

## 22. 仕事目標の扱い

### 22.1 適用範囲

本文書の第3〜14章は、`goal.category = EXAM`（資格試験）の目標を対象とした算出ロジックである。`category = WORK`（仕事）の目標には適用しない（要件定義書R-74、仕様書6.11）。仕事目標が用いる算出ロジックは本章にまとめる。

第3章（1日の境界時刻の解決）は日次記録全体に関わる共通基盤であり、仕事目標にもそのまま適用する。

第15章（週次要約の生成）の対象判定（15.2手順3）は、仕事目標にはstudy_logが存在しないため、ロジックの変更なしに自動的に仕事目標を対象外とする（読書目標と同じ理由、21.1参照）。

**資格試験用AI機能との切り分け（DAILY_FEEDBACK）**：日次報告フィードバック（17.2 DAILY_FEEDBACK）が対象とする「進行中の目標」は、読書と同じく`ai_context_service.list_active_exam_goals`によりEXAMのみへ限定する。仕事目標には別途DAILY_FEEDBACK_WORK（17.8）が存在するため、DAILY_FEEDBACKは引き続きEXAM専用として扱う（読書と同じ理由、21.1参照）。

**今日の一言（DAILY_MESSAGE）への対応 ※読書との重要な相違点**：読書目標は「今日の一言」の対象外である（21.1、要件定義書1.1（改2）時点の設計判断。build_goal_summaryがEXAM前提のコンテキストを組み立てるため、READINGを混ぜると「試験科目未登録」という誤った文脈が生成されてしまうことが理由）。仕事目標はこれと異なり、要件定義書R-77により**今日の一言の対象に含める**。理由は利用者からの明示的な要求（「日々の業務内容や努力を誉めるような機能が欲しい」）であり、日次のAIフィードバック（DAILY_FEEDBACK_WORK、17.8）とは別に、起動時の短い労いの一言を仕事目標にも提示する需要があるためである。これにより「今日の一言の対象＝EXAM及びWORK、READINGのみ除外」という設計に変わる。

対応として、`ai_context_service.list_active_exam_goals`（EXAMのみを返す）とは別に、DAILY_MESSAGEが対象とする「進行中の目標」を求める関数（例：`list_daily_message_target_goals`。EXAM及びWORKを返し、READINGのみ除外する）を新設する。DAILY_MESSAGEのAiPurpose・prompt_template（17.4）は1つのまま維持し、テンプレート本文・変数自体は変更しない。かわりに`{{goal_summary}}`・`{{progress_summary}}`・`{{recent_activity}}`を組み立てる変数ビルダーの内部を`goal.category`により分岐させる。EXAM用のビルダー（科目構成・教材別進捗率が前提）はWORK目標にはそのまま使えないため、WORK用の変数ビルダーを別途新設する必要がある。WORK用の`{{goal_summary}}`・`{{progress_summary}}`は、22.2で算出する経過日数・直近記録日・連続記録日数・直近の月次報告有無を用いて組み立てる（日次ノルマ・進捗率に相当する定量指標を仕事目標は持たないため）。

`POST /goals/{id}/retrospective`（`retrospective_service.generate_retrospective`）はWORK目標に対してVALIDATION_ERRORで拒否する。読書がPhase15時点で経由した「暫定的な拒否ガード」（Phase16のGOAL_RETROSPECTIVE_READING実装により解消済み）とは異なり、仕事目標では月次報告・半期評価という別エンドポイント（`POST /goals/{id}/monthly-report`・`POST /goals/{id}/semiannual-review`、データ構造編6.2）を新設するため、この拒否は暫定ではなく恒久的な仕様である（`/retrospective`はクローズ時1回のレポートを前提とした設計であり、周期的に生成し続けるWORKの月次・半期報告とは呼び出しの意味が異なるため統合しない）。

**対話履歴の分離（chat_message.purpose）**：資格試験（DAILY_FEEDBACK）と仕事（DAILY_FEEDBACK_WORK）の対話は、同一日の同一`daily_record`に混在しうる。読書と同じ仕組み（`purpose`列、データ構造編5.4）により、対話履歴（`{{conversation_history}}`）への注入時にpurposeで絞り込み、用途間の文脈混入を防ぐ。AI対話の実行エンドポイントも`POST /records/{date}/work-chat`（DAILY_FEEDBACK_WORK）として、`/chat`・`/reading-chat`と分離する（データ構造編6.2）。

### 22.2 仕事進捗（WorkAssignmentRead）の算出

書籍の派生値（21.2）と同じ方針で、案件情報の派生値も独立エンドポイントを設けず`WorkAssignmentRead`（`GET /goals/{id}`等の応答）に埋め込む（都度算出、保存しない）。

```

last_work_date = MAX(daily_record.record_date)
                  （対象work_assignmentのwork_logが存在する daily_record のうち）

current_streak = 22.3で定義する

has_recent_monthly_report = 直近の月（前月または当月）を対象期間とする
    goal_retrospective（period_type=MONTHLY）が生成済みか
```

日次ノルマ・実効速度・完了予測日・締切との乖離（第7〜10章）は算出しない。書籍と異なり`work_assignment`は読了目標日に相当する`due_date`を持たないため（データ構造編5.3「work_assignment（案件情報）」参照）、残日数（remaining_days）に相当する指標も算出しない。

### 22.3 連続記録日数（仕事版）

```
T から遡り、対象work_assignmentのwork_logが存在する日が連続する日数。
```

21.3（連続記録日数・読書版）と同じ理由により、バッファ日・除外日による中断除外を行わない。仕事目標は日種別（第4章）による計画運用の対象外であり、資格試験の計画運用と独立させるためである（要件定義書R-74）。

### 22.4 業務記録の時系列注入

日次報告フィードバック（17.8の`{{recent_work_logs}}`）、月次報告（17.9の`{{month_logs}}`）、半期評価（17.10の`{{period_logs}}`）に注入する業務記録は、対象work_assignmentに属する `work_log` を `record_date` の昇順で連結する。週次要約による圧縮（第15章）を経由しない（仕事目標は週次要約を持たないため、読書と同じ理由。21.4参照）。

三者で注入範囲が異なる。

| 用途 | 注入範囲 |
| --- | --- |
| `{{recent_work_logs}}`（17.8） | 直近 `ai.work_recent_log_days`（既定14）日分のみ。日次対話は直近の文脈があれば十分であり、案件の全期間を毎回注入する必要はない |
| `{{month_logs}}`（17.9） | 対象月（period_key）の1日から末日までの全work_log |

プロンプトの段階的縮退（16.5）は資格試験と同じ仕組みをそのまま適用し、`{{period_logs}}`が閾値を超える場合の安全弁とする。

### 22.5 期間判定（月次・半期）

**月次報告の対象期間**

`period_key`は暦月（`"YYYY-MM"`）とする。**`period`クエリパラメータ省略時は前月を既定値とする**（2026-09-04改訂。「提出対象年月」は常に提出月の前月であり、当月はまだ終わっていないため対象としない。要件定義書R-78「提出対象年月」の定義）。前月の`period_key`は単純な月繰り下げとする（1月の前月は前年12月、`"YYYY-01"`の前月は`"(YYYY-1)-12"`）。

**半期の区分**

会社の人事評価サイクル（3月に目標設定・8月に評価、9月に目標設定・翌2月に評価）に合わせ、以下のとおり区切る。一般的な暦半期（1〜6月／7〜12月）とも、会計年度の上期・下期（4〜9月／10〜3月）とも異なる点に注意する（要件定義書R-79）。

```
H1 = 3月1日 〜 8月31日
H2 = 9月1日 〜 翌年2月末日（閏年は2月29日、平年は2月28日）
```

対象日 T から `period_key` を算出する規則は以下のとおり。

```
Tの月が3〜8月のとき   → f"{T.year}-H1"
Tの月が9〜12月のとき  → f"{T.year}-H2"
Tの月が1〜2月のとき   → f"{T.year - 1}-H2"
```

前半期の`period_key`（当該半期の直前の半期）は以下のとおり。

```
対象が "Y-H1" のとき → f"{Y - 1}-H2"
対象が "Y-H2" のとき → f"{Y}-H1"
```

`period`クエリパラメータ省略時は、Tが属する半期を既定値とする。進行中の半期についても、月次報告と同様にドラフトの生成・再生成を許容する（要件定義書R-79「再生成を許容する」）。

### 22.6 月次報告・半期評価の出力フォーマットの組み立てと解析

要件定義書R-82（生成結果を人が確認・修正できること）を実現するため、`goal_retrospective.body`はAIが自由書式で書く1つの文章ではなく、**アプリケーション層が構造化列から一定のテンプレートで機械的に組み立てる**（データ構造編5.4参照）。

**生成時の処理手順**

```
手順1：対象期間（period_key）の直前期間（前月／前半期）の行を取得する
       存在すれば next_goal_text を今回の target_goal_text として複製する
       存在しなければ target_goal_text に固定文言
       「（前月／前半期の記録が無いため、今回は目標との比較を行いません）」を設定する

手順2：17.9／17.10の変数を組み立て、AIへ送信する

手順3：AI応答を見出し文字列（17.9は5節、17.10は4節）で分割する
       各節の内容を対応する列（business_summary、achievement_score、
       achievement_reflection、next_goal_text、report_notes）に格納する
       「達成度」節が半角数字1〜5のいずれでもない場合
       （「対象外」を含む）、achievement_score列はNULLのままとする

手順4：見出しが1つでも検出できなかった場合、当該項目は空文字のまま
       レコードを保存する（生成自体は失敗させない。AI応答全文は
       既存のai_logに記録済みのため、内容自体は失われない）

手順5：target_goal_text・business_summary・achievement_score・
       achievement_reflection・next_goal_text・report_notesを
       下記テンプレートで結合し、bodyへ格納する

手順6：goal_id・period_type・period_keyの一意な行として保存する
       （既存の行があれば上書き。データ構造編5.4「WORKでの流用」）
```

**bodyの組み立てテンプレート（月次報告）**

```
# 月次報告（{{target_month}}）

## 業務内容（案件内容）
{{business_summary}}

## 当月の目標
{{target_goal_text}}

## 目標がどの程度達成されたか
{{achievement_score}}

## 目標の達成状況と進捗に関する振り返り
{{achievement_reflection}}

## 来月の目標
{{next_goal_text}}

## 報告・連絡事項
{{report_notes}}
```

半期評価は見出し・変数名を「対象半期」「当該半期の目標」「次半期の目標」に読み替え、「報告・連絡事項」の節を持たない（要件定義書R-79）。

**利用者による編集（PATCH、要件定義書R-82・R-83）**：レビュー画面での編集は、`target_goal_text`・`achievement_score`・`business_summary`・`achievement_reflection`・`next_goal_text`・`report_notes`の各列を個別に更新可能とし、保存のたびに手順5のテンプレート結合を再実行して`body`を更新する（`body`を直接自由編集させることはしない。列と本文の不整合を防ぐため）。前期の記録が無い場合の手動シード（R-83）は、`target_goal_text`列のみを利用者が直接入力し、他の列は空のまま行を作成する。
