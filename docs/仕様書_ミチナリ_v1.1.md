## 1. 本文書の目的

本文書は、ミチナリが提供する機能の全体像、画面構成、および各機能の入出力を定義する。

要件定義書に記載した要求（R-01〜R-60）に対する実現手段を機能単位で示す。データ構造および算出ロジックの詳細は設計書に記載し、本文書では扱わない。

## 2. システム概要

### 2.1 システム構成（第1フェーズ）

| 層 | 構成 |
| --- | --- |
| クライアント | ブラウザ上で動作するシングルページアプリケーション |
| サーバ | ローカルホストで動作するAPIサーバ |
| データストア | ローカルファイルベースのリレーショナルデータベース |
| AI連携 | APIサーバと同一プロセス内でAI基盤の開発キットを呼び出す |

利用者はローカルホストのURLにブラウザからアクセスする。外部への通信はAI基盤への呼び出しのみとする。

**ポートに関する制約**

AI基盤の開発キットは、認証フローのフォールバック経路（PAT未設定時のブラウザ認証）でローカルの8400番ポートを使用する設定を既定に持つ。主経路のPAT認証ではこのポートは使用されないが、フォールバック経路を確実に動作させるため、アプリケーションサーバは引き続き8400番以外で起動する。既定値は8100とする。

### 2.2 利用形態

単一利用者による使用を前提とする。認証機構は設けない。

## 6. 画面仕様

### 6.1 SC-01 ダッシュボード

**表示要素**

| 領域 | 内容 |
| --- | --- |
| 今日の一言 | AIが生成した肯定的な短文。生成日が当日でない場合のみ再生成 |
| 警告バナー | 警告または強制リプラン条件を満たす目標がある場合に表示 |
| 本日のノルマ | 進行中の全教材について、目標分量・目標時間・使用予定スロット・現在周回を一覧 |
| 目標カード | 進行中の各目標について、全体進捗率、残日数、完了予測日との乖離を表示 |
| 統計サマリ | 連続報告日数、直近30日の報告率、バッファ消費率、実効速度 |
| 本日の状態 | 未入力・進捗のみ登録済・報告済のいずれかを表示 |

**操作**

- 本日の報告ボタン。本日の状態に応じて遷移先を切り替える
- 各カードから対応する詳細画面への遷移

**特記事項**

日種別がバッファ日の場合、本日のノルマ領域には「本日はバッファ日です」と表示し、目標分量を0として扱う。ただし実績登録は可能である旨を併記する。

「本日」の判定には、設定された1日の境界時刻を用いる。境界時刻が午前4時であれば、午前3時のアクセスは前日として扱う。

| 項目 | 内容 |
| --- | --- |

**検証**

## 8. AI連携仕様

本章は、AI基盤の開発キットが提供する実仕様に基づく。開発キットの仕様は変更できないため、制約を前提としたアプリケーション側の設計を定義する。

### 8.1 連携箇所

| 連携ID | 用途 | 実行契機 |
| --- | --- | --- |
| AI-01 | 日次報告フィードバック | 日次報告画面での送信操作 |
| AI-02 | 週次要約生成 | 日曜以降の初回起動時、前週分が未生成の場合 |
| AI-03 | 今日の一言生成 | 起動時、当日分が未生成の場合 |
| AI-04 | 総括レポート生成 | 目標のクローズ時、および再生成操作時 |
| AI-05 | 成長記述の比較 | AI-01 に包含 |

### 8.2 会話の管理方針

**制約**

開発キットでは、メッセージ送信前に会話を作成し、その識別子を指定する必要がある。会話はAI基盤側に永続化される。

**方針：用途と日付ごとに会話を分離する**

| 用途 | 会話の単位 | 会話のタイトル |
| --- | --- | --- |
| 日次報告 | 1日1会話 | `{日付} 日次報告` |
| 週次要約 | 1週1会話 | `{週開始日}週 週次要約` |
| 今日の一言 | 1日1会話 | `{日付} 今日の一言` |
| 総括レポート | 目標ごと1会話 | `総括レポート` |

**方針の理由**

会話を用途ごとに分離することで、異なる目的のプロンプトが文脈として混入することを防ぐ。日次報告のフィードバックが、朝に生成した「今日の一言」の文脈に引きずられる事態を構造的に排除する。

日をまたぐ文脈は、会話の継続によってではなく、週次要約をプロンプトに注入することで実現する。この方式であれば、注入する情報量をアプリケーション側で完全に制御できる。

**フォルダによる整理**

目標ごとにフォルダを作成し、その配下に会話を配置する。フォルダ名は「`{接頭辞}_{目標名}`」とする。接頭辞は設定から変更可能とする。

**会話識別子の保持**

作成した会話の識別子はローカルに保持する。一覧取得APIを毎回呼び出さない。

### 8.3 メッセージ送信の指定

| パラメータ | 指定値 | 理由 |
| --- | --- | --- |
| Web検索 | 無効 | 既定値が有効のため明示指定が必須。試験対策の文脈に無関係な検索結果が混入することを防ぐ |
| ナレッジ検索 | 無効 | 本アプリはアシスタントのナレッジを使用しない |
| 親メッセージ順序 | 送信するが文脈維持には用いない（8.3.1参照） | 同一日内の複数往復における文脈維持は対話履歴の注入（8.4）で実現する |
| 画像・文書・音声 | 使用しない | MVPの範囲外 |

#### 8.3.1 親メッセージ順序に関する既知の制約（要検証）

導入したAI基盤の開発キット（NewtonX ADK v0.10.5）を実際にソースコードで確認したところ、`send_message()`のメソッドシグネチャに親メッセージ順序を指定する引数が存在せず、送信内容には常に固定値0が設定されることを確認した。バンドルされた公式ドキュメント（APIリファレンス、利用ガイド、トラブルシューティング）はすべてこのパラメータが機能する前提で書かれており、ドキュメントと実装が矛盾している。

**この制約を前提に、本アプリは以下の方針を取る。**

- AI基盤側の会話スレッド機能（親メッセージ順序による文脈継承）には依存しない
- 同一日内の複数往復における文脈維持は、本アプリが独自に保持する対話履歴（`chat_message`）を毎回のプロンプトへ全文注入する方式（8.4「対話履歴」）で実現する。この方式はAI基盤側の実装状況によらず機能する
- `ai_conversation.last_parent_order` の値は将来の開発キット改修に備えて記録は継続するが、現状は文脈維持の実効性を持たない
- 回答が出力上限で途切れた場合の継続取得（開発キット側が推奨する「終端マーカー方式」）も親メッセージ順序に依存するため、本アプリでは代わりに直前の応答本文をプロンプトに含めて「続きを出力してください」と自己完結した指示で送信する方式を取る

この制約は導入したADKのバージョン（v0.10.5）に起因するものであり、将来のバージョンアップで解消される可能性がある。解消された場合は、親メッセージ順序による文脈継承を主とし、対話履歴の全文注入を縮退時のみに用いる構成へ最適化してよい。

**アシスタントへのナレッジ登録は行わない。** アシスタントが組織内で共有される可能性があり、個人の学習記録を登録することは不適切である。

### 8.4 日次報告フィードバック（AI-01）の入力構成

システムが保持する定型プロンプトに対し、以下の情報を差し込む。

| 区分 | 差し込む情報 |
| --- | --- |
| 目標情報 | 試験名、科目構成、各科目の受験日、残日数 |
| 教材情報 | 教材ごとの総量、予定周回、現在周回、完了量、残量、締切、必要連続時間、必要環境 |
| 計画状態 | 日次ノルマ、必要速度、実効速度（周回別）、完了予測日、締切との乖離 |
| 負荷状態 | 当日の日種別、負荷係数、バッファ消費率 |
| 当日実績 | 教材別の投下時間、完了分量、周回、品質指標 |
| 当日記述 | 本日の行動・所感、本日学んだこと |
| 過去傾向 | 直近の週次要約 |
| 対話履歴 | 本日の対話における過去の往復 |

全期間の日記原文は入力に含めない。

### 8.5 プロンプトの段階的縮退

**制約**

AI基盤の入力上限は明示されていない。

**方針**

プロンプトを組み立てた後、文字数が設定値を超える場合、以下の順序で情報を削減する。

| 順位 | 削減対象 | 理由 |
| --- | --- | --- |
| 1 | 古い週次要約から順に除外 | 直近ほど関連性が高い |
| 2 | 教材情報の詳細度を下げる | 締切が遠い教材を集約表示にする |
| 3 | 当日の対話履歴を古い往復から除外 | 直近の往復が最も重要 |
| 4 | 日記本文を末尾優先で切り詰める | 完全な除外は避ける |

縮退が発生した場合、その旨を画面上に控えめに表示する。利用者が「なぜ言及されない情報があるのか」を把握できるようにするためである。

### 8.6 応答に対する要求

定型プロンプトは、以下を満たす応答を得るように構成する。

| 要求 | 内容 |
| --- | --- |
| 状況の解釈 | 数値実績と自然言語記述を統合し、進捗の背景要因を推定する |
| 成長の指摘 | 過去の記述との比較により、説明の解像度や構造化の変化を指摘する |
| 行動の提案 | 翌日以降の具体的な行動を提案する |
| 双方向の調整 | 負荷を増やす提案と減らす提案の双方を選択肢として持つ |

**負荷を減らす提案の段階**

| 段階 | 提案内容 |
| --- | --- |
| 軽 | 特定期間の負荷係数の引き下げ |
| 中 | 教材の優先順位変更、学習範囲の絞り込み、予定周回数の削減 |
| 重 | 受験日の後ろ倒し、目標の一時停止 |
| 即時 | 当日の休息 |

### 8.7 認証

**認証方式はPersonal Access Token（PAT）を主とする。** 導入した開発キット（NewtonX ADK）の現行の公式利用ガイドは、Host（サブドメイン）とPATによる認証を標準的な方法として案内しており、ブラウザ経由のOAuth／デバイスコード認証はEntraID構成時のフォールバック経路として内部に残るのみである。当初の設計はブラウザ認証を主経路と想定していたが、公式情報にあわせて以下のとおり改める。

| 項目 | 方針 |
| --- | --- |
| 認証情報の管理 | 開発キットの仕組みに委ねる。独自の資格情報管理を実装しない。Host（例: `xxx.newton-x.net`）とPATは、設定画面（SC-11）から開発キットの設定へ反映する |
| PATの発行 | NewtonXのWeb版アカウント画面で利用者自身が発行する（本アプリからは発行できない）。設定画面に発行手順への案内を表示する |
| 起動時 | Host・PATが設定済みかを確認する。開発キットはPAT設定時、他の認証手段より優先してこれを使用する |
| 未設定・無効時 | 設定画面でHostとPATの入力を促す。フォールバックとしてブラウザ経由の認証フロー（バックグラウンドスレッドで実行）を提供するが、主経路としては使用しない |
| 認証状態の公開 | クライアントには真偽値のみを返す。PAT・トークンは送出しない |
| リダイレクト先（フォールバック時のみ） | 開発キットの既定値（ローカル8400番）を使用する。アプリケーションサーバは別ポート（8100）で起動する |

### 8.8 エラー処理

| エラー種別 | 応答コード | 画面での扱い |
| --- | --- | --- |
| 未認証・トークン期限切れ | AI_AUTH_REQUIRED | 設定画面での再認証を促すメッセージを表示 |
| タイムアウト | AI_TIMEOUT | 再送ボタンを表示。実績入力の内容は保持する |
| 通信エラー・頻度制限 | AI_ERROR | エラー内容を表示。再送ボタンを表示 |
| 会話操作の失敗 | AI_ERROR | 同上 |
| 設定不備 | AI_CONFIG_ERROR | 設定画面への遷移を促す |

**実装上の注意（タイムアウトの判定方法）**

導入した開発キットの例外クラスは `NewtonXError` / `AuthenticationError` / `APIError` / `ConfigurationError` / `FileUploadError` / `ChatError` の6種であり、タイムアウト専用の例外クラスは存在しない。通信タイムアウトも内部的に `APIError` へ一律ラップされるため、型による判定はできない。本アプリでは、呼び出し側で計測した経過時間が設定値（`ai.timeout_seconds`）を超えているか、またはエラーメッセージにタイムアウトを示す文字列が含まれるかによって `AI_TIMEOUT` を判定する。

**重要な制約**

AI呼び出しの失敗により、実績入力の内容が失われてはならない。日次報告画面では、実績と日記の入力内容をクライアント側の状態として保持し、AI応答の成否とは独立させる。

AI応答が得られない状態でも、報告の確定を許容する。AIとの対話は本アプリの中核だが、それが利用できないことを理由に記録自体が失われるのは本末転倒である。

### 8.9 呼び出し頻度の制御

頻度制限が存在する可能性があるため、連続する呼び出しの間隔に下限を設ける。既定値は2秒とする。

週次要約の遡及生成では複数回の呼び出しが連続するため、この制御が特に重要となる。

### 8.9.1 用途別アシスタントの選定（実機確認済み）

連携箇所（8.1）ごとに既定のアシスタントを設定する。全用途を単一アシスタントに固定せず、`get_assistants()`が返す各アシスタントの説明文に基づき、タスク特性に合ったものを既定値とする。

| 連携ID | 用途 | 既定アシスタント | 選定理由 |
| --- | --- | --- | --- |
| AI-01 | 日次報告フィードバック | GPT-5.4（高性能） | 複雑なタスクの整理や具体的な提案に適しており、状況解釈・成長の指摘・行動提案という要求（8.6）に合致する |
| AI-02 | 週次要約生成 | Gemini 2.5 Flash（高速） | 要約に適した特性を持ち、起動時の複数週遡及生成（速度が重要）に適する |
| AI-03 | 今日の一言生成 | GPT-5.4-mini（高速） | 速度と情報整理のバランスに優れ、ダッシュボードでの非同期表示に適する |
| AI-04 | 総括レポート生成 | GPT-5.4（高性能） | AI-01と同様、低頻度・高品質重視のタスクのため同一アシスタントとする |

各アシスタントの識別子は `app_setting`（`ai.assistant_uid.*`、設計書 データ構造編 5.2）に既定値として保持し、設定画面（SC-11）から用途ごとに変更できる。

**既知の非対応アシスタント**：導入済み環境で以下2件は`send_message`が常に失敗することを実機確認済みである。設定画面の選択肢から除外するか、選択・保存時に疎通確認を行うことが望ましい。

| アシスタント名 | 状態 |
| --- | --- |
| GPT-4o mini（高速） | 使用不可（404で確認済み） |
| GPT-4o（高性能） | 使用不可（404で確認済み） |

この一覧は将来変動しうるため、ハードコードした除外リストのみに頼らず、送信失敗時のエラーハンドリング（8.8のAI_ERROR、再送・再選択の導線）で汎用的に吸収できる設計とする。

### 8.10 稼働状況の確認

起動時にAI基盤の利用可否を確認し、設定画面に表示する。利用不可の場合、AI連携機能を無効化し、実績記録のみが可能な状態とする。

## 10. バリデーション方針

| 対象 | 方針 |
| --- | --- |
| 必須項目 | 入力欄単位で即時検証し、未入力を明示する |
| 数値範囲 | 品質指標は0〜100、負荷係数は正の数、総量および完了量は0以上、予定周回数は1以上の整数 |
| 日付整合 | 教材の開始日が締切より後の場合、保存を拒否する |
| 日付整合 | 受験日の期間開始日が期間終了日より後の場合、保存を拒否する |

| リソース | 配分合計の100%超過を保存時に拒否する |
| 遡及入力 | 前日を超える過去日への入力を拒否する |
| 変更不可 | 報告済の日およびクローズ済の目標への更新要求を拒否する |
| 時刻 | 1日の境界時刻は0時から11時の範囲とする |
