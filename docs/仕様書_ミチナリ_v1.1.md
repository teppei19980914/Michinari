要件定義書に記載した要求（R-01〜R-60）に対する実現手段を機能単位で示す。データ構造および算出ロジックの詳細は設計書に記載し、本文書では扱わない。

## 2. システム概要

### 2.1 システム構成（第1フェーズ）

| 層 | 構成 |
| --- | --- |
| クライアント | ブラウザ上で動作するシングルページアプリケーション |
| サーバ | ローカルホストで動作するAPIサーバ |
| データストア | ローカルファイルベースのリレーショナルデータベース |
| AI連携 | APIサーバと同一プロセス内でAI基盤の開発キットを呼び出す |

利用者はローカルホストのURLにブラウザからアクセスする。外部への通信はAI基盤への呼び出しのみとする。

**ポートに関する制約**

AI基盤の開発キットは、認証フローのフォールバック経路（PAT未設定時のブラウザ認証）でローカルの8400番ポートを使用する設定を既定に持つ。主経路のPAT認証ではこのポートは使用されないが、フォールバック経路を確実に動作させるため、アプリケーションサーバは引き続き8400番以外で起動する。既定値は8100とする。

### 2.2 利用形態

単一利用者による使用を前提とする。認証機構は設けない。

| 統計サマリ | 連続報告日数、直近30日の報告率、バッファ消費率（資格試験目標のみ）、実効速度 |
| 先週のまとめ | 直前の月曜始まりの週について、AI週次要約（生成済みならその本文）または非AI集計（記録日数、資格試験のみ投下時間）を表示（S-4 4-4） |
| 直近4週間カレンダー | 月次カレンダー（SC-05）と同じ日種別背景色・記録状態マーカーで直近4週間（日曜始まり28日間）を一覧表示する読み取り専用の縮小ウィジェット（S-4 4-5） |
| 本日の状態 | 未入力・進捗のみ登録済・報告済のいずれかを表示 |

**操作**

- 本日の報告ボタン。本日の状態によらず常に日次報告（SC-06）へ遷移する。当日中に着手している全カテゴリが確定済みの場合のみ、日次報告画面が日次報告閲覧（SC-08）へ自動転送する（1.1（改20））。本日の状態（記録状態）は未着手カテゴリを除外した集約値（7.2）であり、1カテゴリだけ確定した日も「報告済」となるため、遷移先の判定には用いない
- 各カードから対応する詳細画面への遷移
- 着手中（ACTIVE）の目標が2件以上ある場合、画面上部の目標タブ（日次報告6.5と同じGoalTabBar）で対象目標を1件選択して切り替える（1.1改14）。今日の一言・警告バナー・本日のノルマ・目標カード・統計サマリ・先週のまとめは選択中の目標分のみを表示する。着手中の目標が0〜1件の場合は目標タブを表示せず、従来どおりその目標（または該当なし）の内容をそのまま表示する

**特記事項**

日種別がバッファ日の場合、本日のノルマ領域には「本日はバッファ日です」と表示し、目標分量を0として扱う。ただし実績登録は可能である旨を併記する。

本日の状態（未入力・進捗のみ登録済・報告済）・本日の日種別は、目標に紐づかないアプリ全体の値であるため、目標タブの切り替えの影響を受けない。

統計サマリのうちバッファ消費率は、選択中の目標が資格試験目標（category=EXAM）の場合にのみ表示する（1.1改19）。読書・仕事目標は日種別による計画運用の対象外であり（R-71・R-74）、バッファ（予備日）という概念自体を持たないためである。実効速度も同じ理由で教材を持つ資格試験目標にのみ表示される。

「本日」の判定には、設定された1日の境界時刻を用いる。境界時刻が午前4時であれば、午前3時のアクセスは前日として扱う。

**初回記録バナー（S-4 4-2、2026-09-20）**：着手中の目標が1件以上あり、かつ記録が一度も確定（報告済）されていない間、「最初の記録を書いてみましょう」のバナーを表示する。判定は`GET /dashboard`が返す`has_ever_reported_record`（カテゴリを問わず1件でも確定済み記録があればtrue）を用いる。画面遷移時のみの一時的な状態ではなく実データで判定するため、リロードやブラウザバックをまたいでも、いずれかのカテゴリで最初の記録を確定するまで表示され続ける。

**先週のまとめ（S-4 4-4、2026-09-20）**：目標タブで選択中の目標について、直前の月曜始まりの週（今日が属する週の1つ前の週。今日が日曜でも今週は含まない）の振り返りを表示する。AI週次要約（`weekly_summary`、`is_anonymized=false`の版）が既に生成済みならその本文をそのまま表示し、無ければ（AI未設定、または起動時の遡及生成がまだ実行されていない）非AI集計（その週にログが記録された日数。資格試験目標のみ投下時間の合計も表示、読書・仕事目標は時間を定量管理しないため件数のみ）へフォールバックする。AI呼び出しは行わない（DBの既存データを読むだけ）ため、初期表示2秒以内の性能要件に影響しない。記録が0件の週は「先週の記録はありませんでした」と表示する。

**直近4週間カレンダー（S-4 4-5、2026-09-20）**：目標に紐づかないアプリ全体の値のため、目標タブの切り替えの影響を受けない（本日の状態・本日の日種別と同じ扱い）。範囲は「今週を含む直近4週間（日曜始まり28日間、月次カレンダーSC-05と同じ週区切り）」。月次カレンダーと同じ日種別背景色・記録状態マーカーで一覧表示するが、日種別の手動編集・日付クリックでの画面遷移は持たない読み取り専用表示とし、「カレンダーを見る」リンクからSC-05（月次カレンダー）へ遷移して詳しい操作を行う。受験日等の補助表示（目標ごとの詳細情報を要する）は対象外とする。

**1.1改14での変更点**：従来は「進行中の全目標を1画面で俯瞰する画面」として、本日のノルマ・目標カード・統計サマリ・今日の一言のいずれも複数目標分を1画面にグルーピング表示していた（1.1改8で日次報告のみ目標タブ化した際、ダッシュボードは対象外と明記していた）。目標ごとに機能を分離する設計（6.5・6.4参照）をダッシュボードにも統一するため、この判断を撤回し、上記の目標タブ方式に変更した。

**今日の一言の対象目標について**：読書目標（category=READING）は今日の一言の対象外とする（6.10参照）。仕事目標（category=WORK）は読書と異なり対象に含める（R-77、DSH-07・GOL-19で算出する経過日数・直近記録日・連続記録日数・直近の月次報告有無を用いて生成する）。したがって今日の一言の対象は「資格試験目標および仕事目標、読書目標のみ除外」となる。

読書目標・仕事目標の残日数・直近記録日・連続記録日数（・書籍のページ進捗）は目標カードに、資格試験目標の全体進捗率・完了予測日との乖離とは異なる表示要素として含める（DSH-06・DSH-07）。

  - 仕事：「案件を1件登録して、日々の業務を書き留める」

### 6.1.2 SC-17 資格モード作成ウィザード（1.1改29）

SC-16またはSC-02（目標一覧）から「資格」を選んだ場合に進む、5ステップのウィザード形式の作成経路。SC-03（目標詳細・編集）を置き換えるものではなく、作成経路を1つ追加するものである。

**ステップ構成**

1. **試験を選ぶ**：主要な試験のテンプレート（`backend/app/templates/exams/`配下のJSON。ITパスポート・基本情報・応用情報・情報処理安全確保支援士・ネットワークスペシャリスト・データベーススペシャリストの6件）から選択、または「その他」で試験名を手入力する。テンプレートの科目構成・教材例は令和8年度の試験制度改定に伴う暫定値であり、正式な配点は利用者自身がIPA公式の試験要綱で確認する前提とする
2. **科目と受験日を入れる**：テンプレート選択時は科目（科目名・合格基準点）が入った状態で、科目ごとに受験日（期間指定または確定日）を入力する。「その他」選択時は本ステップで科目自体を追加する
3. **教材を確認する**：テンプレートの教材例（教材名・単位・目安の総量）が入った状態で、追加・削除・編集ができる。「目安です。お使いの教材に合わせて変更してください」を常に表示する
4. **学習時間を設定する**：時間スロットが1件も登録されていない場合は、曜日ごとの簡易入力（「平日は何時間」「休日は何時間」）を行い、開始・終了時刻の仮値（平日20:00〜、休日09:00〜。24:00をまたぐ入力は23:59に切り詰める）でスロットを自動生成し、そのまま全時間を本目標へ配分する。「時刻は目安です」を表示する。既にスロットが登録されている場合は、簡易入力の代わりに既存スロットへの配分入力（SC-03のリソース配分タブ相当）を表示する。配分の合計が0分の間は次のステップへ進めない
5. **確認して開始する**：試験名・科目・受験日・教材の内容を確認し、「開始する」で目標を進行中へ遷移させる。負荷係数・必要連続時間・必要環境・品質指標の方式は既定値のまま作成し、目標詳細画面（SC-03）から後で変更できる旨を案内する

各ステップは「次へ」「戻る」で移動する。「次へ」を押した時点で、目標本体・科目・教材・リソース配分をその都度サーバへ反映する（画面を離れても目標はDRAFT状態のまま目標一覧に残り、SC-03から手動で続行できる）。

- あるスロットについて、進行中の全目標の配分時間の合計がそのスロットの連続時間を超える場合、保存を拒否する（NT-04）

- 受験日が期間の場合、期間開始日が本日より過去である場合に警告を表示する

目標の状態がクローズの場合、全項目を読み取り専用とする。

**読書目標（category=READING）の場合**

タブ構成を以下に簡略化する。試験科目・教材・負荷プロファイルの各タブは表示しない（GOL-15、R-69〜R-71）。リソース配分タブは、読書も自由な時間に行う活動でありスロットを奪い合うため表示する（R-64、要件定義書6.10）。

| タブ | 内容 |
| --- | --- |
| 基本情報 | 目標名（書名を既定値とする）、開始日、状態、備考 |
| 書籍 | 書名、著者（任意）、総ページ数、読書開始日、読了目標日（GOL-16、R-70） |
| リソース配分 | 時間スロットごとの、本目標への配分時間（分）の設定。入力項目・検証は資格試験と共通 |

読書目標のリソース配分は**任意**とする。未設定（全スロット0分）のままでも進行中へ遷移できる（R-64）。読書は日次ノルマ・完了予測を持たないため、配分が0でも機能が成立するためである。

書籍タブの入力項目は以下のとおり。書名・読書開始日は、書籍未登録の間は基本情報タブの目標名・目標開始日をそれぞれ初期値として転記する（二重入力の回避。1.1改27）。転記はあくまで初期値であり、登録済みの書籍がある場合や、利用者が値を変更した場合はその値を優先する。

| 項目 | 型 | 必須 | 備考 |
| --- | --- | --- | --- |
| 書名 | 文字列 | 要 | 未登録時は目標名を初期値として転記する |
| 著者 | 文字列 | 任意 | — |
| 総ページ数 | 整数 | 要 | 1以上。ページ進捗を常に表示できるようにするため必須とする（1.1改19） |
| 読書開始日 | 日付 | 要 | 未登録時は目標開始日を初期値として転記する（1.1改27） |
| 読了目標日 | 日付 | 要 | — |

基本情報タブ・書籍タブ以外に、読了レポートタブを設ける。内容はSC-13（6.10）参照。

**読了操作**

読書目標には資格試験のSC-10（受験結果登録）に相当する画面を設けない。かわりに書籍タブに「読了として記録する」操作を設け、実行により目標を直接クローズ状態へ遷移させる（確認モーダル表示）。クローズと同時に読了レポートの生成を開始し、ナレッジエクスポート画面（SC-13）へ遷移する（CLS-07、R-67）。中断・断念する場合は、資格試験と共通のGOL-10（目標状態変更）から一時停止・クローズを行う。

目標のクローズ（読了・中断を問わず）以降、全項目を読み取り専用とする（資格試験と同様の状態制御。R-71）。

日次ノルマ・実効速度・完了予測日・警告に関する表示は行わない（R-71）。かわりにGOL-17（読書進捗表示）を基本情報タブに表示する。表示項目は「残日数」「直近記録日」「連続記録日数」「ページ進捗（現在ページ／総ページ数）」とする。総ページ数は必須のため、現在ページが一度でも入力されていればページ進捗を常に表示する（現在ページが未入力の間のみ非表示）。進捗率は100%を上限とし、これを超えて表示することはない（1.1改19）。

**仕事目標（category=WORK）の場合**

タブ構成を以下に簡略化する。試験科目・教材・リソース配分・負荷プロファイルの各タブは表示しない（GOL-15、R-74、6.11）。

| タブ | 内容 |
| --- | --- |
| 基本情報 | 目標名（案件名を既定値とする）、開始日、状態、備考 |
| 案件情報 | 案件名（取引先・案件の呼称、任意）、想定業務内容、着手日、役割、チームメンバー（GOL-18、GOL-20、GOL-21、R-72、R-73、R-93〜R-95） |

案件情報タブの入力項目は以下のとおり。

| 項目 | 型 | 必須 | 備考 |
| --- | --- | --- | --- |
| 取引先・案件の呼称 | 文字列 | 任意 | — |
| 想定業務内容 | 複数行テキスト | 要 | 営業・顧客から事前に伝えられた内容。登録後も更新可能（更新は上書きとし、変更履歴は保持しない。R-73） |
| 着手日 | 日付 | 要 | — |
| 役割 | 選択式（未設定／評価者／被評価者） | 任意 | 利用者自身がこの案件に対しどちらの立場かを自己申告する（GOL-21、R-95）。マルチユーザー機能ではなく単独の利用者の自己申告であり、評価者に設定すると評価レポートタブ（後述）が表示される |

書籍と異なり読了目標日に相当する項目は持たない（案件には納期未定の場合があり、読書の読了目標日のような必須の外部制約が存在しないため。データ構造編5.3参照）。

**チームメンバー（GOL-20、2026-09-23、R-93・R-94）**

案件情報タブに、チームメンバーの一覧・追加・編集・無効化・削除を行う欄を設ける。役割設定を問わず、この案件を利用する全ての利用者が操作できる。

| 項目 | 型 | 必須 | 備考 |
| --- | --- | --- | --- |
| 氏名・イニシャル | 文字列 | 要 | — |
| 性別 | 選択式（未設定／男性／女性／その他） | 任意 | — |
| 特徴・性格 | 複数行テキスト | 任意 | 第三者の機微情報。保存には下記の同意確認が必要 |

特徴・性格を非空の内容で保存する際は、「本人確認済み（本人の同意を得たうえで登録しています）」チェックボックスへのチェックを必須とする（R-94）。このチェックはサーバ側でも必ず検証し、チェックなしでの保存はエラー（`CONSENT_REQUIRED`）となる。既に保存済みの特徴・性格を変更する場合も、変更のたびに再度チェックが必要である（同じ内容の保存し直しであっても同様。第三者の機微情報を扱う初のフィールドであるための保守的な仕様）。無効化したメンバーは一覧に残るが、新規の日次記録・評価レポート対象からは除外される。評価レポート（後述）が1件でも存在するメンバーは物理削除できない（無効化のみ可能）。

チームメンバーの内容は、この画面（目標詳細画面）と日次報告画面（SC-06、後述）の双方から編集でき、どちらから変更しても双方の画面に同じ内容が反映される（同期、R-93）。

**評価レポートタブ（GOL-21・CLS-15・CLS-16、2026-09-23、R-95・R-96）**

役割が「評価者」に設定されている案件でのみ表示するタブ。役割が未設定または「被評価者」の場合はタブ自体を表示しない。

- 登録済みのチームメンバー（無効化済みを除く）から評価対象を選択する
- 自由記述の考慮事項を入力する
- 「評価レポートを生成」ボタンを押すと、当該案件の日次業務記録・当該案件の日次報告AIフィードバック履歴・入力した考慮事項を入力としてAIが評価レポートのドラフトを生成し、そのまま同タブ内にレビュー用の複数行テキスト欄として表示する（月次報告・半期評価と同じ「生成→その場でレビュー→保存」の流れ。R-96）
- レビュー欄の内容は自由に修正でき、「保存」操作で確定する（保存のたびに当該レポートの内容を上書きする）
- 「Markdownをダウンロード」ボタンで、レビュー欄の現在の内容をファイルとしてダウンロードできる
- 生成のたびに新規の履歴として保持される（月次報告・半期評価のような期間単位の上書きではない。同一メンバーに対して複数時点の評価レポートを保持する意味があるため）。生成履歴の一覧から過去のレポートを選び直してレビュー欄へ読み込み、再編集・再ダウンロードできる

基本情報タブ・案件情報タブ以外に、月次報告タブ・半期評価タブを設ける。ナレッジエクスポート機能はSC-13（6.10）参照。月次報告タブ・半期評価タブは以下のとおり（2026-09-04改訂、要件定義書R-78・R-79・R-82・R-83）。

- 「ドラフトを生成」ボタンを持つ。押下時、対象期間（月次報告は前月、半期評価は当該半期が既定値。ロジック・プロンプト編22.5）のドラフトをAIが生成し、そのまま同タブ内にレビュー用フォームとして表示する（生成結果を別画面に遷移させない）
- レビュー用フォームは、当該期間の目標（`target_goal_text`）・業務内容の要約・達成度（1〜5、選択式）・達成状況の振り返り・来月／次半期の目標案・報告連絡事項（月次報告のみ）を、それぞれ編集可能な入力欄として表示する。利用者はAIの生成内容をその場で修正でき、「保存」操作で確定する（保存のたびに内容を上書きする。修正履歴は保持しない。R-82）
- 生成済みの場合は対象期間を選択して過去分を閲覧・編集できる（過去分の編集もレビュー用フォームと同じ画面・同じ操作で行う）
- 前期に相当する行が存在しない場合（案件着手直後等）、当該期間の目標欄のみを利用者が直接入力して保存できる（AI生成を待たずに運用を開始できる。R-83）
- 「Markdownをダウンロード」ボタンを持つ。押下時、現在保存されている内容から組み立てたMarkdown文書（ロジック・プロンプト編22.6のテンプレート）をファイルとしてダウンロードする。生成直後・未保存の内容ではなく、保存済みの内容を対象とする
- ダッシュボードの仕事目標カード（DSH-07）から、対象の仕事目標の月次報告タブへ直接遷移するボタンを設ける（即座にダウンロードは行わない。生成結果をレビューせず社内へ提出する事故を防ぐため）

**クローズ操作**

仕事目標には資格試験のSC-10（受験結果登録）に相当する画面を設けない。案件の終了は、資格試験と共通のGOL-10（目標状態変更）から行う。案件が納品等の成果を伴って終了した場合は「結果あり」（`CLOSED_WITH_RESULT`）、中止・打ち切りの場合は「結果なし」（`CLOSED_WITHOUT_RESULT`）を選択する（いずれも確認モーダル表示）。読書と異なり、クローズ操作は月次報告・半期評価の生成契機ではない（月次報告・半期評価は案件の進行中に周期的に生成する。CLS-09〜CLS-12）。

目標のクローズ以降、全項目を読み取り専用とする（資格試験と同様の状態制御）。

日次ノルマ・実効速度・完了予測日・警告に関する表示は行わない（R-74）。かわりにGOL-19（仕事進捗表示）を基本情報タブに表示する。表示項目は「経過日数」「直近記録日」「連続記録日数」「直近の月次報告有無」とする。

### 6.3 SC-04 リソースマスタ設定

**時間スロットの入力項目**

| 項目 | 型 | 必須 | 備考 |
| --- | --- | --- | --- |
| スロット名 | 文字列 | 要 | 通勤、始業前など |
| 開始時刻 | 時刻 | 要 | — |
| 終了時刻 | 時刻 | 要 | — |
| 環境タグ | 選択 | 要 | 机上のみ／移動中でも可 |
| 適用曜日 | 複数選択 | 要 | 月〜日 |

連続時間は開始・終了時刻から自動算出する（R-85）。利用者に時間量を直接入力させることはしない。

**時間の単位と表示規則**

算出・保持の単位は分（整数）とする。時間（hour）で表示する箇所では、**小数第2位以下を切り捨てて小数第1位まで**を表示する（例：50分＝0.8333…時間 → 「0.8時間」）。切り捨ては表示時にのみ適用し、算出には常に分（整数）の値を用いる。四捨五入は用いない。

**日種別の既定設定**

曜日ごとに計画日またはバッファ日を選択する。祝日については、祝日データに含まれる日を一律でバッファ日とするか否かを選択する。

**1日の境界時刻**

日付が切り替わる時刻を設定する。既定値は午前0時とする。深夜まで学習する習慣がある場合、午前4時などに設定することで、深夜の学習が翌日に計上されることを防ぐ。

**表示要素**

- 曜日別の総確保時間
- スロットごとの、各目標への配分時間と未配分の残り時間
- 環境タグ別の時間内訳

スロットの配分時間の合計がそのスロットの連続時間を超えている場合、当該スロットに超過分を明示した警告を表示する（NT-09）。この状態は、配分の設定後にスロットを短縮・削除した場合に発生する。

### 6.4 SC-05 カレンダー

**表示仕様**

各日付セルに以下を表示する。

| 要素 | 表示内容 |
| --- | --- |
| 背景色 | 日種別（計画日／バッファ日／除外日）。目標に紐づかないアプリ全体の値 |
| マーカー | 記録状態（未入力／進捗のみ登録済／報告済）。目標に紐づかないアプリ全体の値 |
| 補助表示 | 受験日、受験期間、負荷係数が1.0以外の期間。着手中（ACTIVE）の目標が2件以上ある場合、画面上部の目標タブ（日次報告6.5と同じGoalTabBar）で選択した1目標分のみを表示する（1.1改14）。着手中の目標が0〜1件の場合は目標タブを表示せず、従来どおりその目標（または該当なし）の内容をそのまま表示する |

**1.1改14での変更点**：従来は「進行中の全目標を1画面に集約表示し、2目標以上が同日に補助表示を持つ場合は目標名で区別する」方式だったが、目標ごとに機能を分離する設計（6.5・6.1参照）をカレンダーにも統一するため、目標タブで1目標分に絞り込む方式に変更した。背景色・マーカーは目標に紐づかないアプリ全体の値のため、この変更の対象外である。

**操作**

| 操作 | 条件 | 遷移先 |
| --- | --- | --- |
| 日付選択 | 当日 | 日次報告 |
| 日付選択 | 未入力かつ前日 | 日次報告または進捗のみ登録を選択 |
| 日付選択 | 未入力かつ2日以上前 | 進捗のみ登録 |
| 日付選択 | 進捗のみ登録済かつ前日 | 日次報告への昇格 |
| 日付選択 | 進捗のみ登録済かつ2日以上前 | 閲覧のみ |
| 日付選択 | 報告済かつ当日または前日 | 日次報告 |
| 日付選択 | 報告済かつ2日以上前 | 日次報告閲覧 |
| 日付選択 | 未来日 | 日種別の変更のみ可能 |
| 日種別変更 | 全ての日 | カレンダー内で処理 |

判定は「未来日か」「対象日が入力可能期間（当日または前日、7.2）内か」を先に確定させ、
最後に記録状態で分岐する（1.1（改20））。記録状態は未着手カテゴリを除外した集約値（7.2）であり、
1カテゴリだけ確定した日も「報告済」となるため、これを最優先で閲覧へ振ると同じ日の残りのカテゴリを
報告できなくなるためである。入力可能期間内で「報告済」の日に日次報告へ進んだ場合、着手中の全カテゴリが
確定済みであれば日次報告画面が日次報告閲覧へ自動転送する（6.5）。2日以上前の未入力日で進捗のみ登録へ
直接遷移させるのは、その日はもはや確定できず（7.2）、日次報告を選べても入力内容が確定時に失われるためである。

### 6.5 SC-06 日次報告

**構成**

画面を上下2段に分割する。上段を実績入力、下段をAI対話とする。画面上部に所要時間の目安（「3分で終わります」）を表示する（1.1（改28）、記録画面改善タスク）。

着手中（ACTIVE）の目標が2件以上ある場合、画面上部に目標タブを表示し、対象目標を1件ずつ選択して切り替える（目標設定画面のカテゴリ選択と同様、選択肢は着手中の目標に限る）。実績入力・日記・AI対話は選択中の目標の種別（資格試験／読書／仕事）に応じた内容のみを表示し、他の目標の入力欄は表示しない。ただし下書き値はタブの選択に関わらず全目標分をローカルに保持し続けるため、タブを切り替えても入力内容は失われない。着手中の目標が0〜1件の場合はタブを表示せず、従来通りその目標の内容をそのまま表示する。

確定（finalize）はカテゴリ（資格試験／読書／仕事）ごとに独立している（1.1（改13））。あるカテゴリの確定ボタンを押すと、そのカテゴリの実績・日記のみが確定済み（報告済）となり、そのタブは以降そのセクションのみ読み取り専用表示に切り替わる。他カテゴリの確定状態には影響せず、引き続き入力・確定できる。当日中に着手しているすべてのカテゴリが確定済みになった時点で、初めてダッシュボードへ遷移する。

本画面を開いた時点で、着手中の全カテゴリが既に確定済みの場合、または対象日が入力可能期間（当日または前日、7.2）を過ぎている場合は、日次報告閲覧（SC-08）へ自動転送する（1.1（改20））。遷移元（ダッシュボード6.1・カレンダー6.4）は対象日が入力可能期間内かのみを判定し、「まだ報告すべきカテゴリが残っているか」の判定は本画面に集約する。判定に必要な着手中の目標・書籍・案件は本画面のみが取得しているためである。入力可能期間を過ぎた日で転送するのは、入力させたうえで確定時にエラー（14章 BACKDATE_LIMIT_EXCEEDED）となり入力内容が失われるのを防ぐためである。

**ゼロ記録（「今日は何もしていない」ボタン、1.1（改28））**

画面上部（目標タブの上）に「今日は何もしていない」ボタンを表示する。対象は、その日ACTIVEなのに一度も操作していない（未入力）カテゴリのみとし、既に進捗のみ登録済み（実データがある）カテゴリ・報告済みのカテゴリは対象から除外する。全カテゴリが対象外（未入力カテゴリが無い）の場合はボタン自体を表示しない。

押下すると確認モーダルを挟み（取り消せない操作のため）、承認すると対象カテゴリを実績・日記とも空のまま確定する（資格試験：完了量・投下時間ともに未入力のまま確定、読書・仕事：想起・業務内容とも未入力のまま確定）。これは通常の確定処理と技術的に同一であり、実績が1件も無い状態での確定を拒否しないためゼロ記録として成立する。確定後の記録状態は「報告済」とする（7.2の状態遷移における「報告一式を入力」と同じ終着点として扱う。翌日以降に再入力を促さないため）。

確定後はダッシュボードで表示している日種別に応じて次のいずれかをトースト表示する。

| 日種別 | 表示文言 |
| --- | --- |
| PLAN（計画日） | 「記録しました。明日また開いてください」 |
| BUFFER・OFF（バッファ日・除外日） | 「今日はお休みの日です。休むことも計画のうちです」 |

ゼロ記録の確定はAI対話（`/chat`・`/reading-chat`・`/work-chat`）を一切呼び出さない。当日中に着手している全カテゴリが（ゼロ記録も含めて）確定済みになった場合のみダッシュボードへ遷移する規則は、通常の確定と共通（上記「確定処理」参照）。

ゼロ記録の日もカレンダー・ダッシュボード上は「報告済」として扱われ、連続記録日数・報告率の算出（13章）にもそのまま反映される（record_serviceの確定状態列のみで判定するため、実績行の有無を問わない）。

**実績入力（上段、資格試験目標選択時）**

進行中の教材のうち、当日が学習期間内（開始日〜締切）のものを行として表示する。開始日前の教材は表示しない（先行着手した内容は「本日の行動・所感」に自由記述する）。この絞り込みはSC-01の本日のノルマ・SC-07にも共通で適用される。

上記の目標タブにより、この一覧には選択中の1目標の教材のみが含まれるため、目標名の見出しは表示しない（ダッシュボードSC-01も1.1改14で同じ目標タブ方式に変更されたため、目標名の見出しによるグルーピング表示は行わない）。

| 列 | 内容 |
| --- | --- |
| 教材名 | 表示のみ |
| 現在周回 | 表示のみ。「2周目 / 全3周」の形式 |
| 本日の目標 | 算出された日次ノルマを表示 |
| 時間枠ごとの投下時間 | 後述「時間枠ごとの投下時間の入力」を参照 |
| 投下時間（合計） | 表示のみ。時間枠ごとの入力値の合計を自動算出 |
| 完了分量 | 数値入力 |
| 周回 | 数値入力。既定値は現在の周回数 |
| 品質指標 | 教材の設定方式に応じた入力欄。任意 |

**時間枠ごとの投下時間の入力（R-14、R-86）**

投下時間は教材ごとに1つの欄で入力するのではなく、**教材の行の中に、その目標が配分している時間スロットごとの入力欄を並べて**入力する。教材の投下時間はこれらの合計として自動算出し、実効速度の算出にはこの合計を用いる。

| 項目 | 内容 |
| --- | --- |
| 表示するスロット | 当日の曜日に該当し、かつ選択中の目標がリソース配分を設定しているスロット |
| 初期値 | リソース配分の設定値を、そのスロットに適合する教材へ按分した値（ロジック・プロンプト編9.2） |
| 変更の扱い | 入力値の変更はその日の実績としてのみ保存し、リソース配分の設定値（マスタ）は変更しない |
| 未配分スロットの追加 | 「他の時間枠を追加」操作により、配分していないスロットを行に追加して入力できる。予定外の空き時間に学習した分を記録できないと、投下時間が実態より小さく計上され実効速度が過大に算出されるため |

全スロットの入力欄が空欄の場合、その教材の投下時間は「未入力」として扱う（0分ではない）。未入力の実績は実効速度の算出対象から除外される（ロジック・プロンプト編8.4）。

品質指標の入力形式は以下とする。

| 方式 | 入力形式 |
| --- | --- |
| 客観正答率 | 0〜100の数値 |
| 自己採点得点率 | 0〜100の数値 |
| 主観的手応え | 5段階の選択（内部的に20/40/60/80/100へ変換） |

**日記記述（上段下部、資格試験目標選択時）**

「本日の行動・所感」欄は、空白の入力欄が心理的な壁になる問題への対応として、質問への回答形式へ再構成した（1.1（改28）、記録画面改善タスク）。質問（固定2問、ロケールで管理）と「自由に書く」欄（従来の自由記述欄。ラベルを変更しただけで役割は同じ）を1画面に併記し、いずれも任意入力とする。1つだけ回答しても確定できる。

| 項目 | 内容 |
| --- | --- |
| 質問1 | 「今日いちばん印象に残った問題や概念は？」への回答欄。複数行テキスト。任意 |
| 質問2 | 「詰まったところはある？」への回答欄。複数行テキスト。任意 |
| 自由に書く | 複数行テキスト。自由記述（旧・本日の行動・所感欄） |
| 本日学んだこと | 複数行テキスト。当日の学習内容を自らの言葉で記述する欄。プレースホルダに記述例を提示。質問形式の対象外（従来どおりの単一自由記述欄） |

保存する日記本文（`diary_body`）は、回答された質問を「【質問文】\n回答」の形式で結合し、末尾に「自由に書く」欄の内容（ラベルなし）を連結したものとする。質問に一切回答せず「自由に書く」欄だけを使った場合は、結合結果はその欄の文章そのものになる（ラベルは付与しない）。これにより、質問形式に触れない利用者・進捗のみ登録から継続して報告する利用者のいずれも、従来と同じ本文がそのまま保存・AIへ注入される（データ構造・AIプロンプトへの注入内容は変更しない）。「本日学んだこと」欄は質問形式の対象外で、従来どおり単独の項目として保存する。

各記述欄の上部に、直近の記録日の本文冒頭（100文字程度）を「前回はこう書いていました」として薄く表示する（前回の記録が無ければ非表示。クリックで全文展開）。対象は「前日」に限らず、記録がある直近の日まで遡って探索する。あわせて、記述欄の近くにWindowsの音声入力（Win + H）で入力できる旨を小さく案内する（案内文の表示のみ。音声認識機能自体は実装しない）。

日記欄は上記の目標タブに連動し、選択中の資格試験目標についてのみ表示する（読書目標は後述の想起入力が同じ役割を果たすため、日記欄の対象外）。当日のノルマ有無に関わらず選択中の目標がACTIVEであれば表示し、先行着手した内容を自由記述できる逃げ道を維持する。

**AI対話（下段）**

チャット形式の対話領域とする。初回の応答は、実績入力および日記の内容を確定して送信した時点で生成される。

対話は複数往復可能とする。対話終了後、確定操作により報告が確定する。

同一カテゴリの目標が2件以上同時進行している場合、AI対話（会話・プロンプト・履歴のいずれも）は選択中の1目標のみを対象とする（1.1改15、未決事項L-07の解消方針転換）。目標タブを切り替えて別の目標を選択した場合、実績入力・日記と同様にAI対話も選択中の目標分のみへ切り替わる。以前の版（改13以前）はカテゴリ単位で1本の会話を共有し、複数目標の状況をまとめて1回の応答で返す方式だったが、目標ごとに独立した会話・応答へ変更した。

**AIが参照した情報の開示・送信内容への不安の解消（非エンジニア向けエラー表示改善、2026-09-19）**

対話領域に、直近の送信でAIへ渡した情報の種別を折りたたみ（既定は閉じた状態）で表示する。展開すると「目標の情報」「今日の記録」「直近の週次要約」（資格試験のみ「教材の進捗」も）の一覧が表示される。プロンプト全文は表示しない（長すぎて逆に不安を招くため）。送信欄の近くには「送信されるのはこのPCの中の記録だけです。外部に保存されることはありません」を常時表示する。

**AI未設定時の案内**

AI接続が未設定（設定画面で未認証）の状態でAI対話・レポート生成（総括レポート、月次報告・半期評価を含む）を開いた場合、エラーではなく「この機能を使うには、AIの接続設定が必要です。設定しなくても、記録や閲覧はそのまま使えます」という案内と、設定画面へのボタンを表示する。実績入力・確定・記録の閲覧はAI未設定でも通常どおり行える。

**今日の一言のみ例外（S-4 4-1、2026-09-20）**：今日の一言はGET時に自動生成する設計（DSH-03）のため、上記の「案内表示」ではなく、AI呼び出し自体を行わず固定のねぎらい文言（ロケールファイル外部化）を表示する。DBには保存せず、AI設定後に再取得すると通常のAI生成へ自動的に切り替わる。

**確定処理**

確定（資格試験／読書／仕事の各カテゴリの確定ボタン）により、そのカテゴリについて以下が実行される。

1. 実績数値および日記本文（資格試験のみ）を変更不可として保存
2. 対話履歴を保存
3. 当日・当該カテゴリの記録状態を報告済に変更
4. 当日中に着手している全カテゴリが報告済になった場合のみダッシュボードへ遷移。他に未確定のカテゴリが残る場合は同じ画面に留まり、確定したカテゴリのタブのみ読み取り専用表示に切り替わる

確定前の下書き（実績入力・日記・対話履歴）は、画面（ページ）の外に保持し、確定するまで一切サーバへ保存しない（16.7）。従来はページ単位で保持していたため、確定前に別の画面へ移動すると入力内容が失われていたが、アプリ全体で共有する保持領域へ移したことで、別画面へ移動して戻っても同一セッション内であれば入力内容が復元される（1.1（改28）、記録画面改善タスク）。ブラウザを閉じる・再読み込みすると下書きは失われる（サーバへの下書き保存は日次記録の不変性の設計上行わない）ため、その場合のみブラウザ標準の確認ダイアログで警告する。アプリ内遷移（別画面への移動）そのものはもはや入力内容を失わないため、警告なしで移動を許可する（従来あった「移動しますか？」の確認モーダルは撤去した）。

**AI応答が得られない場合**

AI基盤が利用できない場合も、確定操作を許容する。この場合、対話履歴は空となる。

**読書目標の実績入力（REP-13、REP-14）**

進行中の読書目標を選択している場合、実績入力（上段）に書籍ごとの想起欄を表示する（上記の目標タブにより資格試験目標の教材行とは排他表示となる）。

想起欄も資格試験の日記欄と同様、質問への回答形式へ再構成した（1.1（改28）、記録画面改善タスク）。質問（固定2問）と「自由に書く」欄（従来の想起欄。ラベルを変更しただけで役割は同じ）を1画面に併記し、いずれか1つに入力があれば確定できる（従来の「想起本文は必須」の実質を、質問群のいずれかへの入力必須へ置き換えた）。

| 項目 | 内容 |
| --- | --- |
| 書名 | 表示のみ |
| 質問1 | 「今日読んだ中で心に残った箇所は？」への回答欄。複数行テキスト。任意 |
| 質問2 | 「自分の仕事や生活とつながると感じたことは？」への回答欄。複数行テキスト。任意 |
| 自由に書く | 複数行テキスト。自由記述（旧・今日読んだ内容の想起欄）。プレースホルダに「今日はどこまで読みましたか。印象に残ったことは何ですか」等の記述例を提示 |
| 時間枠ごとの読書時間 | 資格試験の「時間枠ごとの投下時間の入力」と同一の仕様（表示するスロット・初期値・その日限りの変更・未配分スロットの追加）。任意 |
| 読書時間（合計） | 表示のみ。時間枠ごとの入力値の合計を自動算出 |
| 現在ページ | 数値入力。任意。0以上、総ページ数以下 |

保存する想起本文（`recall_body`）は日記欄と同じ規則で結合する（質問回答は「【質問文】\n回答」形式、末尾に「自由に書く」欄をラベルなしで連結）。質問に触れず「自由に書く」欄だけを使った場合は従来と同じ本文がそのまま保存される。数値実績（現在ページ・読書時間）の入力は必須としない（R-65）。想起欄（質問・自由記述のいずれか）のみの入力でも確定できる。

想起欄の上部に「前回はこう書いていました」ヒント、近くにWindows音声入力の案内を表示する（日記欄と同じ仕様、1.1（改28））。

ページに関する入力欄は「現在ページ」1つだけとする（1.1改19）。従来あった「読んだページ数」は廃止した。利用者がその日に読んだページ数を毎日記憶していられないという実際の利用上の問題があり、かつ読書は定量的な進捗管理を行わない目標（R-71）であるため、投下量の指標を保持する意味がないためである。現在ページは画面上の進捗表示のためだけに用い、評価の対象とはしない（下記のAI対話への差し込み情報を参照）。

読書目標で記録した時間は、実効速度・完了予測日の算出には用いない（読書はこれらを持たないため。R-71）。集計・表示・AIへの文脈提供にのみ用いる。

AI対話（下段）は資格試験と共通のUI構成を用いるが、通信先は別エンドポイント（`POST /records/{date}/reading-chat`）とし、読書用プロンプト（REP-14、17.6参照）で生成する。会話・対話履歴は用途ごと・目標ごとに分離されており（`ai_conversation`の`scope`＋`goal_id`、および`chat_message.purpose`＋`goal_id`によるフィルタリング。データ構造編5.4・5.5、ロジック・プロンプト編21.1、1.1改15）、資格試験目標と読書目標が同日に両方進行中でも、また同カテゴリの目標が2件以上進行中でも、互いの対話内容は相手のプロンプトに混入しない。

業務内容欄も読書の想起欄と同様、質問への回答形式へ再構成した（1.1（改28）、記録画面改善タスク）。

読書と異なり、ページ数のような数値項目は持たない（要件定義書6.11本文「構造化フィールドは持たない」という設計判断）。保存する業務内容（`body`）は日記欄・想起欄と同じ規則で結合し（質問回答は「【質問文】\n回答」形式、末尾に「自由に書く」欄をラベルなしで連結）、質問・自由記述のいずれか1つの入力でも確定できる（従来の「業務内容は必須」の実質を、質問群のいずれかへの入力必須へ置き換えた）。業務内容欄の上部に「前回はこう書いていました」ヒント、近くにWindows音声入力の案内を表示する（日記欄と同じ仕様）。

### 6.6 SC-07 進捗のみ登録

実績入力領域のみを持つ。日記記述およびAI対話領域を持たない。実績入力の構成（時間枠ごとの投下時間の入力を含む）は6.5と共通とする。

**対象カテゴリ（1.1（改21））**

実績入力は6.5と共通であり、資格試験（教材ごとの実績）・読書（書籍ごとの想起）・仕事（案件ごとの業務記録）の3カテゴリを扱う。着手中（ACTIVE）の目標があるカテゴリの入力欄をすべて同時に表示し、1回の登録操作でまとめて送信する（カテゴリのいずれかに1件以上の入力があれば登録できる）。

6.5と異なり目標タブは設けない。目標タブはAI対話と確定を目標1件へ絞るための仕組みであり（6.5）、どちらも持たない本画面では絞り込む必要がないためである。

既に報告済みのカテゴリは変更不可のため（7.2）、そのカテゴリの入力欄を表示せず、登録の送信対象にも含めない。着手中の全カテゴリが報告済みの日は、本画面を開いた時点で日次報告閲覧（SC-08）へ自動転送する。

投下時間は任意入力とする。時間枠ごとの入力欄がすべて空欄の場合を未入力とし、当該日は実効速度の算出対象から除外される旨を画面上に明示する。

対象日が未来日の場合は、本画面を開いた時点で日次報告閲覧（SC-08）へ自動転送する（仕様書1.1（改20））。進捗のみ登録に遡りの上限は無いが未来日は登録できず（7.2）、入力させたうえで送信時にエラーとなると入力内容が失われるためである（SC-06の入力可能期間ガードと同じ方針）。

### 6.8 SC-09 分析

### 6.16 SC-18 本棚（1.1改38）

読了・中断した読書目標（category=READING）を書籍カードとして表示する画面。SC-02（目標一覧）のクローズ済み表示を置き換えるものではなく、読書目標を選んだ利用者が引き続き使う追加の入口という位置づけ（設計協議で確定。資格試験・仕事目標には本画面は無い）。

**表示要素**

| 領域 | 内容 |
| --- | --- |
| 読了した本棚 | `status=CLOSED_WITH_RESULT` かつ `archived_at IS NULL` の書籍カードを、クローズ日（`closed_at`）の新しい順に表示 |
| 中断した本棚 | `status=CLOSED_WITHOUT_RESULT` かつ `archived_at IS NULL` の書籍カードを、読了棚とは別セクションに同じ順序で表示。背表紙の配色・バッジを読了棚と変え、中断であることを視覚的に区別する |

| しまった本を見るトグル | ONにすると`archived_at IS NOT NULL`の書籍のみのセクションを追加表示（SC-02の「アーカイブ済みを表示」と同じ設計） |

**操作**

- 棚上（未アーカイブ）の書籍カードの「棚にしまう」ボタン：確認後、しまった本セクションへ移動する（SC-02の「アーカイブ」と同じ`archived_at`を用いた操作。本棚専用の状態列は持たない）
- しまった本セクションの書籍カードの「棚に戻す」ボタン：即時に棚上へ戻す（確認モーダルなし）
- しまった本セクションの書籍カードの「完全に削除」ボタン：MD-08で確認後、目標および紐づく全データ（書籍・想起記録）を物理削除する

**状態による制御**

- 「棚にしまう」操作が可能なのは棚上（`archived_at IS NULL`）の書籍のみ。完全削除操作が可能なのはしまった本のみ（SC-02の状態制御と同じ`canArchiveGoal`判定を用いる）

## 7. 状態遷移仕様

### 7.1 目標の状態遷移

```
        ┌─────────┐
        │ 下書き  │
        └────┬────┘
             │ 開始
        ┌────▼────┐
   ┌────│ 進行中  │────┐
   │    └────┬────┘    │
   │ 一時停止 │ 受験完了 │ 中断・辞退
   │         │         │
┌──▼──────┐  │  ┌──────▼──────┐
│ 一時停止 │  │  │ クローズ     │
└──┬──────┘  │  │（結果登録なし）│
   │ 復帰     │  └─────────────┘
   └─────────┘
             │
       ┌─────▼──────────┐
       │ クローズ        │
       │（結果登録あり）  │
       └────────────────┘
```

**遷移条件**

| 遷移 | 条件 |
| --- | --- |
| 下書き → 進行中 | 試験科目1件以上、教材1件以上、リソース配分が設定済み（いずれか1つ以上のスロットへ1分以上を配分していること） |
| 進行中 → 一時停止 | 制約なし。リソース配分を解放する（配分値は保持したまま、スロットの空き時間の計算対象から除外する） |
| 一時停止 → 進行中 | 配分している各スロットについて、空き時間が元の配分時間以上であること。1つでも不足する場合はエラー |
| 進行中 → クローズ（結果あり） | 全科目の受験結果が登録済み |
| 進行中 → クローズ（結果なし） | 確認モーダルでの承認 |
| クローズ → 他の状態 | 遷移不可 |

クローズへの遷移時、総括レポートの生成を非同期で開始する。生成の成否はクローズ処理の成否に影響しない。

### 7.1.1 アーカイブ状態

アーカイブは `GoalStatus` とは独立したフラグ（`archived_at`）で表現し、状態遷移図には含めない。可視性のみを制御し、`status` 自体は変化しない。

| 遷移 | 条件 |
| --- | --- |
| 進行中でない → アーカイブ | `status` が `ACTIVE` 以外（`DRAFT` / `PAUSED` / `CLOSED_WITH_RESULT` / `CLOSED_WITHOUT_RESULT`）であること（要件定義書R-61、1.1（改6）） |
| アーカイブ → 復元 | いつでも可能。復元後の `status` はアーカイブ前のまま変わらない |
| アーカイブ済み → 完全削除（物理削除） | アーカイブ済みであること。学習実績を含めて削除するか、実績が残る場合は拒否するかを選択する（データ構造編4.2） |

アーカイブ中は状態遷移操作（下書き→進行中の開始、一時停止→進行中の再開、下書きの即時削除）を拒否し、まず復元（アーカイブ解除）が必要（`activate_goal`・`resume_goal`・`delete_goal`のガード）。`ACTIVE`は元よりアーカイブ不可のため、進行中→一時停止・進行中→クローズの遷移とアーカイブ状態が同時に成立することはない。

**読書目標（category=READING）の場合の遷移条件**

状態遷移そのもの（下書き／進行中／一時停止／クローズ）は資格試験と共通の`GoalStatus`を用いるが、遷移条件は以下のとおり読み替える。アーカイブ・完全削除の遷移条件（上記7.1.1）は種別を問わず共通であり、完全削除時の実績の道連れ判定は読書目標では想起記録（reading_log）が対象となる（データ構造編4.2）。

| 遷移 | 条件 |
| --- | --- |
| 下書き → 進行中 | 書籍が1件登録済みであること（試験科目・教材は不要。リソース配分は任意のため未設定でも遷移できる。R-64） |
| 進行中 → 一時停止 | 制約なし。リソース配分を設定している場合は資格試験と同様に解放する |
| 一時停止 → 進行中 | 配分している各スロットについて、空き時間が元の配分時間以上であること。配分が未設定の場合は制約なし |
| 進行中 → クローズ（`CLOSED_WITH_RESULT`＝読了） | 書籍タブでの「読了として記録する」操作の承認（6.2、`POST /books/{id}/complete`） |
| 進行中 → クローズ（`CLOSED_WITHOUT_RESULT`＝中断） | 確認モーダルでの承認（`POST /goals/{id}/close`。資格試験の「結果なし」クローズと同一エンドポイント） |
| クローズ → 他の状態 | 遷移不可 |

`CLOSED_WITH_RESULT`は資格試験では「合否結果を伴うクローズ」を意味するが、読書では合否が存在しないため「読了という成果を伴うクローズ」という意味に読み替えて用いる（設計書 データ構造編 5.3）。`CLOSED_WITH_RESULT`への遷移時、読了レポートの生成を非同期で開始する。生成の成否はクローズ処理の成否に影響しない（資格試験の総括レポートと同じ方針）。

**仕事目標（category=WORK）の場合の遷移条件**

状態遷移そのもの（下書き／進行中／一時停止／クローズ）は資格試験と共通の`GoalStatus`を用いるが、遷移条件は以下のとおり読み替える。アーカイブ・完全削除の遷移条件（上記7.1.1）は種別を問わず共通であり、完全削除時の実績の道連れ判定は仕事目標では業務記録（work_log）が対象となる（データ構造編4.2）。

| 遷移 | 条件 |
| --- | --- |
| 下書き → 進行中 | 案件情報が1件登録済みであること（試験科目・教材・リソース配分は不要） |
| 進行中 → 一時停止 | 制約なし。仕事目標は元よりリソース配分を持たないため解放処理は発生しない |
| 一時停止 → 進行中 | 制約なし（リソースの空き確認は行わない） |
| 進行中 → クローズ（`CLOSED_WITH_RESULT`＝結果あり） | 確認モーダルでの承認（納品等の成果を伴う終了。GOL-10、`POST /goals/{id}/close`にbody `with_result=true`を指定） |
| 進行中 → クローズ（`CLOSED_WITHOUT_RESULT`＝結果なし） | 確認モーダルでの承認（中止・打ち切り。`POST /goals/{id}/close`。`with_result`省略時の既定） |
| クローズ → 他の状態 | 遷移不可 |

読書と異なり、仕事目標のクローズ操作はレポート生成の契機ではない。月次報告・半期評価は案件が進行中の間、周期的に生成する（CLS-09〜12、6.2「クローズ操作」）。クローズ後は資格試験・読書と同様に全項目を読み取り専用とするが、既に生成済みの月次報告・半期評価は引き続き閲覧・エクスポートできる。

### 7.2 日付の記録状態遷移

記録状態（未入力／進捗のみ登録済／報告済）は、日付単位ではなくカテゴリ（資格試験／読書／仕事）ごとに独立して保持する（1.1（改13））。以下の状態遷移図・入力可能期間は、日付×カテゴリの組ごとに個別に適用される。あるカテゴリを報告済にしても、同日の他カテゴリの状態には影響しない。

```
  ┌────────┐
  │ 未入力 │
  └───┬────┘
      │
      ├──[実績数値のみ入力]──→ ┌──────────────┐
      │                        │ 進捗のみ登録済 │
      │                        └───────┬──────┘
      │                                │
      │                                │ 前日以内の場合のみ
      │                                │ 日記＋対話を追加
      │                                ▼
      └──[報告一式を入力]────────→ ┌──────────┐
                                    │ 報告済    │
                                    └──────────┘
                                    （以降変更不可）
```

**入力可能期間**

| 状態 | 入力可能条件 |
| --- | --- |
| 未入力 → 進捗のみ登録済 | 対象日が当日または前日以前 |
| 未入力 → 報告済 | 対象日が当日または前日 |
| 進捗のみ登録済 → 報告済 | 対象日が当日または前日 |
| 報告済 → 変更 | 不可（当該カテゴリのみ）。コメント追加のみ可能 |

「当日」の判定には設定された1日の境界時刻を用いる。

カレンダー・ダッシュボードで表示する日単位の記録状態（1状態）は、その日に着手した全カテゴリ（一度も入力していないカテゴリは対象外）の状態から算出する集約値である。着手した全カテゴリが報告済なら報告済、1つでも進捗のみ登録済があれば進捗のみ登録済、いずれのカテゴリにも一度も入力が無ければ未入力とする。

### 7.3 受験日の状態遷移

```
  ┌──────────────┐  確定操作  ┌──────────────┐
  │ 期間（暫定）  │──────────→│ 確定日        │
  └──────────────┘            └──────────────┘
```

期間から確定日への遷移時、計画の再算出を自動的に実行する。確定日から期間への逆遷移は許容する（誤操作の訂正のため）。

### 8.2 会話の管理方針

**制約**

開発キットでは、メッセージ送信前に会話を作成し、その識別子を指定する必要がある。会話はAI基盤側に永続化される。

**方針：用途と日付ごとに会話を分離する**

| 用途 | 会話の単位 | 会話のタイトル |
| --- | --- | --- |
| 日次報告 | 1日1会話（複数目標にまたがりうるため目標非依存） | `{日付} 日次報告` |
| 週次要約 | 1週1会話（目標ごと） | `{週開始日}週 週次要約` |
| 今日の一言 | 1日1目標につき1会話（ACTIVEな目標が無い日のみ目標非依存の1件） | `{日付} 今日の一言 {目標名}` |
| 総括レポート | 目標ごと1会話 | `総括レポート` |
| 仕事日次報告 | 1日1会話（読書と同様、目標非依存。資格試験の日次報告とは別会話） | `{日付} 仕事日次報告` |
| 月次報告 | 1か月1会話（目標ごと・対象月ごと） | `{対象月} 月次報告` |
| 半期評価 | 1半期1会話（目標ごと・対象半期ごと） | `{対象半期} 半期評価` |

**方針の理由**

会話を用途ごとに分離することで、異なる目的のプロンプトが文脈として混入することを防ぐ。日次報告のフィードバックが、朝に生成した「今日の一言」の文脈に引きずられる事態を構造的に排除する。

今日の一言は目標ごとに独立した会話・プロンプト呼び出しとする（未決事項L-04）。複数目標が同時進行している場合に、他目標の情報を一切混ぜないことで、順調な目標に引っ張られて停滞している目標の実態と乖離した一言が生成されることを構造的に防ぐ。

日をまたぐ文脈は、会話の継続によってではなく、週次要約をプロンプトに注入することで実現する。この方式であれば、注入する情報量をアプリケーション側で完全に制御できる。

**フォルダによる整理**

すべての会話をフォルダ配下に作成する。目標に紐づく会話（週次要約・総括レポート・今日の一言・月次報告・半期評価）はフォルダ名「`{接頭辞}_{目標名}`」の目標別フォルダに、目標に紐づかない会話（日次報告、仕事日次報告、およびACTIVEな目標が無い日の今日の一言）は接頭辞そのものを名前とする共通フォルダに配置する。接頭辞は設定から変更可能とする。共通フォルダをAI基盤側で削除するだけで、アプリ由来の会話を一括で解放できる。

**会話識別子の保持**

作成した会話の識別子はローカルに保持する。一覧取得APIを毎回呼び出さない。

### 8.3 メッセージ送信の指定

| パラメータ | 指定値 | 理由 |
| --- | --- | --- |
| Web検索 | 無効 | 既定値が有効のため明示指定が必須。試験対策の文脈に無関係な検索結果が混入することを防ぐ |
| ナレッジ検索 | 無効 | 本アプリはアシスタントのナレッジを使用しない |
| 親メッセージ順序 | 送信するが文脈維持には用いない（8.3.1参照） | 同一日内の複数往復における文脈維持は対話履歴の注入（8.4）で実現する |
| 画像・文書・音声 | 使用しない | MVPの範囲外 |

#### 8.3.1 親メッセージ順序に関する既知の制約（要検証）

導入したAI基盤の開発キット（NewtonX ADK v0.10.5）を実際にソースコードで確認したところ、`send_message()`のメソッドシグネチャに親メッセージ順序を指定する引数が存在せず、送信内容には常に固定値0が設定されることを確認した。バンドルされた公式ドキュメント（APIリファレンス、利用ガイド、トラブルシューティング）はすべてこのパラメータが機能する前提で書かれており、ドキュメントと実装が矛盾している。

**この制約を前提に、本アプリは以下の方針を取る。**

- AI基盤側の会話スレッド機能（親メッセージ順序による文脈継承）には依存しない
- 同一日内の複数往復における文脈維持は、本アプリが独自に保持する対話履歴（`chat_message`）を毎回のプロンプトへ全文注入する方式（8.4「対話履歴」）で実現する。この方式はAI基盤側の実装状況によらず機能する
- `ai_conversation.last_parent_order` の値は将来の開発キット改修に備えて記録は継続するが、現状は文脈維持の実効性を持たない
- 回答が出力上限で途切れた場合の継続取得（開発キット側が推奨する「終端マーカー方式」）も親メッセージ順序に依存するため、本アプリでは代わりに直前の応答本文をプロンプトに含めて「続きを出力してください」と自己完結した指示で送信する方式を取る

この制約は導入したADKのバージョン（v0.10.5）に起因するものであり、将来のバージョンアップで解消される可能性がある。解消された場合は、親メッセージ順序による文脈継承を主とし、対話履歴の全文注入を縮退時のみに用いる構成へ最適化してよい。

**アシスタントへのナレッジ登録は行わない。** アシスタントが組織内で共有される可能性があり、個人の学習記録を登録することは不適切である。

### 8.5 プロンプトの段階的縮退

**制約**

AI基盤の入力上限は明示されていない。

**方針**

プロンプトを組み立てた後、文字数が設定値を超える場合、以下の順序で情報を削減する。

| 順位 | 削減対象 | 理由 |
| --- | --- | --- |
| 1 | 古い週次要約から順に除外 | 直近ほど関連性が高い |
| 2 | 教材情報の詳細度を下げる | 締切が遠い教材を集約表示にする |
| 3 | 当日の対話履歴を古い往復から除外 | 直近の往復が最も重要 |
| 4 | 日記本文を末尾優先で切り詰める | 完全な除外は避ける |

縮退が発生した場合、その旨を画面上に控えめに表示する。利用者が「なぜ言及されない情報があるのか」を把握できるようにするためである。

**上表はAI-01（資格試験の日次報告フィードバック）専用**。AI-06（読書）・AI-08（仕事）の日次報告フィードバックは、直近記録の窓（`ai.reading_recall_recent_days`／`ai.work_recent_log_days`）より前の経過をAI-11・AI-12（週次要約、L-11で新設）が補い、①週次要約を古い週から除外→②直近記録（想起記録・業務記録）を古い日から除外→③当日対話を古い往復から除外、の3段階で縮退する（詳細はロジック・プロンプト編16.5・21.4・22.4）。AI-04・AI-07・AI-09・AI-10（総括レポート・読了レポート・月次報告・半期評価）も、対象期間のうち週次要約が既に生成済みの範囲は圧縮表現へ、まだ生成されていない直近部分は生ログのまま①週次要約を古い週から除外→②生ログを古い日から除外、の2段階＋末尾切り詰めのフェイルセーフで縮退する（詳細はロジック・プロンプト編17.5・21.4・22.4）。特にAI-10（半期評価）は最大6ヶ月分の生ログ注入となる設計のため、この週次要約による圧縮の効果が最も大きい（2026-09-15時点で識別した「対象期間の前半の実績が人事評価から漏れる」副作用への根本対応、2026-09-16実装、ロジック・プロンプト編L-11）。

### 8.7 認証

**認証方式はPersonal Access Token（PAT）を主とする。** 導入した開発キット（NewtonX ADK）の現行の公式利用ガイドは、Host（サブドメイン）とPATによる認証を標準的な方法として案内しており、ブラウザ経由のOAuth／デバイスコード認証はEntraID構成時のフォールバック経路として内部に残るのみである。当初の設計はブラウザ認証を主経路と想定していたが、公式情報にあわせて以下のとおり改める。

| 項目 | 方針 |
| --- | --- |
| 認証情報の管理 | 開発キットの仕組みに委ねる。独自の資格情報管理を実装しない。Host（例: `xxx.newton-x.net`）とPATは、設定画面（SC-11）から開発キットの設定へ反映する |
| PATの発行 | NewtonXのWeb版アカウント画面で利用者自身が発行する（本アプリからは発行できない）。設定画面に発行手順への案内を表示する |
| 起動時 | Host・PATが設定済みかを確認する。開発キットはPAT設定時、他の認証手段より優先してこれを使用する |
| 未設定・無効時 | 設定画面でHostとPATの入力を促す。フォールバックとしてブラウザ経由の認証フロー（バックグラウンドスレッドで実行）を提供するが、主経路としては使用しない |
| 認証状態の公開 | クライアントには真偽値のみを返す。PAT・トークンは送出しない |
| リダイレクト先（フォールバック時のみ） | 開発キットの既定値（ローカル8400番）を使用する。アプリケーションサーバは別ポート（8100）で起動する |

### 8.8 エラー処理

| エラー種別 | 応答コード | 画面での扱い |
| --- | --- | --- |
| 未認証・トークン期限切れ | AI_AUTH_REQUIRED | 設定画面での再認証を促すメッセージを表示 |
| タイムアウト | AI_TIMEOUT | 再送ボタンを表示。実績入力の内容は保持する |
| 通信エラー・頻度制限 | AI_ERROR | エラー内容を表示。再送ボタンを表示 |
| 会話操作の失敗 | AI_ERROR | 同上 |
| 設定不備 | AI_CONFIG_ERROR | 設定画面への遷移を促す |

**実装上の注意（タイムアウトの判定方法）**

導入した開発キットの例外クラスは `NewtonXError` / `AuthenticationError` / `APIError` / `ConfigurationError` / `FileUploadError` / `ChatError` の6種であり、タイムアウト専用の例外クラスは存在しない。通信タイムアウトも内部的に `APIError` へ一律ラップされるため、型による判定はできない。本アプリでは、呼び出し側で計測した経過時間が設定値（`ai.timeout_seconds`）を超えているか、またはエラーメッセージにタイムアウトを示す文字列が含まれるかによって `AI_TIMEOUT` を判定する。

**重要な制約**

AI呼び出しの失敗により、実績入力の内容が失われてはならない。日次報告画面では、実績と日記の入力内容をクライアント側の状態として保持し、AI応答の成否とは独立させる。

AI応答が得られない状態でも、報告の確定を許容する。AIとの対話は本アプリの中核だが、それが利用できないことを理由に記録自体が失われるのは本末転倒である。

**非エンジニア向けエラー表示の方針（2026-09-19）**

全エラーコードの画面文言は、①何が起きたか（1文）②何をすればいいか（1文）の形式に統一し、技術的なエラーコードは表示しない（データ構造編6.3参照）。教材・書籍・案件情報の削除拒否（実績が紐づく場合）はエラーコード自体を増やさず、レスポンスの`details`に理由を含めて画面側で文言を出し分ける。

ドメイン例外・入力検証エラー以外の未分類の例外（バグ等の想定外エラー）も、必ず`INTERNAL_ERROR`として本アプリ標準の応答形式で返す（API層の最終防波堤のハンドラ）。フロントエンドにも画面全体のエラー境界を設け、予期しない描画エラーで画面が真っ白になることを防ぐ。トースト表示は、技術的な詳細（エラーコード等）を折りたたみで残せるようにし、開いている間は自動で消えないようにする（サポートへの報告に使える）。

### 8.9 呼び出し頻度の制御

頻度制限が存在する可能性があるため、連続する呼び出しの間隔に下限を設ける。既定値は2秒とする。

週次要約の遡及生成では複数回の呼び出しが連続するため、この制御が特に重要となる。

| 周回整合 | 予定周回数を、既に完了した周回数を下回る値に変更できない |
| 完了量 | 累積完了量が総作業量を超える入力を警告する。保存は許容する（見積もり誤差の吸収のため） |
| リソース | 配分時間は0以上の整数（分）とする。スロットごとの配分合計がそのスロットの連続時間を超える保存を拒否する（NT-04）。ただしスロット側の短縮・削除による事後的な超過は警告のみとし保存を許容する（NT-09） |
| 時間表示 | 分から時間へ換算して表示する箇所は、小数第2位以下を切り捨てて小数第1位まで表示する（四捨五入しない）。算出には常に分（整数）を用いる |
| 遡及入力 | 前日を超える過去日への入力を拒否する |
| 変更不可 | 報告済の日およびクローズ済の目標への更新要求を拒否する |
| 時刻 | 1日の境界時刻は0時から11時の範囲とする |
| 読書：書籍 | 総ページ数は必須とし、1以上の整数とする |
| 読書：想起 | 想起本文は必須、現在ページは0以上・総ページ数以下の整数とする（任意入力） |
| 読書：冊数 | 1目標に対して書籍を2件以上登録できない |
| 仕事：案件情報 | 想定業務内容・着手日は必須。取引先・案件の呼称は任意 |
| 仕事：業務記録 | 業務内容の自由記述は必須（数値項目は持たないため他の数値バリデーションは適用対象外） |
| 仕事：案件数 | 1目標に対して案件情報を2件以上登録できない |

### 13.4 スケジュール状態アイコン（UI-02〜UI-04）の適用範囲

完了予測日と締切の乖離（`overrun_days`、`speed_service.compute_forecast_date`）は、教材・負荷プロファイルを持つ資格試験目標（`GoalCategory.EXAM`）にのみ存在する算出値である。読書目標・仕事目標は日次ノルマ・実効速度・完了予測日を持たず（R-71・R-74、6.1）、対応する目標カード表示項目も別内容（残日数・直近記録日・連続記録日数等、DSH-06・DSH-07）である。

したがって、UI-02（遅延）・UI-03（順調）・UI-04（前倒し）は**資格試験目標にのみ表示し、読書・仕事目標には表示しない**。読書・仕事目標のカードにこれらのアイコンを出す設計にしないよう、実装時に横展開注意（対象カテゴリのガードを1箇所に集約し、DSH-06・DSH-07相当のカードから誤って参照しないこと）。

分岐基準は`overrun_days`の符号のみを用いる（>0＝遅延、==0＝順調、<0＝前倒し）。閾値によるあそびは設けない。

### 13.5 休憩バッファアイコン（UI-07）の適用範囲

`DayType.BUFFER`はカレンダー・日種別設定（`calendar_service.resolve_day_types`）に基づく。リソース配分（スロット）を持つ資格試験目標（必須）・読書目標（任意）ではバッファ日の概念が意味を持つが、仕事目標はリソース配分の対象外（R-74、1.1改18）のため、UI-07は**資格試験・読書目標にのみ表示し、仕事目標には表示しない**。

### 13.6 目標達成アイコン（UI-11）の判定基準

目標達成の判定基準はカテゴリごとに異なる。

| カテゴリ | 判定基準 | 根拠 |
| --- | --- | --- |
| 資格試験（EXAM） | 全科目の`exam_result.result`が`PASS`の場合のみ達成扱い。1科目でも`FAIL`が含まれる場合、または結果未登録の科目が残る場合は達成扱いにしない | 仕様書上「資格試験合格登録後」に使うアイコンであり（アイコンセット仕様書13章）、`GoalStatus.CLOSED_WITH_RESULT`は合否を区別しないため（`goal_service.close_goal`、S-12） |
| 読書（READING） | `GoalStatus.CLOSED_WITH_RESULT`（`book_service.complete_book`による読了完了）を達成扱いとする | 読了そのものが目的達成であり、合否のような二値判定を持たないため |
| 仕事（WORK） | `GoalStatus.CLOSED_WITH_RESULT`（`close_goal`の`with_result=True`、成果を伴う終了）を達成扱いとする | `with_result`は「納品等の成果を伴う終了」を明示的に指定するパラメータであり、既に成功を意味するため（`goal_service.close_goal`） |

資格試験のみ、`CLOSED_WITH_RESULT`だけでは判定できない（S-12、未解消）。バックエンドに合否判定込みの算出フィールドを追加してから実装する。

### 13.7 保存中・削除中オーバーレイ（UI-05・UI-06）の対象操作範囲

**実装方式**：フロントエンドはTanStack Queryの`useMutation`の`meta.overlay`（`'saving' | 'deleting'`）にオーバーレイ種別を持たせ、`LoadingOverlay`（`frontend/src/components/LoadingOverlay.tsx`）が`useMutationState`でミューテーションキャッシュを横断監視して自動表示する。呼び出し元は`meta`を付けるだけでよく、表示・非表示の手動制御を各画面に書かない（DRY、横展開漏れの防止）。

**対象範囲（13.2策定時からの拡張）**：13.2策定時点では「保存系・削除系の狭義CRUD」のみを対象と定義したが、実装時の全`useMutation`呼び出し（60箇所）の横断点検により、目標の状態遷移（開始・一時停止・再開・クローズ・読了完了・アーカイブ・アーカイブ解除・教材/メンバーの非活性化・受験日確定）・AI接続確認・エクスポートのプレビュー生成・バックアップの作成/復元も、ユーザーの明示操作から応答まで時間を要し多重クリックが起こりうる点で保存系と性質が変わらないと判断し、対象に含めるよう拡張した。UI-05・UI-06は、目標のカテゴリを問わず、**データを書き込む・外部（AI基盤・開発キット）と通信する全ての`useMutation`呼び出し**に適用する（カテゴリによる出し分けを行わない）。

**saving / deletingの判定基準**：物理削除（DELETE）・論理削除（アーカイブ、カレンダー日種別オーバーライドのクリア）は`deleting`とする。それ以外（作成・更新・状態遷移・非活性化・復元・生成AI疎通・接続確認・エクスポート・バックアップ）は、対象を破壊的に取り除く操作ではないため`deleting`ではなく`saving`とする。特に以下は「削除」の語感があるが`saving`に区分する（削除中アイコンの表示は「対象が失われる」ことを示すため、復元系の操作に出すと利用者に誤解を与える）。

| 操作 | 区分 | 理由 |
| --- | --- | --- |
| 目標のアーカイブ解除（`unarchiveGoal`） | saving | アーカイブ（`deleting`）の逆操作であり、対象を復元する。削除中アイコンを出すと「消えてしまう」という誤った印象を与える |
| 教材・チームメンバーの非活性化（`deactivateMaterial`/`deactivateWorkMember`） | saving | 物理削除ではなく状態フラグの更新であり、いつでも編集し直せる |
| プロンプトテンプレートの初期値リセット（`resetPromptTemplate`） | saving | 既定値を書き込む更新操作であり、テンプレート自体は削除されない |
| バックアップからの復元（`restoreBackup`） | saving | データを書き込む操作であり、個別レコードの除去ではない |
| カレンダー日種別オーバーライドのクリア（`clearDayType`） | deleting | その日の個別設定（レコード）を取り除き、曜日既定値に戻す論理削除に相当する |

対象画面・操作の詳細な一覧（ファイルパス:行番号）は実装フェーズ分割計画書の該当フェーズに記載する。
