# CODING_RULES.md — コーディングルール

本ドキュメントは `dry-reviewer` / `style-reviewer` / `label-checker` エージェントが判定基準として参照する
**唯一の情報源（Single Source of Truth）** です。CLAUDE.md や各エージェント/スキルにはルールの詳細を複製せず、
本ファイルへの参照のみを記載してください（重複記述はDRY違反であり、無駄なトークン消費の原因になります）。

## 最重要の2原則

### ① DRYの原則（同じ処理を2箇所に書かない）

同じ処理をコピペすると「片方だけ直して直し忘れる」事故が起きる。共通処理は1つの関数にまとめて呼び出す。

- **判断の目安**: 同じような処理を2回書きそうになったら、コピペ前に「共通関数にできないか」を考え、既に似た処理がないか軽く探す
- **良い実装例**: <!-- 例: src/utils/storage.js の readJSON / writeJSON -->
- 定数・ID・設定値の直書きも対象（値の重複＝ロジックの重複と同じリスク）
- 検出は `dry-reviewer` エージェントが担当

### ② ゼロハードコーディング（画面の文字・値を直接コードに書かない）

ラベルや文言・画面ID等の「コード上の名前」を1箇所にまとめ、そこから参照する。

- 検出は `label-checker` エージェントが担当（対象: ユーザー向け文字列）
- 定数・IDの重複は `dry-reviewer` エージェントが担当（対象: コード上の名前の重複）

## テストカバレッジ

追加実装・変更を行う場合は、必ずテストコードを実装する。例外処理（想定外エラーのフォールバック等）を除き、
カバレッジ100%を目指す。

- **判断の目安**: 新しい分岐（if/switch/早期return等）を追加したら、その分岐を通るテストケースを追加する
- **除外可**: 例外処理・想定外エラーのフォールバック等、意図的に発生させにくい異常系は対象外としてよい（除外理由をテストのdescribe/コメントに明記する）
- **機械的に計測する**: フロントエンドは `npm run test`（Vitest + v8）が閾値100%未満で失敗する。バックエンドは `pytest --cov` が計測のみを行い、100%の強制は `--cov-fail-under=100` を渡す側で行う（リリースゲート `build_package.run_tests()` と Stop Hook のデプロイチェックが渡している。`pyproject.toml` の `addopts` に入れないのは、部分実行が常に閾値割れで失敗するのを避けるため）。計測対象・除外範囲とその理由は `OPERATIONS.md`「フロントエンドのテストとカバレッジ」、リリース時に実行されるテストは同「リリース時に必ず実行されるテスト」を参照
- **フロントの分岐は `.ts` へ切り出す**: 判定ロジックは純粋関数として `.ts` に置き、コンポーネントは描画と通信に専念させる。`.tsx` も `@testing-library/react` で描画テストを書けるが（環境は jsdom）、分岐を純粋関数側に寄せたほうが検証が速く安定する。「押した結果どう送信されるか」までを守りたいものは `.tsx` 側もテストし、カバレッジ対象に個別追加する
- 検出は `test-coverage-reviewer` エージェントが担当

### DBマイグレーションのテスト（既存データに対する安全性）

既存テーブルへの列追加・変更を伴うAlembicマイグレーション（`backend/alembic/versions/`）
を追加する場合、そのテーブルに既存データがある状態で当該マイグレーションを適用し、
エラーにならず・データが保持されることを検証するテストを必ず追加する。空のDBに対する
`upgrade head`だけでは検出できない不具合があるため（下記理由）、通常のテストカバレッジ
とは別に明記する。

- **理由**: 2026-08-29、`exam_subject.passing_score_type`列追加マイグレーションが、
  SQLiteのbatch mode（`env.py`の`render_as_batch=True`）でのテーブル再作成時に
  `server_default`を失い、既存行のコピーがNOT NULL制約違反になる不具合を含んだまま
  配布された。既存のテスト（`conftest.py`のセッション単位フィクスチャ）は常に空DBへ
  `upgrade head`するだけで、既存データに対する適用は一度も検証していなかったため
  検出されなかった
- **判断の目安**: 新規テーブルの`create_table`のみのマイグレーションは対象外（コピー元
  データが存在しないため、この種の不具合は起きない）。既存テーブルへの`add_column`/
  `alter_column`等が対象
- **書き方**: `backend/tests/migration_helpers.py`（`upgrade_to`/`drop_alembic_version_table`）
  を使い、対象マイグレーションの1つ前のリビジョンまでDBを構築 → 対象テーブルへ生SQLで
  代表的な行を挿入 → 対象リビジョンへ`upgrade` → エラーが起きないこと・挿入した行が
  保持されていることを検証する（`backend/tests/test_bootstrap.py`の
  `test_upgrade_database_schema_migrates_legacy_unversioned_database_without_data_loss`
  を参考にする）

## 保守性（複雑度）

DRY違反（重複）とは別に、単一のファイル/関数が肥大化・複雑化すること（いわゆるスパゲッティコード）を防ぐ。

- **目安**: 1関数は1画面に収まる程度（大まかな目安として100行以内）、ネストは3階層以内
- **単一責任**: 1つの関数/コンポーネントが担う責務は1つに絞る。「〜と〜をする」関数は分割を検討
- **機械的検知を優先**: 循環的複雑度（cyclomatic complexity）や関数行数の上限は、可能な限りLintルールで機械的に検知する。LLMレビューの主観判断より優先する
- **フロントエンドの設定**: `frontend/.oxlintrc.json` で `max-lines-per-function`（100行。コメント・空行は除外）と `max-depth`（3階層）を**warn**で有効化している。`npm run lint` に既存の超過分が並ぶが、これは「直すべき負債の一覧」であり、新しく増やさないための歯止めとして使う。テストファイルは `describe` のコールバックが1関数として数えられてしまうため `overrides` で対象外にしている
- **超過を解消するときの手順**: 画面の分割は振る舞いを壊しやすい。`frontend/src/pages/DailyReportPage.tsx` では ①現状の振る舞いを固定する描画テストを先に書く → ②意図的に不具合を注入してテストが落ちることを確認する（落ちなければ網が不十分） → ③分割する、の順で進めた。テストの無いコンポーネントを行数だけを理由に分割しないこと
- 検出は `dry-reviewer` エージェントが重複コードと合わせてレビューする（機械的Lintの補完）

## 置き場所ルール

| 何を置くか | 置き場所 |
|---|---|
| 画面のラベル・ボタン文言 | `frontend/src/locales/ja.json` |
| 画面ID・APIパス等「コード上の名前」 | `backend/app/constants/`、`frontend/src/constants/` |
| キャッシュキー（TanStack Query） | `frontend/src/constants/queryKeys.ts`（取得と無効化が必ず同じキーを指すよう1箇所へ集約。前方一致に依存する組み合わせも同ファイルに明記） |
| 複数画面で使う共通処理 | `backend/app/services/`（業務ロジック）、`frontend/src/hooks/`（フロント共通処理） |
| 複数画面で使う共通部品 | `frontend/src/components/` |
| 閾値・パラメータ | `app_setting` テーブル（画面から変更可能。ソースコードへの直接記述を禁止） |
| プロンプト文面 | `prompt_template` テーブル（画面から変更可能。ソースコードへの直接記述を禁止） |
| 1画面でしか使わない処理・値 | その画面のファイル内でOK（無理に切り出さない） |

詳細なディレクトリ構成は設計書 データ構造編 第8章を参照。

## 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| テーブル名 | 単数形スネークケース | `daily_record` |
| 列名 | スネークケース | `amount_completed` |
| APIパス | 複数形ケバブケース | `/api/v1/load-profiles` |

- 省略しすぎない名前にする（例: `d` より `data`、`data` より `userProfile`）

## コメントの書き方

1. ファイル先頭に役割と背景を書く（仕様書の該当番号があれば添える）
2. 専門用語は使う場所でカッコ書きの説明を添える
3. 公開関数には引数・返り値・使用例を書く
4. 「なぜこうしたか」は省略しない（不自然・遠回りに見えるコードほど厚めに。ライブラリ不具合の回避策などが典型例）
5. コードを読めば分かることは最小限でよいが、迷ったら書く方が安全（未経験者基準で判断）

検出は `style-reviewer` エージェントが担当。

## 秘密情報の扱い

パスワード・APIキー等は `.env` に書き、コードに直書きしない。`.env` はGit管理対象外。
新しい環境変数を追加したらチームに共有する。

詳細な多層防御の仕組み（Hook / Agent）は CLAUDE.md「コミット前チェック」を参照。
