## 1. 本文書の目的と範囲

本文書は、ミチナリのデータ構造、永続化方式、API構成、およびディレクトリ構成を定義する。

算出ロジックの数式定義およびプロンプト設計は「設計書 ロジック・プロンプト編」に記載する。

## 2. 技術構成

| 層 | 採用技術 | 選定理由 |
| --- | --- | --- |
| フロントエンド | React + TypeScript + Tailwind CSS | 開発者の習熟度 |
| バックエンド | FastAPI | AI基盤の開発キットがPython製であり、同一プロセスで動作可能 |
| ORM | SQLAlchemy 2.0 | 集計クエリの表現力。長期メンテナンスの安定性 |
| マイグレーション | Alembic | 段階的なスキーマ拡張を前提とするため必須 |
| データベース | SQLite | 単一利用者、ローカル動作。将来のPostgreSQL移行を阻害しない |

**ORM選定における除外検討**

Prisma Client Python は開発が終了しているため採用しない。SQLModel は記述量で優位だが、本アプリの中核である集計クエリで SQLAlchemy の API に降りる必要が生じ、二重の学習コストが発生するため採用しない。

**SQLite使用上の制約への対応**

| 制約 | 対応 |
| --- | --- |
| ALTER TABLE の制限 | Alembic の batch_alter_table を使用する |
| 日付型が存在しない | DATE型は ISO 8601 文字列として保存し、SQLAlchemy の Date 型で扱う |
| 真偽値型が存在しない | Boolean型は整数として保存し、SQLAlchemy の Boolean 型で扱う |
| 外部キー制約が既定で無効 | 接続時に `PRAGMA foreign_keys = ON` を実行する |

**起動ポート**

AI基盤の開発キットは、認証フローのフォールバック経路（PAT未設定時のブラウザ認証）でローカルの8400番ポートを使用する設定を既定に持つ。主経路のPAT認証ではこのポートは使用されないが、フォールバック経路を確実に動作させるため、アプリケーションサーバは引き続き8400番以外で起動する。既定値は8100とする。

## 3. 設計方針

### 3.1 派生値を保存しない

以下は一切保存せず、参照時に算出する。これが本アプリの中核的な設計判断である。

| 派生値 | 算出根拠 |
| --- | --- |
| 日次ノルマ | 残量、残計画日数、負荷係数 |
| 総作業量 | 総量、予定周回数 |
| 残量 | 総作業量、実績の累計 |
| 現在周回 | 総量、実績の累計 |
| 実効速度 | 実績の投下時間と完了分量（周回別） |
| 必要速度 | 残量、残計画日の利用可能時間 |
| 完了予測日 | 残量、実効速度、計画日の分布 |
| バッファ消費率 | バッファ日の実績有無 |

日次ノルマを保存しないことにより、未達分の繰り越し処理が不要になる。残量を残計画日で再配分する式が毎日評価されるため、負荷の平準化が構造的に成立する。

### 3.2 基準値のみ履歴として保存する

警告判定（日次ノルマが初期ノルマの一定倍率を超えたか）には比較対象が必要である。この基準値は `plan_baseline` テーブルに履歴として保存する。

リプラン実施時に新しい基準行を追加することで、リプラン後は新しい計画が基準となり、過去の乖離を引きずらない。

**この履歴は、総括レポートの分析根拠としても用いる。** いつ、何回、どの契機で計画を修正したかという情報は、合否要因の分析において最も重要な材料である。

### 3.3 不変性の担保

日次報告および学習実績は、確定後の更新をアプリケーション層で拒否する。データベース制約では表現せず、サービス層のガードとして実装する。

### 3.4 外部識別子の保持

AI基盤側に作成された会話の識別子はローカルに保持する。一覧取得APIによる検索を毎回行わない。これは通信回数の削減と、頻度制限への配慮による。

      │      │
      │      └─< material_subject >─┐
      │                              │

      │      │

      │

### 4.2 関連の定義

| 親 | 子 | 多重度 | 削除時動作 |
| --- | --- | --- | --- |
| goal | exam_subject | 1対多 | CASCADE |
| goal | material | 1対多 | CASCADE |
| goal | load_profile | 1対多 | CASCADE |
| goal | weekly_summary | 1対多 | CASCADE |
| goal | goal_retrospective | 1対多 | CASCADE |
| goal | ai_conversation | 1対多 | CASCADE |
| goal | book | 1対1（goal_idにUNIQUE制約） | CASCADE |
| goal | work_assignment | 1対1（goal_idにUNIQUE制約） | CASCADE |
| exam_subject | exam_result | 1対1 | CASCADE |
| material | exam_subject | 多対多（material_subject） | CASCADE |
| material | plan_baseline | 1対多 | CASCADE |
| material | study_log | 1対多 | RESTRICT |
| book | reading_log | 1対多 | RESTRICT |
| work_assignment | work_log | 1対多 | RESTRICT |
| daily_record | study_log | 1対多 | CASCADE |
| daily_record | reading_log | 1対多 | CASCADE |
| daily_record | work_log | 1対多 | CASCADE |
| daily_record | chat_message | 1対多 | CASCADE |
| daily_record | record_comment | 1対多 | CASCADE |
| resource_slot | resource_slot_weekday | 1対多 | CASCADE |

`book` から `reading_log` への削除は `material` から `study_log` への削除と同じ理由でRESTRICTとする。想起記録が存在する書籍の削除は、記録の消失を伴うため許可しない。

`work_assignment` から `work_log` への削除も同じ理由でRESTRICTとする。業務記録が存在する案件情報の削除は、記録の消失を伴うため許可しない（要件定義書6.11）。

`material` から `study_log` への削除は RESTRICT とする。実績が存在する教材の削除は、実績の消失を伴うため許可しない。教材を除外したい場合は無効化フラグを用いる。

**アーカイブ済み goal の完全削除時の例外**：`DELETE /goals/{id}/archived` で `cascade_study_logs=true` を指定した場合に限り、サービス層（`goal_service.delete_archived_goal`）が DB の RESTRICT 制約に反しない手順で `study_log`／`reading_log`／`work_log`（`_cascade_delete_activity_logs`）を先行削除する。

1. 対象 goal 配下の全 material／book／work_assignment に紐づく `study_log`／`reading_log`／`work_log` を取得する
2. 各ログについて、削除後に親 `daily_record` が完全に空（他 goal の study_log・reading_log・work_log、chat_message、record_comment、日記本文のいずれも存在しない）になるかを判定する
3. ログを削除する。手順2で完全に空になると判定された `daily_record` のみ、続けて物理削除する（他 goal のデータが1件でも残る `daily_record` は保持する）
4. `session.delete(goal)` を実行し、上表の CASCADE 定義済みの子（exam_subject・material・load_profile・weekly_summary・goal_retrospective・ai_conversation・book・work_assignment とそれぞれの子）を連鎖削除する

`cascade_study_logs=false`（既定は画面上ON、明示的にOFFにした場合）の場合は、対象 goal 配下のいずれかの material に `study_log` が1件でも存在する時点で削除全体を中断し、エラーを返す（通常の `RESTRICT` 挙動のまま）。

**アシスタント選定について（2026-08-23、実機確認済み）**

用途ごとに異なるアシスタントを既定値とする。全用途を単一のアシスタントに固定すると、要約向きのタスクと分析・提案向きのタスクの双方に同じ特性のモデルを使うことになり最適でないため、`get_assistants()`で取得できる説明文を根拠に用途別へ分離した。

| 用途 | 既定アシスタント | 選定理由 |
| --- | --- | --- |
| DAILY_FEEDBACK（日次報告フィードバック） | GPT-5.4（高性能） | 「複雑なタスクの整理や具体的な提案に適しています」。状況解釈・成長の指摘・具体的行動提案・計画提案という17.2の要求に合致 |
| WEEKLY_SUMMARY（週次要約） | Gemini 2.5 Flash（高速） | 「日常的な要約や調べものに適しています」。起動時に複数週分を逐次生成するため速度も重視 |
| DAILY_MESSAGE（今日の一言） | GPT-5.4-mini（高速） | 「回答速度が速く、情報整理や提案をバランスよくこなせます」。ダッシュボードで非同期表示される軽量な生成に適する |
| GOAL_RETROSPECTIVE（総括レポート） | GPT-5.4（高性能） | DAILY_FEEDBACKと同様、低頻度・高品質重視のため同一アシスタントを採用 |

| GPT-4o（高性能） | `8d0bbf4e-79c1-4f9e-9e9a-a034b784b11a` | 使用不可（404で確認済み） |

**制約**

- `status` が ACTIVE の全 goal について、`resource_ratio` の合計が 1.0 を超えないこと。アプリケーション層で検証する。**この合計計算に `category=READING` および `category=WORK` の goal を含めない**（要件定義書 R-64、R-74）
- PAUSED および CLOSED 状態の goal は、リソース比率の合計計算に算入しない。ただし `resource_ratio` の値自体は保持し、復帰時の要求値として用いる
- `archived_at` を設定できるのは `status` が `ACTIVE` 以外（`DRAFT` / `PAUSED` / `CLOSED_WITH_RESULT` / `CLOSED_WITHOUT_RESULT`）の場合のみ。アプリケーション層で検証する（仕様書7.1.1、要件定義書R-61）
- 物理削除（`DELETE /goals/{id}/archived`）は `archived_at` が設定済みの goal のみ許可する
- `archived_at` が設定済みの goal は、開始（`activate_goal`）・再開（`resume_goal`）・下書きの即時削除（`delete_goal`）を許可しない。先にアーカイブ解除（復元）が必要（仕様書7.1.1）
- `category` は作成後の変更を許容しない。種別を変えたい場合は目標を作り直す（仕様書6.2）

**読書目標（category=READING）のクローズ**

読書に固有の `BookStatus` は設けない。読了は `status='CLOSED_WITH_RESULT'`、中断は `status='CLOSED_WITHOUT_RESULT'` として、資格試験と同じ `GoalStatus` をそのまま用いる。ただし読書では `exam_result` を作成しない（`CLOSED_WITH_RESULT` は「合否結果を伴うクローズ」ではなく「目標に対する成果を伴うクローズ」という意味に拡張して用いる）。クローズ時に生成する `goal_retrospective` が、資格試験では総括レポート、読書では読了レポートとして機能する（17.5、17.7参照）。

**仕事目標（category=WORK）のクローズ**

仕事目標も固有のステータス列は設けず、資格試験・読書と同じ `GoalStatus` をそのまま用いる。1目標＝1案件（プロジェクト）に対応するため、案件が終了すればクローズし、次の案件は新しい goal を作成する（要件定義書R-72）。納品等の成果を伴う終了は `status='CLOSED_WITH_RESULT'`、中止・打ち切りは `status='CLOSED_WITHOUT_RESULT'` とする。読書と同様に `exam_result` は作成しない。複数の仕事目標を同時に進行中とすることを妨げない（既存の複数目標並行の仕組みをそのまま用いる）。

仕事目標は読書と異なり、クローズ時に「読了レポート」に相当する1回きりのレポートは生成しない。かわりに、進行中の間は月次・半期という周期で `goal_retrospective` を生成し続ける（`period_type`／`period_key`、5.4「goal_retrospective（総括レポート／読了レポート／定期報告）」参照）。クローズ操作自体は、進行中の月次・半期報告の生成契機とは独立している。

**締切の自動導出**

- 教材と科目の紐付けが変更されたとき
- 紐づく科目の受験日が変更されたとき

自動導出値を保存するのは、締切がガントチャート表示や締切超過判定など多数の箇所で参照されるためである。派生値を保存しない原則の例外にあたるが、再計算契機が限定的かつ明確であるため許容する。

**daily_record（日次記録）**

| 列名 | 型 | 制約 | 説明 |

日次記録は日付単位で一意とする。目標単位ではない。複数目標が同時進行する場合も1日1レコードとし、実績は study_log 側で教材ごとに、日記は daily_goal_diary 側で目標ごとに保持する。

確定状態（`*_record_state`/`*_reported_at`）はカテゴリ（EXAM/READING/WORK）ごとに独立した3組の列で保持する（1.1（改16）、仕様書1.1（改13））。従来は`record_state`/`reported_at`の単一組だったため、1カテゴリを確定すると同日の他カテゴリも一括で報告済になっていた（資格試験・読書・仕事の目標を同時進行する利用者が、他カテゴリの入力・確定を継続できなくなる問題）。値がNULLのカテゴリは、その日一度もそのカテゴリを操作していないことを表す。カレンダー・ダッシュボード等が必要とする日単位の単一状態は、`record_service.aggregate_record_state`が3カテゴリの値から都度算出する派生値であり、列としては保持しない（未着手カテゴリは判定から除外し、着手した全カテゴリが報告済なら報告済、1つでも進捗のみ登録済があれば進捗のみ登録済とする）。

`GET /records/{date}/quota`（QuotaItemRead）・`GET /dashboard`（TodayQuotaEntryRead）が返す教材別の日次ノルマ一覧には、表示専用の派生値として `goal_id`・`goal_name` を含む（DBには保存しない。`material.goal_id` から都度算出する）。複数目標が同時進行する日、ダッシュボードSC-01はこの値をもとに目標ごとに一覧をグルーピング表示する（未決事項L-04参照）。日次報告SC-06は同じ値を用いて画面上部の目標タブの選択対象を絞り込み、選択中の1目標分のみを表示する（仕様書6.5）。

`exam_record_state`/`reading_record_state`/`work_record_state`は、対応するカテゴリがREPORTEDの場合、そのカテゴリに関連する study_log・reading_log・work_log・daily_goal_diary の更新を拒否する（他カテゴリが未確定であれば引き続き更新できる）。

`record_date` は、設定された1日の境界時刻に基づいて決定される論理的な日付である。

EXAM・READINGでは、再生成を許容するため goal に対して複数レコードを持てる構造とする（最新のものを既定で表示、匿名化版は別レコード）。

**読書目標での流用**：新規テーブルを設けず、本テーブルをそのまま「読了レポート」として用いる（`goal.category=READING`）。生成契機・匿名化・再生成の仕組みは資格試験の総括レポートと共通。内容の違いはプロンプト（AiPurpose.GOAL_RETROSPECTIVE_READING、ロジック・プロンプト編17.7）にのみ起因する。`period_type`以下の追加列はNULLのまま用いない。

**仕事目標での流用（period_type以下の追加列）**：仕事目標も新規テーブルを設けず、本テーブルを「月次報告」「半期評価」の双方に流用する（`goal.category=WORK`）。読書との違いは、クローズ時の1回きりの生成ではなく、案件が進行中の間、月次・半期という周期で生成し続ける点にある（要件定義書6.11「定期報告型」）。同一goalに対し`period_type`／`period_key`の異なる複数レコードが並存する（例：2026-08分の月次報告、2026-09分の月次報告、2026-H1の半期評価が同一goalに同時に存在しうる）。

**WORKの行は、EXAM／READINGと異なり「1期間につき1行のみ」を保つ**（`is_anonymized=false`の行に限る。匿名化版は別途、エクスポート時に都度生成する）。月次報告は監査目的の履歴ではなく随時修正しうる実務文書であるという性質上、再生成・利用者による編集のいずれも既存行への上書き（`target_goal_text`以下の構造化列を更新し、そこから`body`を再組み立てし、`edited_at`を編集時のみ設定）として扱い、EXAM／READINGのように新規レコードを追加しない。これによりアプリ側は常に「そのgoalのその期間の行は高々1件」を前提にでき、`goal_id`・`period_type`・`period_key`・`is_anonymized`の組み合わせで一意に1行を特定できる。

**制約**：`goal_id` と `period_type` と `period_key` と `is_anonymized` の組み合わせは、WORKでは常に一意（アプリケーション層でupsertとして扱う）。EXAM／READINGでは`period_type`・`period_key`が共にNULLであるため、この組み合わせは目標ごとに複数行が該当し、一意制約の対象外とする（従来どおり無制限に再生成できる）。

**「最新の総括レポートを取得する」ロジックの拡張**：既存の`get_latest_retrospective`（goal_idと`is_anonymized`のみで絞り込み、`generated_at`降順で先頭を返す実装）は、`period_type`／`period_key`の指定がある場合はその条件でも絞り込めるよう拡張する（例：「このgoalの2026-09分の月次報告」を取得する用途。WORKでは該当行が高々1件のため実質的に完全一致の取得となる）。指定がない場合は従来どおり`period_type IS NULL`のレコード（EXAM総括レポート・READING読了レポート）を対象とする。実装はPhase22（仕事AI連携）で行う。

### 5.5 AI連携系

**ai_conversation（会話識別子）**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| goal_id | INTEGER | NULL, FK → goal.id | 日次報告フィードバックは複数目標にまたがりうるためNULL可。今日の一言はACTIVEな目標が無い日のみNULL（それ以外は目標ごとに独立した会話を持つ、未決事項L-04） |

**設計意図**

### 5.8 認証情報の保管

**方針：AI基盤の開発キットが提供する仕組みに委ねる。**

開発キットは、設定に基づきPAT（Personal Access Token）およびトークンをファイルとして管理する機能を備えている。アプリケーション側で独自の資格情報管理を実装しない。

**認証方式はPATを主とする。** 開発キットの現行の公式利用ガイドは、Host＋PATによる認証を標準の方法として案内している。ブラウザ経由のOAuth／デバイスコード認証（EntraID）は、開発キット内部にフォールバック経路として残るのみであり、PATが設定されていれば優先して使用される。

| 項目 | 方針 |
| --- | --- |
| PAT・トークンの保存 | 開発キットの設定に従う（`~/.newtonx/config.json` 等）。`app_setting` には保存しない |
| PATの入力 | 設定画面（SC-11）でHostとPATを入力すると、開発キットの設定へ反映する。Hostは`app_setting: ai.host`にも保存し、設定画面の表示値と一致させる（PATは`app_setting`へ保存しない） |
| 保存先パス | 開発キットの既定値を使用する。設定画面に表示のみ行う |
| 起動時の確認 | Host・PATが設定済みかを確認し、認証済みとして扱う |
| フォールバック認証 | PAT未設定・無効時のみ、設定画面からブラウザ経由の認証フローを実行できる |
| クライアントへの公開 | 認証状態の真偽値のみを返す。PAT・トークンは送出しない |

**v1.0からの変更理由**

v1.0では独自にOS資格情報ストアへ保管する方針としていたが、開発キットが独自にPAT・トークンを管理する仕様であるため、二重管理は認証状態の不整合を招く。開発キットの仕組みに一本化する。

**v1.1（本改訂）での変更理由**：当初はブラウザ経由のOAuthフローを認証の主経路として設計していたが、実際に導入した開発キットの公式利用ガイドを確認した結果、PATが現行の標準的な認証方式であることが判明したため、主経路をPATに改めた。

**フォールバック認証フローの実行方式**

ブラウザ経由の認証フローは起動して待機するため、APIリクエストのスレッドをブロックする可能性がある。バックグラウンドスレッドで実行し、クライアントは認証状態をポーリングして完了を検知する。

いずれも`goal_retrospective`（`period_type`／`period_key`で期間を区別、WORKでは1期間1行）を読み書きする。既存の`POST /goals/{id}/retrospective`（EXAM/READING専用の総括レポート・読了レポート生成エンドポイント）はWORK目標に対してはVALIDATION_ERRORで拒否する。読書がPhase15時点で暫定的に経由した拒否ガード（後にGOAL_RETROSPECTIVE_READINGの実装で解消）と似た挙動だが、仕事目標では月次・半期という別エンドポイントを新設するため、この拒否は恒久的な仕様である点が読書と異なる（`/retrospective`はクローズ時1回のレポートを前提とした設計であり、周期的に生成し続けるWORKの月次・半期報告とは呼び出しの意味が異なるため統合しない）。

**行が存在しない場合の扱い（初回利用者への配慮）**：`target_goal_text`は前期の`next_goal_text`を複製して埋めるため、前期の行が存在しない状態（案件開始直後の初回）でPOSTすると、AIが達成度を判定する対象を持たない（`achievement_score`はNULLのまま、生成される本文にも「比較対象となる前期の目標が無いため今回は評価対象外」と明記する。ロジック・プロンプト編22.6参照）。この状態で運用を続けたくない場合、利用者は`PATCH /goals/{id}/monthly-report?period={前期のperiod_key}`を**POSTで生成する前に**呼び出し、存在しない前期の行を新規作成した上で`next_goal_text`のみ手動入力できる（PATCHは対象行が無い場合、`body`等の生成専用列を空のまま行を新規作成する。この行はAI生成を経ていないため`generated_at`は作成時刻、`edited_at`も同時刻を設定し、いずれもNULLにはしない）。

### 7.3 匿名化の処理

| 対象 | 処理 |
| --- | --- |
| 日記本文 | 出力から除外する |
| AI対話履歴 | 出力から除外する |
| 週次要約 | 業務・家庭に関する記述を除外するようAIに指示して再生成する |
| 総括レポート | 個人的事情への言及を避けるようAIに指示して再生成する |

匿名化版の週次要約および総括レポートは、それぞれ別レコードとして保持する。元の版は削除しない。

**読書目標（category=READING）の場合**：「日記本文」は想起記録（`reading_log.recall_body`）に読み替えて出力から除外する。週次要約は存在しないため対象外。「総括レポート」は読了レポートに読み替え、同様に個人的事情への言及を避けるようAIに指示して再生成する。

**仕事目標（category=WORK）の場合**：「日記本文」は業務記録（`work_log.body`）に読み替えて出力から除外する。週次要約は存在しないため対象外。「総括レポート」は月次報告・半期評価（`retrospectives`の各要素）に読み替え、対象goalに紐づく全件を、それぞれ個人的事情への言及を避けるようAIに指示して再生成する。

### 8.1 責務分割の原則

| 層 | 責務 | 禁止事項 |
| --- | --- | --- |
| api | リクエスト受付、スキーマ検証、サービス呼び出し | 業務ロジックの記述 |
| services | 業務ロジック、算出、状態遷移の検証 | HTTPに関する知識 |
| models | データ構造の定義 | 業務ロジックの記述 |
| ai | AI基盤との通信、プロンプト組み立て、会話管理 | 業務判断 |

### 8.2 定数管理の原則

| 対象 | 配置先 |
| --- | --- |
| UI文言 | frontend/src/locales/ja.json |
| 列挙型の値 | backend/app/constants/、frontend/src/constants/ |
| 閾値およびパラメータ | app_setting テーブル（画面から変更可能） |
| プロンプト文面 | prompt_template テーブル（画面から変更可能） |

ソースコード中に文字列リテラルおよび数値リテラルを直接記述しない。
