## 1. 本文書の目的と位置づけ

本文書は、資格試験合格を目的とした学習計画の立案・実行・修正を継続的に支援するアプリケーション「ミチナリ」について、**なぜ作るのか**および**何を満たすべきか**を定義するものである。

具体的な機能一覧は仕様書、データ構造および算出ロジックは設計書に分離して記載する。本文書では、実装方式に踏み込まず、解決すべき課題と満たすべき要求に限定して記述する。

### 名称の由来

カーナビゲーションの案内表現「道なりに進んでください」に由来する。示された道をたどるだけで目的地に到達できること、および状況に応じて道が引き直されることの双方を含意する。

## 2. 背景

### 2.1 課題認識の出発点

資格学習は、努力量ではなく**計画の運用品質**によって結果が左右される。しかし学習者の大半は、計画の立案と修正に必要な認知コストを個人で負担しており、そのコストが学習そのものを圧迫している。

本アプリは、この構造を前提として設計される。すなわち、学習者から奪うべきは学習時間ではなく、**学習以外に費やされている判断の時間**である。

### 2.2 原体験としての三つの課題

実際の資格学習において、以下の三つの課題が反復的に発生している。

**課題1：初期計画の立案コストが過大である**

試験範囲の把握、教材の分量測定、残日数からの逆算、日次ノルマへの分解という一連の作業に、およそ4時間を要している。この作業は学習開始前に発生するため、着手そのものを遅延させる要因になっている。

**課題2：計画修正のコストが継続的に発生する**

計画は必ず崩れる。業務の繁閑、体調、家庭の事情によって予定は変動し、そのたびに再計算が必要になる。1回あたりおよそ1時間の修正コストが発生し、修正を怠れば計画は現実から乖離して形骸化する。結果として、**修正コストを避けるために計画そのものを放棄する**という最悪の帰結に至りやすい。

**課題3：合格への接近を実感できない**

日々の学習を継続していても、それが合格という目標にどの程度近づいているのかが分からない。学習時間や消化ページ数は記録できても、それらは投下量の指標であって到達度の指標ではない。この不確実性は、学習の中断を招く最大の心理的要因である。

### 2.3 課題の構造的分析

上記三課題は、それぞれ独立した不便ではなく、単一の構造的欠陥に由来する。

**現行のあらゆる学習管理手段は、計画を「静的な文書」として扱っている。**

計画が静的であるため、立案は一度きりの重い作業となり（課題1）、現実との乖離は手作業でしか埋められず（課題2）、進捗は計画に対する消化率としてしか表現できない（課題3）。

したがって本アプリが解くべき問題は、「より良い計画を作ること」ではない。**計画を動的なものに変えること**である。

### 2.4 学習の反復構造という前提

資格学習において、教材は一度で完了しない。過去問集は複数周回することが前提であり、周回を重ねるごとに処理速度と定着度が変化する。

したがって計画の単位は「教材を1回終える」ことではなく、「教材を予定回数だけ周回する」ことである。この前提を欠いた計画は、初回の周回を終えた時点で意味を失う。

### 2.5 本アプリの位置づけにおける個人的な動機

開発者本人は、業務・家事・家庭の各領域において既に高い負荷状態にある。その状況下でなお資格取得による市場価値向上を目指すという前提に立つとき、学習計画に関する判断を自ら行い続けることは現実的でない。

本アプリは、**学習に関する意思決定を外部化し、学習者が学習そのものにのみ集中できる状態を作る**ことを目的とする。これは怠慢ではなく、有限な認知資源を最も価値の高い活動に集中させるための合理的な資源配分である。

ただしこの目的は、後述する「下方修正の要求」と不可分である。判断を委ねる対象が、負荷を増やす方向にしか作用しないならば、外部化はむしろ有害となる。

### 2.6 学習経験の散逸という課題

資格学習の過程で蓄積される情報は、受験終了とともに失われる。どの教材にどれだけの時間を投じたか、どの時点で計画が崩れたか、何が合否を分けたかという情報は、本来であれば次の受験および他者の受験にとって極めて価値が高い。

しかし現状、これらは記録として残らない。合格した場合は「何が効いたか」が言語化されず、不合格の場合は「何が足りなかったか」が検証されないまま次の挑戦に向かうことになる。

**学習の記録は、受験が終わった時点でこそ価値が最大化される。** 本アプリは、目標のクローズ時に学習過程を構造化された知見として出力し、本人の振り返りと他者への横展開の双方に供することを目的の一つとする。

## 3. 既存手段の限界

| 手段 | 提供する価値 | 不足している点 |
| --- | --- | --- |
| 表計算ソフトによる自作計画表 | 完全な自由度 | 立案・修正のコストが全面的に利用者負担。乖離の検知機構なし |
| 学習記録アプリ（学習時間の記録） | 記録の容易さ、可視化 | 計画を生成しない。記録は事後的であり、行動を導かない |
| 汎用ToDo・タスク管理アプリ | タスクの管理 | 総量からの逆算がない。日次ノルマが利用者の主観に依存 |
| 暗記支援アプリ | 記憶定着の最適化 | 対象が暗記領域に限定。試験全体の計画は範囲外 |

**共通する不足は三点である。**

第一に、**個別の状況に応じた計画の自動生成**が存在しない。いずれの手段も、計画の立案そのものは利用者に委ねている。

第二に、**客観的視点からの継続的な軌道修正と伴走**が存在しない。記録は残るが、その記録を解釈して次の行動を提案する機能はない。

第三に、**学習経験を他者に継承可能な形で出力する手段**が存在しない。記録は個人の中に留まり、組織の資産にならない。

## 4. 本アプリのコンセプト

### 4.1 中核概念：適応型リプランニング・エンジン

本アプリは学習計画アプリではない。**適応型リプランニング・エンジン**である。

価値の中心は、初期計画を生成することではなく、**実際の行動実績に応じて計画を継続的に再最適化し続けること**にある。計画は文書ではなく、日々更新される派生値として扱われる。

この概念に基づき、日次ノルマはデータベースに保存されない。残量・残計画日数・負荷係数から**毎日その場で算出される**。計画を保存しないことによって、計画の陳腐化という概念自体が消滅する。

### 4.2 設計思想

本アプリの全機能は、以下の思想に従って設計される。

**(1) 判断基準の外部化**

学習の進め方に関する判断基準を、利用者の直感や記憶ではなく、明示的かつ設定可能なパラメータとして表現する。これにより、結果が個人の資質に依存せず再現可能となる。

**(2) 投下量と到達度の分離**

学習時間のみを管理すると、理解を伴わない時間経過を進捗として誤認する。学習分量のみを管理すると、惰性による非効率が検出できない。したがって「時間」「分量」「品質」の三層で計測する。

**(3) 負債を積まず、負荷を平準化する**

未達分を翌日に単純加算すると、数日の停滞で日次ノルマが心理的限界を超える。本アプリは未達分を加算せず、残量を残計画日で再配分する。これにより負荷はなだらかに上昇し、継続が阻害されない。

**(4) バッファの非対称性**

計画に組み入れない日（バッファ日）を明示的に定義する。バッファ日は、学習しなくても負債を生まないが、学習すれば翌日以降の負荷を軽減する。**休息に罰を与えず、努力にのみ報酬を与える**構造とする。

**(5) 保守的推定**

完了予測はバッファ日を計算に含めずに行う。予測は常に悲観方向へ振れ、実際にはバッファ日の学習によって前倒しされる。学習計画において、この方向の誤差のみが安全側である。

**(6) 上方修正と下方修正の対称性**

システムの目的関数は「計画の達成」ではなく「試験の合格」である。したがって、負荷を増やす提案と同等の重みで、負荷を減らす提案が可能でなければならない。受験日の後ろ倒し、学習範囲の絞り込み、期間ごとの負荷軽減、目標の一時停止は、いずれも合格という目的に照らして正当な選択肢である。

**(7) 記録の不変性と補足の可変性**

学習実績および日次報告の本文は、記録後の変更を認めない。実績は算出ロジックの根拠であり、可変であれば計画全体の信頼性が損なわれる。一方、後日の気づきを残せないことは日記としての価値を毀損するため、コメントによる補足を別レイヤーで許容する。

**(8) AIは知識源ではなく解釈エンジンである**

試験範囲や教材の内容についてAIに問い合わせることはしない。それらは利用者が構造化して入力する。AIの役割は、入力された数値実績と自然言語記述を統合して解釈し、行動修正を提案することに限定される。

**(9) 設定の完全な画面化**

利用者はソースコードおよび設定ファイルを参照しない。全パラメータは画面上から設定可能とする。

**(10) 外部制約への適応**

利用するAI基盤の仕様は変更できない。制約は所与のものとして受け入れ、アプリケーション側の設計で吸収する。制約を理由に要求を諦めない。

## 5. 対象範囲

### 5.1 利用者

第1フェーズにおいては開発者本人の単独利用を想定する。将来的には社内エンジニアへの配布を想定するが、MVPにおいてマルチユーザー機能は実装しない。

### 5.2 対象試験

**特定試験に依存しない汎用構造とする。** 試験区分、科目構成、教材、評価方式のいずれもデータとして表現し、アプリケーション側に個別試験の知識を持たせない。

複数の目標を同時に登録でき、期間の重複を許容する。ただし学習リソースは目標横断の共有資源として管理し、過剰配分を構造的に禁止する。

### 5.3 スコープ

**MVPに含むもの**

- 目標設定（試験・科目・受験日・教材・周回数・リソース配分）
- 学習リソースのマスタ管理（時間スロット単位）
- 日次ノルマの自動算出
- 日次報告（実績登録・日記・AIとの対話）
- 進捗のみの登録（日次報告を伴わない実績入力）
- 乖離の検知と警告、リプラン誘導
- ダッシュボード（統計・進捗・品質推移）
- カレンダーおよびガントチャートによる可視化
- 受験結果登録と目標のクローズ
- **総括レポートの生成とナレッジエクスポート**
- 設定画面
- データのエクスポート／インポート
- **目標種別「読書」（書籍の登録、日次報告での想起記録、読了レポートの生成。6.10参照）**
- **目標種別「仕事」（案件の登録、日次報告での業務記録、月次報告・半期評価レポートの生成。6.11参照）**

**MVPに含まないもの（将来構想）**

- AIとの対話による目標および学習範囲の自動設定
- 乖離検知時のスケジュール自動修正（MVPでは提案のみ、修正は利用者が実施）
- 教材選定に関するAIによる助言
- マルチユーザー対応および管理者向け機能
- モバイル端末への対応

MVPにおいて、**リプランの提案はAIが行い、実行は利用者が行う**。この分離により、自動化の対象は「実行」のみとなり、将来の自動化においてデータ構造の変更を要しない。

## 6. 要求事項

### 6.1 目標および計画に関する要求

| ID | 要求事項 |
| --- | --- |
| R-01 | 一つの目標に対し、複数の試験科目を登録できること。科目ごとに受験日を個別に設定できること |
| R-02 | 受験日は確定日および期間（範囲）のいずれでも登録できること。期間の場合は最も早い日を暫定受験日として算出に用いること |
| R-03 | 受験日が期間から確定日へ変更された際、計画を自動的に再最適化すること |
| R-04 | 一つの目標に対し、複数の教材を登録できること。教材と試験科目は多対多の関係を持てること |
| R-05 | 教材の締切は、紐づく試験科目のうち最も早い受験日から自動導出されること。利用者による上書きを許容すること |
| R-06 | 複数の目標を同時に進行でき、期間の重複を許容すること |
| R-07 | 学習リソースの総量を超える配分を構造的に禁止すること。禁止の判定単位は時間スロットとし、一つのスロットに対する全目標の配分時間の合計が、そのスロットの連続時間を超えないこと |
| R-51 | 教材ごとに予定周回数を設定できること |
| R-52 | 残量を、総量ではなく総作業量（総量×予定周回数）から算出すること。一つの周回が完了しても計画が消滅しないこと |

### 6.2 学習リソースに関する要求

| ID | 要求事項 |
| --- | --- |
| R-08 | 学習リソースは、単一の時間量ではなく、時間スロットの集合として管理すること |
| R-09 | 各スロットは、連続時間および利用環境（携帯端末／PC等）の属性を持つこと |
| R-10 | 教材は、必要とする連続時間および利用環境を要求条件として持てること |
| R-11 | 教材の要求条件を満たすスロットが存在しない場合、これを検知して警告すること |
| R-12 | 各日付を「計画日」「バッファ日」「除外日」のいずれかに分類できること。曜日単位の既定値と、日付単位の個別指定の双方を許容すること |
| R-13 | 任意の期間に対して負荷係数を設定でき、日次ノルマの配分に反映されること |
| R-54 | 1日の境界時刻を設定できること。深夜をまたぐ学習が意図しない日に計上されないこと |
| R-84 | リソース配分は、目標に対する比率ではなく、**スロットごとに割り当てる時間（分）**として入力すること。一つの目標が複数のスロットへ配分を持てること |

### 6.10 読書目標に関する要求

目標には種別（資格試験／読書）を持たせる。資格試験は**管理型**（合格という締切に向け、日次ノルマ・実効速度で計画を常時管理する）であるのに対し、読書は**記録・活用型**（管理・矯正の対象ではなく、日々の想起を蓄積し、読了時にその蓄積を自分のための資産として活用する）と位置づける。この違いにより、読書には6.1・6.3・6.4の定量的な計画管理（日次ノルマ、実効速度、警告・リプラン判定）を適用しない。

**リソース配分（6.2）はこの分類とは別の軸で要否を決める。** 配分の対象とすべきかどうかは、目標種別が管理型か記録・活用型かではなく、**その活動が自由な時間に行われるものか否か**で判断する。リソース配分とは有限な自由時間の割り振りであり、資格試験の学習も読書も自由な時間に行う活動であるため、いずれも配分の対象とする（R-64）。一方、仕事は自由な時間に行う活動ではないため対象としない（R-74）。

| ID | 要求事項 |
| --- | --- |
| R-69 | 目標に種別（資格試験／読書）を設定できること。種別は目標作成後も一覧・詳細で識別できること |
| R-70 | 読書目標には書籍（書名、著者、総ページ数、読了目標日）を1件登録できること。総ページ数は必須入力とし、1以上の整数とすること（1.1改16。ページ進捗を常に提示できるようにするため、従来の「任意入力」から変更した） |
| R-71 | 読書目標は、資格試験目標が持つ日次ノルマ・実効速度・完了予測日・警告判定を持たないこと。かわりに、残日数・直近の記録日・連続記録日数・総ページ数に基づく進捗（進捗率は100%を上限とする）を提示すること。読書目標で記録したスロットごとの時間は、実効速度や完了予測の算出には用いず、集計・表示・AIへの文脈提供にのみ用いること |
| R-64 | 読書目標は、学習リソース（時間スロット）の配分対象（R-07、R-08〜R-13、R-84〜R-87）に**含めること**。読書は自由な時間に行う活動であり、資格試験の学習と同じ時間を奪い合うためである。ただし配分の設定は任意とし、配分が未設定でも読書目標を進行中へ遷移できること（読書は日次ノルマ・完了予測を持たないため、配分が0でも機能が成立する） |
| R-65 | 日次報告において、進行中の読書目標がある場合、当日読んだ内容を想起する自由記述欄を提示できること。数値実績の入力を必須としないこと。ページに関する入力欄は「現在ページ」1つのみとし、その日に読んだページ数を利用者に入力させないこと（1.1改16。毎日記憶していられない値であり、かつ読書は定量的な進捗管理を行わない目標であるため） |
| R-66 | 読書目標の日次報告に対しても、AIによるフィードバックを返せること。フィードバックはノルマ達成の圧力を含まない内容とすること。読書の日次報告は評価の場ではなく利用者の気持ち・考え・思いを引き出す場とし、現在ページを含むページに関する数値をAIへの文脈として渡さないこと（1.1改16。現在ページは画面上の進捗表示のためだけに用いる） |

| R-68 | 読書目標の読了レポートは、既存のナレッジエクスポート機能（R-57〜R-60）の対象に含まれること |

**要求の背景**

R-59は、総括レポートの分析精度を決定づける。計画がいつ崩れたか、修正が遅れなかったかという情報は、合否の要因分析において最も重要でありながら、通常はどこにも残らない。

R-60は、他者への横展開を前提とした場合に必要となる。日記本文には業務や家庭の事情が含まれるため、共有時にこれを除外できる必要がある。

### 6.11 仕事目標に関する要求

目標種別「仕事」は読書と同じ**記録・活用型**（管理・矯正の対象ではなく、日々の記録を蓄積し、蓄積を自分のための資産として活用する）に分類され、日次ノルマ・実効速度を適用しない点は読書目標（6.10）と同じである。ただしリソース配分については読書と扱いが異なり、仕事は対象としない（R-74）。6.10に記した通り配分の要否は「自由な時間に行う活動か否か」で判断するためであり、仕事は自由な時間に行う活動ではない。一方、読書がクローズ時（読了時）の1回きりのレポート生成であるのに対し、仕事は業務が続く限り**月次・半期という周期で振り返りと次期の目標案を生成し続ける**点が異なる（副分類：定期報告型）。

仕事目標は1目標＝1案件（プロジェクト）に対応する。営業・顧客から事前に伝えられる想定業務内容と、実際に着手する業務内容とがしばしば乖離するという実務上の特性を踏まえ、想定内容は目標に1件だけ保持し、実際の内容は日次記録の積み上げから把握する（両者の比較・解釈はAIが担う。差分を利用者に構造化入力させない）。

| ID | 要求事項 |
| --- | --- |
| R-72 | 目標に種別「仕事」を設定できること。仕事目標は1目標＝1案件（プロジェクト）に対応し、案件ごとに独立して進行・クローズできること。複数の仕事目標が同時に進行中でもよいこと |
| R-73 | 仕事目標には案件情報（案件名、営業・顧客から事前に伝えられた想定業務内容、着手日）を1件登録できること。想定業務内容は登録後も更新できること（更新は上書きとし、変更履歴は保持しない） |
| R-74 | 仕事目標は、資格試験目標が持つ日次ノルマ・実効速度（R-23〜R-29）の対象としないこと（読書目標R-71と同じ考え方）。あわせてリソース配分（R-07、R-08〜R-13、R-84〜R-87）の対象ともしないこと。仕事は自由な時間に行う活動ではなく、自由時間の割り振りという配分の目的に当てはまらないためである（この点で読書目標R-64とは扱いが異なる） |
| R-75 | 日次報告において、進行中の仕事目標がある場合、当日の業務内容を自由記述で記録できる欄を提示できること。数値実績の入力を必須としないこと |
| R-76 | 仕事目標の日次報告に対してもAIによるフィードバックを返せること。フィードバックは日々の業務内容や努力を労う内容とすること |
| R-77 | 「今日の一言」（R-36）は仕事目標にも適用すること。読書目標では対象外としているが（要求の背景を参照）、仕事目標では日々の努力を称える一言を明示的に必要とするため対象に含める |

**要求の背景**

R-77（今日の一言の対象化）：読書目標は「今日の一言」の対象外としている（要件定義書1.1（改2）時点の設計判断。日次のAIフィードバック（R-66）で足りるとされた）。仕事目標では、利用者が明示的に「日々の業務内容や努力を誉める機能」を求めており、日次フィードバックとは別に短文で労う一言の需要がある。読書と異なる扱いとする根拠はこの明示的な要求にある。

R-78（外部フォームへの自動送信を行わない根拠）：Microsoft Formsは、回答を外部から送信するための公式API（Microsoft Graph等）を提供していない（[Microsoft Q&A: Submit Form response through Graph API](https://learn.microsoft.com/en-us/answers/questions/1193927/submit-form-response-through-graph-api)、[Microsoft Forms API \| Microsoft Community Hub](https://techcommunity.microsoft.com/discussions/microsoftforms/microsoft-forms-api/4480628)、2026-09-03時点で要件定義時に確認。非公式エンドポイントは存在するが非サポートのため採用しない）。そのため、既存のナレッジエクスポート（R-57〜R-60）と同様、アプリ内でドラフトを生成し利用者が転記する方式とする。

R-80（案件単位で生成する根拠）：複数案件を横断した1通に集約する設計も検討したが、利用者の実際の運用（案件ごとに独立した振り返りを求める）に合わせ、既存の総括レポート・読了レポート（goal_retrospective）と同じ「1目標＝1レポート対象」の設計を踏襲することとした。

R-82（人による修正機能の根拠）：この機能はAIの出力精度（特に達成度判定）が半期評価にまで波及する性質を持つ。誤った達成度がそのまま会社への提出物になれば利用者の評価に直接影響するため、AIの出力を鵜呑みにせず人が確認・訂正できる導線を必須とした。

R-83（初回利用者への配慮）：R-78②「対象月の目標」はR-82の仕組みにより前月の報告から引き継がれる値だが、案件開始直後は引き継ぐ元の報告が存在しない。この状態でAI生成のみに機能を依存させると初回利用者が機能を使えなくなるため、手動での目標設定を許容する。

| 応答性能 | ダッシュボードの初期表示を2秒以内とする。AI応答は10秒以内を目標とする |
| データ量 | 1目標あたり最大365日分の日次記録を想定する |
| 可用性 | ローカル動作を前提とし、可用性要件は設けない。ただしデータ破損に備えたバックアップ機能を設ける |
| セキュリティ | AI連携の認証情報は、AI基盤の開発キットが提供する仕組みに委ねる。ブラウザ側の記憶領域には保持しない |
| 保守性 | UI文言はロケールファイル、パラメータは設定として外部化する。ソースコード中に文字列および数値を直接記述しない |
| 拡張性 | 将来のマルチユーザー化およびデータベース移行を阻害しない構造とする |
| 耐障害性 | AI基盤が利用できない状況でも、実績の記録が可能であること |

## 8. 制約および前提条件

### 8.1 AI基盤に関する制約

利用するAI基盤（NewtonX）の開発キット仕様は変更できない。以下は所与の制約として受け入れる。

| 項目 | 制約内容 | アプリ側の対応方針 |
| --- | --- | --- |
| 利用形態 | Python向け開発キット経由。REST APIではない | バックエンドをPythonで構成し、同一プロセスから呼び出す |
| 構造化出力 | 対応していない | 応答を自然文として扱い、機械的解析を行わない |
| Web検索 | メッセージ送信時の既定値が有効 | 呼び出しごとに明示的に無効化する |
| 会話の永続化 | 会話がAI基盤側に作成・保持される | 会話の識別子をローカルに保持し、用途と日付ごとに会話を分離する |
| 会話の整理 | フォルダ機能が提供される | 目標ごとにフォルダを作成するほか、目標に紐づかない会話も共通フォルダへ集約し、フォルダ削除だけでアプリ由来の会話を一括解放できるようにする |
| 文脈管理 | 親メッセージ順序による文脈維持機構が提供される | 同一会話内の連続往復にのみ使用し、日をまたぐ文脈は自前で注入する |
| 認証 | ブラウザ経由の認証フロー。トークンは開発キットがファイル管理する | 独自の資格情報管理を実装せず、開発キットの仕組みに委ねる |
| リダイレクト先 | ローカルの特定ポートを使用する | アプリケーションサーバは別ポートで起動する |
| 入力上限 | 明示されていない | プロンプト長を推定し、上限超過時に情報を段階的に縮退させる |
| 通信制限 | 頻度制限が存在する可能性がある | 呼び出し間隔の下限を設ける |
| ファイル登録 | アシスタントへのナレッジ登録機能が存在する | 使用しない。共有アシスタントに個人の学習記録を登録しない |

## 9. 成功指標

**KGI（最終目標指標）**

- 登録した目標の達成、すなわち対象試験への合格

**KPI（先行指標）**

- アプリ利用率 ＝ 日次報告を実施した日数 ÷ 学習開始日から受験日までの日数

KPIを利用率としたのは、本アプリの価値が対話による継続的な軌道修正にあるためである。報告が途絶えた時点でリプランは機能を停止する。したがって利用率は、機能の稼働率そのものを表す。

**補助的観測指標**

以下は目標値を設定しないが、設計の妥当性を検証するために記録する。

- 初期計画立案に要した時間（現状比較の対象値：約4時間）
- リプラン1回あたりに要した時間（現状比較の対象値：約1時間）
- 強制リプランの発火回数
- 品質指標の推移が合格基準線に到達した時期
- バッファ消費率の推移

## 10. 将来構想

### 10.1 機能面の拡張

第1段階として、AIとの対話による目標および学習範囲の自動設定を追加する。これにより課題1（立案コスト）が完全に解消される。

第2段階として、乖離検知時のスケジュール自動修正を追加する。MVPにおいて利用者が担っている「実行」の役割をシステムに移管する。この時点で、適応型リプランニング・エンジンが完全な形で成立する。

第3段階として、教材選定に関する助言機能を追加する。

### 10.2 展開構想

本アプリは開発者個人の利用から開始するが、その先に社内配布を構想している。

資格取得は、個人の市場価値向上と組織の技術力向上が同時に成立する数少ない領域である。しかし多くの学習者は、本文書2.2に記した三課題によって途中で離脱している。**離脱の原因が意欲の欠如ではなく計画運用コストにあるならば、それは技術によって解決可能な問題である。**

**ナレッジエクスポート機能（6.9）は、この展開構想における中核をなす。**

個人が使うだけであれば、エクスポートは振り返りの手段に留まる。しかし複数の学習者が同一の形式で学習記録を出力するようになれば、「この試験には何時間必要か」「どの教材をどの順で使うべきか」「どの時点で計画を修正すべきか」という問いに、実データで答えられるようになる。

とりわけ**不合格事例の記録に価値がある**。合格体験談は世に溢れているが、不合格の要因が構造的に分析された記録はほとんど存在しない。本アプリはリプラン履歴と品質指標の推移を保持しているため、「どの時点で軌道修正すべきだったか」を事後に特定できる。これは他の学習管理手段では不可能である。

この構想を実現するには、マルチユーザー対応、テナント境界の保護、および管理者向けの集計機能が必要となる。MVPの設計においては、これらの追加が既存構造の変更を要しないよう配慮する。

## 11. 用語定義

| 用語 | 定義 |
| --- | --- |
| 目標 | 一つの試験合格を単位とする管理対象。複数の試験科目と教材を含む |
| 試験科目 | 目標に含まれる受験単位。それぞれ独立した受験日を持つ |
| 教材 | 学習の対象物。単位、総量、予定周回数、必要連続時間、必要環境、品質指標の方式を属性として持つ |
| 予定周回数 | 締切までに教材を何回反復する計画か |
| 総作業量 | 総量 × 予定周回数。残量算出の基礎となる |
| 計画日 | 日次ノルマを課す日。日次ノルマ算出の分母に算入される |
| バッファ日 | ノルマを課さない日。分母から除外されるが、学習実績の登録は可能 |
| 除外日 | 学習が不可能であることが事前に判明している日。分母および実効速度の算出から除外される |
| 日次ノルマ | 当日に達成すべき分量。保存されず都度算出される |
| 実効速度 | 単位時間あたりの完了分量。投下時間が記録された日のみを対象に、周回別に算出される |
| 必要速度 | 締切までに完了するために必要な単位時間あたりの分量 |
| 完了予測日 | 現在周回の実効速度を維持した場合に教材が完了する日 |
| 負荷係数 | 特定期間における学習量の重み。日次ノルマの配分に用いる |
| リプラン | 計画の再最適化。MVPにおいてはAIの提案に基づき利用者が実施する |
| 1日の境界時刻 | 日付が切り替わる時刻。深夜学習の計上日を制御する |
| 総括レポート | 目標クローズ時にAIが生成する、学習過程の要因分析 |
| ナレッジエクスポート | 目標単位の学習記録を、振り返りおよび横展開に供する形式で出力すること |
