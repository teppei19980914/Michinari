# 開発Todo：スケジュール・ガントチャート機能（MVP） v1.1

| 版 | 日付 | 内容 |
| --- | --- | --- |
| 1.0 | 2026-10-18 | 初版（単位1〜4） |
| 1.1 | 2026-11-12 | AIによるスケジュール修正案（承認制）を単位5として追加（D-51〜D-66、第13章・第14章）。D-41を改訂。デグレ・横展開漏れを防ぐ共通の進め方を追加（第15章） |

本書は、目標ごとのスケジュール作成機能とガントチャート表示機能（以下「本機能」）のMVPの設計確定事項をまとめたものである。開発は第9章の5つの開発単位に分けて進め、各単位の着手時に本書の該当章を入力とする。

各単位の着手時には、従来どおり次の順で進める。
1. 全ソースコードを走査し、影響範囲を確定する
2. 単位ごとの開発Todoを作成する
3. 開発Todoに沿って実装する

本書と既存の設計書（要件定義書・仕様書・設計書・技術選定書）が食い違う場合は、本書を正とする。既存の設計書は、各単位の実装と同時に本書に合わせて改訂する。

---

## 1. 目的と位置づけ

- **目的**：利用者が別のアプリやツールを使わずに、目標ごとのスケジュールを作成し、ガントチャートで可視化できるようにする。ガントチャートは入力内容からシステムが自動で描画するため、非エンジニアでも本質的な作業以外の手間をかけずにスケジュールを管理できる。
- **対象**：3種別すべての目標（資格試験〈EXAM〉・読書〈READING〉・仕事〈WORK〉）。
- **既存機能との関係**
  - 資格試験の分析画面にある教材ガント（ANL-04）とは併存し、連携しない。
  - 日次報告の実績（StudyLog・ReadingLog・WorkLog）とは役割が異なり、置き換えない。日次の実績はノルマ・完了予測・警告・AIフィードバックの元データとして従来どおり扱う。本機能の「状況・実績日」は作業項目単位の進み具合を表す。
  - 作業項目の状況・実績日の保存先は、本機能のデータだけとする。日次報告からの更新も同じデータへ書き込み、二重管理はしない。
- **AIによる修正案（単位5）**：日次報告の確定後に、システムが遅れを検知した目標について、AIがスケジュールの修正案（予定日の変更）を作る。修正案は、利用者が承認した行だけスケジュールに反映する。承認なしにスケジュールが変わることはない（第13章）。
- **将来の拡張（MVPの対象外）**：作業の前後関係（先行作業）の管理、行の追加・分割の提案。

## 3. 画面仕様：スケジュールタブ

### 3.1 構成

上から次の順に配置する。

1. 役割の案内文：「日々の進捗は日次報告で、作業項目の状況はこの画面または日次報告で更新します」など（文言はロケールファイルで管理する）
2. ツールバー：固定する行数、固定する列数、「今日へ」、「行を追加」、「列を追加」、「変更を破棄」、「保存」
3. 一体型グリッド：左側が表、右側がガント

### 3.2 一体型グリッド

- **列の並び**：行操作列 → 既定の7列 → 追加列 → 日付の列
- **行操作列**：上へ、下へ、下に挿入、削除のボタンを置く。行操作列は常に左端に固定し、固定する列数には数えない。閲覧のみの目標では表示しない。
- **固定する列数**：既定の7列と追加列を、左から数えた数とする。日付の列は固定できない。
- **固定する行数**：見出し行は常に固定する。それに加えて、データ行を先頭から0〜N行固定する。
- **固定の実装**：CSSの `position: sticky` で実現する。列幅は固定幅（D-15）とし、固定列の `left` の位置を算出できるようにする。
- **日付の見出し**：年月の段と日の段の2段とし、見出し行と一緒に固定する。

### 3.3 編集

- 常に編集できる状態で表示する（閲覧のみの目標を除く）。変更があると「保存」と「変更を破棄」が押せるようになる。
- **状況**：選択式とする。スケジュール画面で状況を変更した場合も、日次報告と同じ補完ルール（6.3）を本日の日付で適用する。
- **追加列の見出し**：見出しのセルで名前を変更でき、左右への移動と削除の操作を置く。
- **保存時の409（版数の不一致）**：「他の画面で更新されました」と知らせ、「最新を読み込む（編集内容は破棄）」と「編集を続ける」を選べるようにする。

### 3.4 ガント

- **描画**：1日ごとのセルをDOMとして並べない（100行×数百日で描画が重くなるため）。行ごとに予定帯・実績帯を絶対位置で配置し、土日祝の網掛けと本日線は、グリッド全体に1回だけ重ねて描く。
- **1日分の幅**：「表示領域の幅÷表示期間の日数」を、下限と上限の範囲に収めた値とする。下限は日付の数字（2桁）が読める幅とし、単位はremで指定する。これにより、文字サイズの設定（fontScale）に追従させる。
- **表示期間**：全行の予定開始日・予定終了日・実績開始日・実績終了日と本日のうち、最も早い日から最も遅い日までとする。予定日が未入力の行は、表には表示するがガントには描かない。
- **初期のスクロール位置**：本日の日付の列が、固定列のすぐ右に来るようにする。期間の終わりに近く、そこまでスクロールできない場合は、右端までスクロールした位置で止める。
- **「今日へ」ボタン**：初期表示と同じ位置へスクロールする。
- **色**：既存のテーマのトークンに合わせて、次の色を `index.css` に追加する（ダークモードにも対応する）。
  - 土曜日
  - 日曜日・祝日（同じ色）
  - 予定帯
  - 実績帯（進行中はアクセント色、完了は成功を表す緑、中止はグレー）
  - 遅れの印（警告色）
- **遅れ日数**：未完了で本日が予定終了日を過ぎている場合は「本日－予定終了日」、完了していて実績終了日が予定終了日を過ぎている場合は「実績終了日－予定終了日」とする。
- **既存の教材ガントとの共通化**：既存の `ganttGeometry.ts` は百分率方式で、教材ガントで使われている。日付の差の計算など共通にできる部分だけを切り出して共通化し、既存の教材ガントの表示は変えない（デグレ禁止）。

### 3.5 祝日の表示

- 表示期間の祝日を `GET /holidays` で取得する。
- 収録範囲外の年が表示期間に含まれる場合は、ガントの上に「YYYY年の祝日データは未収録です」と注記する。

## 4. 画面仕様：日次報告の「今日の作業項目」欄

- **配置**：各種別の実績入力の直下に、目標ごとに置く（D-38）。
- **表示する行**：D-33の条件に当てはまる行を表示する。「すべて表示」で、その目標の完了・中止以外の全行に展開できる。
- **各行の表示**：作業項目、予定期間、状況（選択式）、実績開始日、実績終了日。
- **状況を変更したとき**：6.3の補完ルールで、報告対象日を自動で入れる。
- **保存**：種別の「確定」またはSC-07の「登録」のときに保存する（D-35）。変更しなかった行は送信しない。
- **確定済みの種別**：入力欄を出さず、その日に更新した内容を読み取り専用で表示する。
- **下書き**：既存の下書きの仕組み（`useDailyReportDraft` 等）に、作業項目の入力内容を含める。

## 6. 入力の検証ルール（共通）

### 6.1 検証の置き場所

検証はサービス層の1か所に集約し、スケジュール画面の一括保存と日次報告・SC-07からの更新で共通に使う（DRYの原則）。画面側でも同じルールで入力中にエラーを表示するが、最終的な判定はサーバーで行う。

### 6.2 ルール

| 対象 | ルール |
| --- | --- |
| 作業項目 | 必須。空白のみは不可 |
| 予定開始日・予定終了日 | 必須。予定開始日 ≦ 予定終了日 |
| 状況 | 必須（初期値は未着手） |
| 未着手 | 実績開始日・実績終了日は入力不可 |
| 進行中 | 実績開始日は必須、実績終了日は入力不可 |
| 完了 | 実績開始日・実績終了日はともに必須 |
| 中止 | 実績日は任意。ただし実績終了日だけを入力することは不可 |
| 実績日 | 実績開始日 ≦ 実績終了日。どちらも本日（サーバーの論理日）以前 |
| 上限 | 追加列は10列、行は100行（`app_setting`） |
| 追加列の名前 | 必須。同じ目標の中で重複は不可 |
| 所有者 | 送られてきた行・列のIDが、対象の目標に属すること |
| 目標の状態 | 終了した目標への書き込みは拒否する |

### 6.3 状況を変更したときの実績日の補完

基準日は、日次報告とSC-07では報告対象日、スケジュール画面では本日とする。

| 変更後の状況 | 補完内容 |
| --- | --- |
| 進行中 | 実績開始日が空なら基準日を入れる。実績終了日は消す |
| 完了 | 実績開始日が空なら基準日を入れる。実績終了日が空なら基準日を入れる |
| 未着手 | 実績開始日・実績終了日を消す |
| 中止 | 変更しない |

補完した値は、利用者が修正できる。

## 7. データモデル

### 7.1 新規テーブル

## 8. API

| メソッド・パス | 内容 |
| --- | --- |
| `GET /goals/{goal_id}/schedule` | 行、追加列、セル、固定の設定、revision、本日（サーバーの論理日）を返す |
| `PUT /goals/{goal_id}/schedule` | 一括保存（8.1）。revisionが一致しなければ409を返す |
| `PUT /goals/{goal_id}/schedule/view-setting` | 固定の行数・列数を即時に保存する（revisionは変えない） |
| `GET /holidays?date_from&date_to` | 期間内の祝日（日付・名称）と、収録済みの最初と最後の年を返す |
| `GET /records/{target_date}/schedule-items` | 報告対象日にD-33の条件で表示する作業項目を、目標ごとに返す |
| `POST /records/{target_date}/finalize`<br>`POST /records/{target_date}/reading-finalize`<br>`POST /records/{target_date}/work-finalize` | リクエストに任意の `schedule_item_updates` を追加する。その種別の目標に属する行だけを受け付ける |
| `POST /records/{target_date}/progress` | 同上（全種別の行を受け付ける）。「実績が1件以上必須」を「実績または作業項目の更新が1件以上必須」に緩める。作業項目の更新だけの場合は、DailyRecordを作らず報告状態も変えない（D-36） |

- `schedule_item_updates` の各要素は、行ID、状況、実績開始日、実績終了日とする。
- エラーは、既存のエラーのコード化の仕組み（`開発Todo_エラーのコード化_v1.0.md`）に沿ってコードを割り当てる。
- フロントエンドのAPIの型は `npm run generate:api-types` で再生成する（手書きは禁止）。

### 8.1 一括保存（PUT）の差分ルール

- **リクエストの内容**：revision、columns（id または仮キー、name）、items（id、既定の7列の値、セルの値）。
- **行と列の判定**：IDがあれば更新、なければ新規作成、送られてこなかった既存のものは削除する。並び順は配列の順とする。
- **新規列への値の紐付け**：新しい列のセルは、画面側で振った仮キーで対応付ける。
- **所有者の検証**：送られてきたIDが他の目標に属していればエラーとする（認可境界のテストを必須とする）。
- **トランザクション**：すべての変更を1つのトランザクションで適用し、revisionを1増やす。
- **履歴**：状況・実績日が変わった行について、source=SCHEDULE_SCREEN で履歴を追加する。

## 12. 本書で補った細目（設計インタビューの決定を具体化したもの）

インタビューで明示的に決めていないが、決定事項と整合するように本書で補った仕様である。影響範囲の確定時に、問題があれば指摘すること。

1. スケジュール画面で状況を変更した場合も、6.3の補完ルールを本日の日付で適用する。
2. 進行中の行には実績終了日を入力できない。中止の行では、実績終了日だけを入力することはできない。
3. 行操作列は常に左端に固定し、固定する列数には数えない。

5. 追加列の名前は必須で、同じ目標の中での重複は不可とする。
6. 確定済みの種別では、その日に更新した作業項目を読み取り専用で表示する。
7. 日次報告の「すべて表示」では、完了・中止以外の全行を表示する。
8. 409のときは、「最新を読み込む（編集内容は破棄）」と「編集を続ける」を選べるようにする。

## 13. AIによるスケジュール修正案（単位5）

### 13.1 全体の流れ

1. 利用者が日次報告の種別を「確定」する（単位4の作業項目の更新も、ここで保存される）。
2. 確定APIの応答に、その種別の目標のうち遅れのある目標の一覧（`schedule_revision_candidates`）を含める（13.2）。
3. 画面は確定の完了をすぐに表示し、続けて一覧の目標ごとに修正案の生成APIを呼ぶ。生成中は「スケジュールの修正案を作成中…」と表示し、利用者の操作は止めない。
4. 生成が終わったら、「修正案があります（スケジュールタブで確認）」とリンクを表示する。修正すべき行がなければ何も表示しない。
5. 利用者は、スケジュールタブで行ごとに承認・却下する。承認した行だけ、予定日が変わる。

- 生成の依頼を画面から行うのは、新しい常駐処理（裏で動くスレッドなど）を増やさないためである。確定後に画面を閉じた場合は生成されないが、次の確定時、またはスケジュールタブの「AIに修正案を依頼」で作り直せる。
- 進捗のみ登録（SC-07）は確定ではないため、自動生成のきっかけにしない。スケジュールタブのボタンからは依頼できる。
- ひとこと記録モードで確定した場合も、自動生成の対象とする（確定の処理が同じため）。

### 13.2 遅れの判定（AIを使わない）

共通の関数として、サービス層に1つだけ置く（DRYの原則）。ガントの遅れの印（D-18）も、この関数の結果を使う。

| 種類 | 条件 |
| --- | --- |
| 終了の遅れ | 状況が未着手または進行中で、本日 > 予定終了日 |
| 開始の遅れ | 状況が未着手で、本日 > 予定開始日 |

- 本日はサーバーの論理日（`goal_service.resolve_today`）とする。
- 終了した目標は対象外とする。
- 自動生成は、同じ目標・同じ報告対象日につき1回までとする（同じ日に種別を分けて確定しても、二重に生成しない）。

### 13.3 AI呼び出し

- **新しい用途**：`AiPurpose.SCHEDULE_REVISION` と `ConversationScope.SCHEDULE_REVISION` を追加する。1回ごとに完結する呼び出しとし、会話は継続しない。
- **プロンプト**：既存の方式どおり、`prompt_template` に初期値を投入する（`init/prompt_texts_common.py`、`init/seed_data.py`）。アシスタントのUIDは、既存のキーの形（`ai.assistant_uid.*`）で `app_setting` に追加する。
- **プロンプトに渡す情報**
  - 本日、目標の種別、目標の期限（D-62。期限がなければ「なし」）
  - スケジュールの全行：行ID、並び順、作業項目、作業内容（上限文字数で切り詰める）、予定開始日、予定終了日、状況、実績開始日、実績終了日、システムが判定した遅れの種類。この一覧自体は固定変数（縮退対象外）とする
  - 日次報告の文脈：その種別の既存の文脈構築（`ai_context_exam`・`ai_context_reading`・`ai_context_work` の直近の記録と週次要約）を再利用し、`prompt_builder.build_with_degradable_entries` で文字数の上限内に縮退させる（古い記録から落とす）
  - **行一覧が上限に収まらない場合の縮退**（開発Todo_スケジュール・ガントチャート_検証修正_v1.0.md 修正4）：日次報告の文脈を0件まで縮退させても上限に収まらない場合、スケジュールの行一覧から完了・中止の行を先に落として再試行する（CHANGE判定は未着手・進行中の行にしか適用されないため、生成結果への影響が最も小さい）。それでも収まらない場合は`ScheduleRevisionPromptTooLongError`で生成を中止する（従来どおり）
  - 直近に却下した内容（D-64）：行、却下した変更案、却下の理由（入力があれば）
- **AI通信とトランザクション**：CODING_RULES「AI通信とトランザクション」に従う。必ず `ensure_conversation` と `send_and_log` を経由する。AIの応答を待つ間はDBに書き込まない。修正案の保存と古い修正案の置き換え（D-65）は、応答を得た後に `serialize_writes()` の中で1つのトランザクションとして書き込む。
- **表示言語**：英語表示の場合の応答言語は、既存の `send_and_log` の仕組みに従う。

### 13.4 応答の形式と読み取り

既存の `quiz_generation_service.py` と同じく、`===` の行で区切ったブロック形式とする。ブロックは次の2種類とする。

```
種類: 変更
行ID: 12
予定開始日: 2026-11-20
予定終了日: 2026-11-25
理由: （1行）
===
種類: 注意
行ID: 15
理由: （1行。期限内に収まらない理由など）
===
総評: （任意、1行）
```

- 正規表現は各項目を1行として `[^\n]+?` で読み取り、`re.DOTALL` は使わない（ReDoS対策、CWE-1333）。
- 1ブロックの文字数の上限を設け、超えたブロックは正規表現に通さずに捨てる。
- 形式が崩れたブロックだけを捨て、他のブロックは生かす。

### 13.5 検証（不正なブロックは捨てる）

| 対象 | ルール |
| --- | --- |
| 行ID | 対象の目標に属する行であること |
| 状況 | 未着手または進行中の行だけ（完了・中止の行は捨てる） |
| 進行中の行 | 予定開始日は現在の値と同じであること（変更不可） |
| 新しい予定日 | 本日以降。予定開始日 ≦ 予定終了日 |
| 期限 | 目標に期限がある場合、新しい予定終了日 ≦ 期限 |
| 差分 | 現在の値と少なくとも1つ異なること |
| 理由 | 必須。上限文字数以内 |
| 重複 | 同じ行IDのブロックが複数ある場合は、最初のものだけを使う |
| 注意ブロック | 行IDが対象の目標に属すること。理由は必須 |

有効な変更ブロックも注意ブロックもない場合は、修正案を保存せず「修正が必要な行はありませんでした」と返す。

### 13.6 データモデル（新規テーブル）

**schedule_revision_proposal**（修正案）

| 列 | 型 | 制約・備考 |
| --- | --- | --- |
| id | Integer | PK |
| goal_id | FK goal.id | ON DELETE CASCADE、INDEX |
| trigger | Enum ScheduleRevisionTrigger | AUTO（確定後の自動生成）／MANUAL（ボタン） |
| record_date | Date | NULL可（自動生成のきっかけとなった報告対象日。13.2の1日1回の判定に使う） |
| summary | Text | NULL可（総評） |
| status | Enum ScheduleRevisionProposalStatus | PENDING（未判断の行がある）／RESOLVED（すべて判断済み）／SUPERSEDED（新しい修正案に置き換え済み） |
| created_at | DateTime | NOT NULL（UTC） |

**schedule_revision_proposal_item**（修正案の行）

| 列 | 型 | 制約・備考 |
| --- | --- | --- |
| id | Integer | PK |
| proposal_id | FK schedule_revision_proposal.id | ON DELETE CASCADE、INDEX |
| schedule_item_id | FK schedule_item.id | ON DELETE CASCADE |
| kind | Enum ScheduleRevisionItemKind | CHANGE（変更）／WARNING（注意） |
| before_planned_start_date / before_planned_end_date / before_status | Date / Date / Enum | 生成時点の値（D-59の判定に使う） |
| proposed_planned_start_date / proposed_planned_end_date | Date | NULL可（WARNINGではNULL） |
| reason | Text | NOT NULL |
| decision | Enum ScheduleRevisionDecision | PENDING／APPROVED／REJECTED／ACKNOWLEDGED（注意の確認済み）／SUPERSEDED |
| applied_planned_start_date / applied_planned_end_date | Date | NULL可（承認時に実際に反映した値。利用者が修正した場合はその値） |
| reject_reason | Text | NULL可 |
| decided_at | DateTime | NULL可（UTC） |

- 注意（WARNING）の行は承認・却下の対象ではなく、「確認しました」で閉じる（decision＝ACKNOWLEDGED）。
- 予定日の変更履歴は、本テーブルが兼ねる（`schedule_item_history` は状況・実績日の履歴のまま変更しない）。
- 新しいテーブルを追加するため、全データのエクスポートの `DATA_SCHEMA_VERSION` を、単位5の時点の次の版に上げる。

### 13.7 API

| メソッド・パス | 内容 |
| --- | --- |
| 確定API3本（単位4で拡張済み） | 応答に `schedule_revision_candidates`（遅れのある目標IDの一覧。13.2の1日1回の判定で生成済みの目標は除く）を追加する |
| `POST /goals/{goal_id}/schedule/revision-proposals` | 修正案を生成する。リクエストに `trigger`（AUTO／MANUAL）と、AUTOの場合は `record_date` を含める。AUTOで遅れがない場合はAIを呼ばずに「対象なし」を返す |
| `GET /goals/{goal_id}/schedule` | 応答に、未判断の修正案（あれば1件）を含める |
| `POST /goals/{goal_id}/schedule/revision-proposals/{proposal_id}/decisions` | 行ごとの判断を受け付ける。各要素は、修正案の行ID、判断（承認／却下／確認済み）、承認時の予定開始日・予定終了日（修正した場合）、却下の理由（任意） |
| `GET /dashboard`（既存） | 応答に、未判断の修正案がある目標の一覧を追加する |

**判断API（decisions）のルール**

- 修正案が対象の目標に属し、PENDINGであること。
- 承認する行は、変更前の値が現在の値と一致すること（D-59）。一致しない行はその行だけ「変更されたため承認できません」として結果に返し、他の行は処理する。
- 利用者が日付を修正して承認する場合は、第6章の検証ルールに加えて、13.5の「新しい予定日」と「進行中の行」のルールを適用する。期限（D-62）は、利用者の判断を優先して適用しない。
- 承認した行は `schedule_item` の予定日を更新し、`goal_schedule.revision` を1増やす。
- すべての行の判断が終わったら、修正案をRESOLVEDにする。
- 終了した目標では拒否する。

### 13.8 画面

**スケジュールタブ**

- ツールバーに「AIに修正案を依頼」ボタンを追加する。生成中は押せないようにし、終了した目標では表示しない。AIにログインしていない場合は、既存のAI認証の導線に従う。

### 13.10 テスト

- 遅れの判定：2種類の条件の境界（本日＝予定日、本日＝予定日＋1日）、完了・中止の行、終了した目標。
- 応答の読み取り：正常、形式の崩れ、一部だけ不正、ReDoSになりうる入力（既存の `quiz_generation_service` のテストと同じ観点）。
- 検証：13.5の全ルール。特に、他の目標の行ID（認可境界）、完了した行、過去の日付、期限超過、進行中の行の開始日の変更。
- 期限：資格試験（確定日、期間指定、複数科目）、読書、仕事（制約なし）。既存の `compute_due_date` と同じ結果になること。
- 判断API：行ごとの承認・却下・確認済み、日付を修正した承認、変更前の値が一致しない行、PENDING以外の修正案、revisionの加算、RESOLVEDへの遷移。
- 置き換え：新しい修正案の生成で、古い修正案の未判断の行がSUPERSEDEDになること。
- 1日1回：同じ目標・同じ報告対象日の自動生成が2回目は行われないこと。
- AI通信とトランザクション：`backend/tests/test_ai_write_lock.py` と同じ観点で、AI呼び出し中に別接続から書き込めること。
- 画面：未保存の変更があるときの判断ボタンの無効化、点線の重ね表示、確定後の案内の表示。

## 14. 単位5で補った細目

インタビューで明示的に決めていないが、決定事項と整合するように本書で補った仕様である。影響範囲の確定時に、問題があれば指摘すること。

1. 生成の依頼は画面から行い、新しい常駐処理は増やさない（13.1）。
2. 進捗のみ登録（SC-07）は自動生成のきっかけにしない。ひとこと記録モードの確定は対象とする。
3. 自動生成は、同じ目標・同じ報告対象日につき1回までとする。
4. ガントの遅れの印（D-18）は、13.2の判定関数を共通で使い、開始の遅れにも印を付ける（Tooltipで遅れの種類を区別する）。
5. 利用者が日付を修正して承認する場合は、目標の期限の制約を適用しない（利用者の判断を優先する）。
6. 注意の行は「確認しました」で閉じる。
7. 表に未保存の変更があるときは、承認・却下できないようにする。
8. 予定日の変更履歴は、修正案のテーブルが兼ねる。

## 15. 各単位の共通の進め方（デグレ・横展開漏れの防止）

各単位は、新しいClaude Codeセッションで、次の手順を必ず守って進める。CLAUDE.mdの「コミット前チェック」は、本章の手順13で実施する（重複して定義しない）。

### 15.1 着手前

1. **前提の確認**：前の単位の開発Todoがすべて完了し、PRが `main` にマージされ、テストが通っていることを確かめる。満たしていなければ着手せずに報告する。
2. **ベースラインの取得**：変更前に次を実行し、テスト件数と結果を記録する。既存の失敗があれば、今回の変更と区別して記録する。
   - backend：`ruff check .`、`pytest`
   - frontend：`npm run lint`、`npm run build`（型チェックを含む）、`npm test`
3. **全量走査と影響範囲の確定**：全ソースコードと関連文書を走査し、影響範囲表（ファイル／変更内容／理由／対応するD-ID）を作る。
4. **横展開チェックリストの作成**：漏れを機械的に見つけるための検索語（grep）と、期待する結果を列挙する。少なくとも次の観点を含める。
   - 追加・変更した列挙型の値を扱うすべての分岐・対応表（backendとfrontendの両方）
   - 画面文言（`ja.json` と `en.json` の両方）
   - APIの型（`npm run generate:api-types` で再生成し、手書きの型が残っていないこと）
   - 全データのエクスポート・取り込み（`DATA_SCHEMA_VERSION`、旧版の取り込み）
   - `app_setting` の初期値（`init/seed_data.py`）と設定画面
   - アプリ内ヘルプ（`help_content.json`）と各設計書
5. **食い違いの扱い**：設計書と現行コードの食い違いや、設計書で決まっていない点のうち仕様に影響するものは、推測で補わない。一覧にして報告し、判断を仰ぐ（その部分の実装は止める）。仕様に影響しない実装上の詳細は、設計書の意図に沿って決め、理由を開発Todoに残す。
6. **脅威分析**：`/threat-model` スキルでSTRIDE分析を行い、対策を開発Todoに反映する。
7. **開発Todoの作成**：`docs/開発Todo_スケジュール・ガントチャート_単位N_v1.0.md`（Nは単位の番号）を作る。チェックボックス形式とし、各項目に対応するD-IDを付ける。末尾に追跡表（D-ID → 実装箇所 → テスト名）を設ける。
8. **回帰の網を先に張る**：今回変更する既存の振る舞いについて、変更前に現在の挙動を固定するテスト（特性テスト）を追加し、変更前のコードで通ることを確かめてから実装に入る。

### 15.2 実装中

9. 開発Todoの順に小さく進め、区切りごとに関連するテストを実行する。
10. 既存テストの削除・skip・期待値の変更は原則として行わない。やむを得ない場合は、理由と本書の根拠（D-ID）を開発Todoに記録する。
11. 単位の範囲外は変更しない。範囲外の不具合を見つけた場合は、修正せずに報告に載せる。

### 15.3 完了時

12. 全テストを再実行し、ベースラインと比べる（件数の増減と、新たな失敗がないこと）。
13. CLAUDE.mdの「コミット前チェック」をすべて実施する（該当する観点別レビューのエージェントを含む）。
14. 横展開チェックリストの検索をやり直し、漏れがないことを確かめる。
15. 追跡表のすべてのD-IDが、実装とテストに対応していることを確かめる。
16. **独立レビュー**：本書の該当章と今回の差分だけを渡した別のサブエージェント（実装の経緯を知らない状態）に、仕様の漏れ・デグレのリスク・横展開の漏れをレビューさせ、指摘に対応する。
17. 単位ごとに指定した文書を更新する。
18. 開発Todoの末尾に、次の単位への引き継ぎ事項を記載する。
19. 次の形式で報告する。
    1. 実施内容の要約
    2. ベースラインとの比較（テスト件数と結果）
    3. 追跡表
    4. 既存テストを変更した場合は、その内容と理由
    5. 報告が必要な食い違い・範囲外の不具合
    6. 次の単位への引き継ぎ事項
