## 3. 設計方針

### 3.1 派生値を保存しない

以下は一切保存せず、参照時に算出する。これが本アプリの中核的な設計判断である。

| 派生値 | 算出根拠 |
| --- | --- |
| 日次ノルマ | 残量、残計画日数、負荷係数 |
| 総作業量 | 総量、予定周回数 |
| 残量 | 総作業量、実績の累計 |
| 現在周回 | 総量、実績の累計 |
| 実効速度 | 実績の投下時間と完了分量（周回別） |
| 必要速度 | 残量、残計画日の利用可能時間 |
| 完了予測日 | 残量、実効速度、計画日の分布 |
| バッファ消費率 | バッファ日の実績有無 |

日次ノルマを保存しないことにより、未達分の繰り越し処理が不要になる。残量を残計画日で再配分する式が毎日評価されるため、負荷の平準化が構造的に成立する。

### 3.2 基準値のみ履歴として保存する

警告判定（日次ノルマが初期ノルマの一定倍率を超えたか）には比較対象が必要である。この基準値は `plan_baseline` テーブルに履歴として保存する。

リプラン実施時に新しい基準行を追加することで、リプラン後は新しい計画が基準となり、過去の乖離を引きずらない。

**この履歴は、総括レポートの分析根拠としても用いる。** いつ、何回、どの契機で計画を修正したかという情報は、合否要因の分析において最も重要な材料である。

### 3.3 不変性の担保

日次報告および学習実績は、確定後の更新をアプリケーション層で拒否する。データベース制約では表現せず、サービス層のガードとして実装する。

### 3.4 外部識別子の保持

AI基盤側に作成された会話の識別子はローカルに保持する。一覧取得APIによる検索を毎回行わない。これは通信回数の削減と、頻度制限への配慮による。
