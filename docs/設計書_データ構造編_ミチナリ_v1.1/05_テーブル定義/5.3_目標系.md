**制約**

- リソース配分は `goal_slot_allocation`（5.2）が保持する。配分の上限制約・カテゴリ別の対象範囲・一時停止時の扱いは同テーブルの制約を参照する
- `archived_at` を設定できるのは `status` が `ACTIVE` 以外（`DRAFT` / `PAUSED` / `CLOSED_WITH_RESULT` / `CLOSED_WITHOUT_RESULT`）の場合のみ。アプリケーション層で検証する（仕様書7.1.1、要件定義書R-61）
- 物理削除（`DELETE /goals/{id}`）は、実行中（ACTIVE）以外のすべての状態（アーカイブ済みを含む）で許可する。関連データは常にカスケード削除する（1.1改32。旧 `DELETE /goals/{id}/archived` と cascade_study_logs の選択は廃止）
- `archived_at` が設定済みの goal は、開始（`activate_goal`）・再開（`resume_goal`）を許可しない。先にアーカイブ解除（復元）が必要（仕様書7.1.1）

#### 状態遷移履歴（goal_status_history、1.1改32）

報告率・連続報告日数から、一時停止・中断の期間を除外するために、目標の状態が変わるたびに1行追加する。

| 列 | 型 | NULL | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | NOT NULL | 主キー |
| goal_id | INTEGER | NOT NULL | 目標ID（goal.id、ON DELETE CASCADE） |
| from_status | TEXT | NULL | 変更前の状態。作成時の1行目のみNULL |
| to_status | TEXT | NOT NULL | 変更後の状態（GoalStatus） |
| changed_at | DATETIME | NOT NULL | 変更日時（UTC） |

既存の目標の初期履歴は、既存の時刻列（作成日時・開始日時・終了日時・更新日時）から、確実に分かる遷移だけを復元する（移行 5e0f3b7c2a91）。
- `category` は作成後の変更を許容しない。種別を変えたい場合は目標を作り直す（仕様書6.2）

**読書目標（category=READING）のクローズ**

読書に固有の `BookStatus` は設けない。読了は `status='CLOSED_WITH_RESULT'`、中断は `status='CLOSED_WITHOUT_RESULT'` として、資格試験と同じ `GoalStatus` をそのまま用いる。ただし読書では `exam_result` を作成しない（`CLOSED_WITH_RESULT` は「合否結果を伴うクローズ」ではなく「目標に対する成果を伴うクローズ」という意味に拡張して用いる）。クローズ時に生成する `goal_retrospective` が、資格試験では総括レポート、読書では読了レポートとして機能する（17.5、17.7参照）。

**仕事目標（category=WORK）のクローズ**

仕事目標も固有のステータス列は設けず、資格試験・読書と同じ `GoalStatus` をそのまま用いる。1目標＝1案件（プロジェクト）に対応するため、案件が終了すればクローズし、次の案件は新しい goal を作成する（要件定義書R-72）。納品等の成果を伴う終了は `status='CLOSED_WITH_RESULT'`、中止・打ち切りは `status='CLOSED_WITHOUT_RESULT'` とする。読書と同様に `exam_result` は作成しない。複数の仕事目標を同時に進行中とすることを妨げない（既存の複数目標並行の仕組みをそのまま用いる）。

仕事目標は読書と異なり、クローズ時に「読了レポート」に相当する1回きりのレポートは生成しない。かわりに、進行中の間は月次・半期という周期で `goal_retrospective` を生成し続ける（`period_type`／`period_key`、5.4「goal_retrospective（総括レポート／読了レポート／定期報告）」参照）。クローズ操作自体は、進行中の月次・半期報告の生成契機とは独立している。

**有効受験日の導出**

算出処理で用いる有効受験日は以下とする。保存しない。

- `exam_date_type` = FIXED のとき `exam_date_fixed`
- `exam_date_type` = RANGE のとき `exam_date_from`

期間指定時に最も早い日を採用するのは、予測を保守側へ倒すためである。

**v1.0からの変更点**

- `planned_cycles` を追加した
- `current_cycle` を削除した。現在周回は累積完了量から導出する派生値であり、保存すると実績との不整合が生じ得るため

**総作業量と現在周回**

```
総作業量 ＝ total_amount × planned_cycles
現在周回 ＝ floor(累積完了量 ÷ total_amount) + 1
```

いずれも保存しない。

**締切の自動導出**

`due_date_is_manual` が false のとき、`due_date` は紐づく exam_subject の有効受験日のうち最も早い日の前日として算出し、保存する。ただし算出結果が教材の開始日より前になる場合は開始日を締切とする（開始日を下限とするクランプ。受験日を開始日以前・当日に設定した場合の例外処置、1.1改30）。この下限クランプは受験日自体を上限とし、開始日が受験日より後（受験日を過ぎてから学習を始める矛盾した入力）の場合にまで締切を引き上げることはしない。この場合は締切が開始日より前のまま残り、教材作成・更新のバリデーション（`start_date > due_date`）で拒否される。以下の契機で再計算する。

- 教材と科目の紐付けが変更されたとき
- 紐づく科目の受験日が変更されたとき

自動導出値を保存するのは、締切がガントチャート表示や締切超過判定など多数の箇所で参照されるためである。派生値を保存しない原則の例外にあたるが、再計算契機が限定的かつ明確であるため許容する。

**book（書籍）**

`category=READING` の goal に対して、`exam_subject` と `material` を統合した位置づけの子テーブルとして1件登録する。

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| goal_id | INTEGER | NOT NULL, UNIQUE, FK → goal.id | — |
| title | TEXT | NOT NULL | 書名 |
| author | TEXT | NULL | 著者 |
| total_pages | INTEGER | NOT NULL | 総ページ数（1以上。進捗率算出用） |
| start_date | DATE | NOT NULL | 読書開始日 |
| due_date | DATE | NOT NULL | 読了目標日 |
| created_at | DATETIME | NOT NULL | — |
| updated_at | DATETIME | NOT NULL | — |

`goal_id` にUNIQUE制約を持たせ、1目標1冊を保証する（要件定義書R-70、仕様書6.2）。`material` と異なり、`due_date` は `exam_subject` の受験日から自動導出せず、常に利用者が直接入力する（読書には受験日に相当する外部制約が存在しないため）。

`total_pages` は必須とする（1.1改20、要件定義書R-70改訂）。読書進捗（ロジック・プロンプト編21.2）の進捗率を常に算出できるようにするためであり、「総ページ数が未入力の書籍ではページ進捗を表示しない」という旧仕様を廃止したことに伴う。既存行が NULL の場合は、その書籍に記録済みの `reading_log.current_page` の最大値（1件も無ければ1）を暫定値として補填する（総ページ数は書籍固有の事実でありシステムが推定できないため、進捗率が100%を超えない最小限の値を置き、利用者が書籍編集で訂正する前提とする）。

総ページ数を後から現在ページより小さい値へ引き下げる訂正は許容する。誤記の訂正手段を残すためであり、確定済みの日次報告は変更できず現在ページを先に直せないケースがあるためである。この場合 `current_page > total_pages` が成立しうるが、進捗率は算出側で100%にクランプする（5.4 `reading_log` 参照）。

独自の状態列（status／completed_at）は持たない。読了・中断は `goal.status` で表現する（5.3「読書目標（category=READING）のクローズ」参照）。

**work_assignment（案件情報）**

`category=WORK` の goal に対して、`book` と同じ位置づけ（`exam_subject` と `material` を統合した子テーブル）で1件登録する。

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| goal_id | INTEGER | NOT NULL, UNIQUE, FK → goal.id (CASCADE) | — |
| client_name | TEXT | NULL | 取引先・案件の呼称（任意） |
| expected_content | TEXT | NOT NULL | 営業・顧客から事前に伝えられた想定業務内容 |

| created_at | DATETIME | NOT NULL | — |
| updated_at | DATETIME | NOT NULL | — |

`goal_id` にUNIQUE制約を持たせ、1目標1案件を保証する（要件定義書R-72）。`book` と異なり `due_date` を持たない。仕事の案件は納期が未定のことが多く、読書における読了目標日のような必須の外部制約が存在しないためである（要件定義書R-73）。

`expected_content` は登録後も更新可能とし、更新は上書きとする（変更履歴は保持しない、要件定義書R-73）。実際に着手した業務内容は日次記録（`work_log`）の積み上げから把握し、想定内容との比較・解釈はAIに委ねる（利用者に構造化した差分入力をさせない設計判断、要件定義書6.11本文）。

独自の状態列（status／completed_at）は持たない。案件の終了（成果あり／なし）は `goal.status` で表現する（5.3「仕事目標（category=WORK）のクローズ」参照）。
