### 5.8 認証情報の保管

**方針：AI基盤の開発キットが提供する仕組みに委ねる。**

開発キットは、設定に基づきPAT（Personal Access Token）およびトークンをファイルとして管理する機能を備えている。アプリケーション側で独自の資格情報管理を実装しない。

**認証方式はPATを主とする。** 開発キットの現行の公式利用ガイドは、Host＋PATによる認証を標準の方法として案内している。ブラウザ経由のOAuth／デバイスコード認証（EntraID）は、開発キット内部にフォールバック経路として残るのみであり、PATが設定されていれば優先して使用される。

| 項目 | 方針 |
| --- | --- |
| PAT・トークンの保存 | 開発キットの設定に従う（`~/.newtonx/config.json` 等）。`app_setting` には保存しない |
| PATの入力 | 設定画面（SC-11）でHostとPATを入力すると、開発キットの設定へ反映する。Hostは`app_setting: ai.host`にも保存し、設定画面の表示値と一致させる（PATは`app_setting`へ保存しない） |
| 保存先パス | 開発キットの既定値を使用する。設定画面に表示のみ行う |
| 起動時の確認 | Host・PATが設定済みかを確認し、認証済みとして扱う |
| フォールバック認証 | PAT未設定・無効時のみ、設定画面からブラウザ経由の認証フローを実行できる |
| クライアントへの公開 | 認証状態の真偽値のみを返す。PAT・トークンは送出しない |

**v1.0からの変更理由**

v1.0では独自にOS資格情報ストアへ保管する方針としていたが、開発キットが独自にPAT・トークンを管理する仕様であるため、二重管理は認証状態の不整合を招く。開発キットの仕組みに一本化する。

**v1.1（本改訂）での変更理由**：当初はブラウザ経由のOAuthフローを認証の主経路として設計していたが、実際に導入した開発キットの公式利用ガイドを確認した結果、PATが現行の標準的な認証方式であることが判明したため、主経路をPATに改めた。

**フォールバック認証フローの実行方式**

ブラウザ経由の認証フローは起動して待機するため、APIリクエストのスレッドをブロックする可能性がある。バックグラウンドスレッドで実行し、クライアントは認証状態をポーリングして完了を検知する。
