### 5.4 記録系

**daily_record（日次記録）**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| record_date | DATE | NOT NULL, UNIQUE | 対象日 |
| exam_record_state | TEXT | NULL | RecordState（資格試験）。NULLはそのカテゴリを未着手であることを表す |
| exam_reported_at | DATETIME | NULL | 資格試験の報告確定日時 |
| reading_record_state | TEXT | NULL | RecordState（読書） |
| reading_reported_at | DATETIME | NULL | 読書の報告確定日時 |
| work_record_state | TEXT | NULL | RecordState（仕事） |
| work_reported_at | DATETIME | NULL | 仕事の報告確定日時 |
| created_at | DATETIME | NOT NULL | — |

日次記録は日付単位で一意とする。目標単位ではない。複数目標が同時進行する場合も1日1レコードとし、実績は study_log 側で教材ごとに、日記は daily_goal_diary 側で目標ごとに保持する。

確定状態（`*_record_state`/`*_reported_at`）はカテゴリ（EXAM/READING/WORK）ごとに独立した3組の列で保持する（1.1（改16）、仕様書1.1（改13））。従来は`record_state`/`reported_at`の単一組だったため、1カテゴリを確定すると同日の他カテゴリも一括で報告済になっていた（資格試験・読書・仕事の目標を同時進行する利用者が、他カテゴリの入力・確定を継続できなくなる問題）。値がNULLのカテゴリは、その日一度もそのカテゴリを操作していないことを表す。カレンダー・ダッシュボード等が必要とする日単位の単一状態は、`record_service.aggregate_record_state`が3カテゴリの値から都度算出する派生値であり、列としては保持しない（未着手カテゴリは判定から除外し、着手した全カテゴリが報告済なら報告済、1つでも進捗のみ登録済があれば進捗のみ登録済とする）。

`GET /records/{date}/quota`（QuotaItemRead）・`GET /dashboard`（TodayQuotaEntryRead）が返す教材別の日次ノルマ一覧には、表示専用の派生値として `goal_id`・`goal_name` を含む（DBには保存しない。`material.goal_id` から都度算出する）。日次報告SC-06・ダッシュボードSC-01はいずれもこの値を用いて画面上部の目標タブの選択対象を絞り込み、選択中の1目標分のみを表示する（仕様書6.5・6.1、1.1（改17）でダッシュボードもグルーピング表示から目標タブ方式に統一。未決事項L-04参照）。

`exam_record_state`/`reading_record_state`/`work_record_state`は、対応するカテゴリがREPORTEDの場合、そのカテゴリに関連する study_log・reading_log・work_log・daily_goal_diary の更新を拒否する（他カテゴリが未確定であれば引き続き更新できる）。

`record_date` は、設定された1日の境界時刻に基づいて決定される論理的な日付である。

**daily_goal_diary（日記・目標別）**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| daily_record_id | INTEGER | NOT NULL, FK → daily_record.id (CASCADE) | — |
| goal_id | INTEGER | NULL, FK → goal.id (CASCADE) | 対象目標 |
| diary_body | TEXT | NULL | 以前の日記本文（旧仕様の質問形式・自由記述で保存された本文。1.1（改30）以降の新規入力では空） |
| diary_learned | TEXT | NULL | 今日学んだこと・理解したこと（資格試験の日記入力欄の主役。1.1（改30）） |
| created_at | DATETIME | NOT NULL | — |
| UNIQUE(daily_record_id, goal_id) | | | 1日1目標につき1件 |

日記は元々 daily_record 直下の共有フィールド（diary_body・diary_learned）だったが、複数目標が同時進行する日に「どの目標についての記述か」を区別できず、週次要約・ナレッジエクスポートで他目標の日記が混入する実害があったため、目標別テーブルへ分離した（未決事項L-04、対応は9a1c3e7d5b2fマイグレーション）。

`goal_id` は NULL を許容する。これは分離時のデータ移行で、複数目標にまたがり帰属先を機械的に特定できなかった過去の日記（study_logの無いバッファ日等）を失わずに保持するための安全弁であり、通常の新規入力では常に目標が指定される。

対象目標の入力欄は、当日のノルマ有無に関わらず「選択中の資格試験目標」について表示する（先行着手した内容を自由記述できる逃げ道を維持するため、仕様書6.5）。着手中（ACTIVE）の目標が2件以上ある場合、対象目標は画面上部の目標タブで選択する（仕様書6.5）。

**study_log（学習実績）**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| daily_record_id | INTEGER | NOT NULL, FK → daily_record.id | — |
| material_id | INTEGER | NOT NULL, FK → material.id | — |
| minutes_spent | INTEGER | NULL | 投下時間（分）。**`study_log_slot_time` の合計値**（後述） |
| amount_completed | REAL | NOT NULL | 完了分量 |
| cycle_number | INTEGER | NOT NULL | 周回数 |
| quality_value | REAL | NULL | 品質指標（0〜100に正規化済み） |
| created_at | DATETIME | NOT NULL | — |

**制約**：`daily_record_id` と `material_id` の組み合わせは一意とする。

`minutes_spent` が NULL または 0 のレコードは、実効速度の算出から除外する。この扱いにより、進捗のみ登録で時間を入力しなかった日が速度を汚染しない。

`minutes_spent` は利用者が直接入力する値ではなく、時間スロットごとの入力（`study_log_slot_time`）の合計としてサービス層が設定する（仕様書6.5「時間枠ごとの投下時間の入力」）。合計値を列として持つのは、実効速度（ロジック・プロンプト編8.1）・週次集計・ナレッジエクスポートがいずれも教材単位の合計のみを必要とし、内訳を都度結合すると同一の集約が多数の照会箇所へ分散するためである。合計の更新経路はサービス層の実績登録処理1箇所に限定し、内訳との不整合を防ぐ。スロットの入力が1件も無い場合は NULL とする（0分ではない）。

**study_log_slot_time（学習実績の時間枠別内訳）**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| study_log_id | INTEGER | NOT NULL, FK → study_log.id (CASCADE) | — |
| slot_id | INTEGER | NULL, FK → resource_slot.id (SET NULL) | 時間枠。NULL は「記録後にそのスロットが削除された」ことを表す |
| minutes | INTEGER | NOT NULL | その時間枠での投下時間（分）。1以上 |

**制約**：`study_log_id` と `slot_id` の組み合わせは一意とする。

配分していないスロットの行も持てる（仕様書6.5「未配分スロットの追加」）。0分の入力は行を作らない。

`slot_id` を NULL 許容とし `ON DELETE SET NULL` とするのは、**スロットの削除を許容しつつ実績を失わないため**である（要件定義書R-87、仕様書NT-09。RESTRICT にすると過去に一度でも使ったスロットを削除できなくなり、「生活の変化を先に登録できる」という要件と矛盾する）。内訳の帰属先は失われるが、実効速度が用いる `study_log.minutes_spent`（合計）は影響を受けない。NULL を「帰属不明」として残す扱いは `chat_message.goal_id`・`daily_goal_diary.goal_id` と同じ安全弁の考え方である。スロット削除で `slot_id` が NULL になった行が同一 `study_log` に複数生じうるが、いずれも帰属不明として同義に扱う（合計値には影響しない）。

`quality_value` は正規化後の値を保存する。主観的手応えの5段階は保存時に 20/40/60/80/100 へ変換する。

`cycle_number` は利用者が入力する。既定値として算出値を提示するが、途中から次の周回へ移る運用に対応するため上書きを許容する。

**reading_log（読書記録）**

`study_log` の読書版。定量実績ではなく、想起した内容を自由記述で保持する。

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| daily_record_id | INTEGER | NOT NULL, FK → daily_record.id | — |
| book_id | INTEGER | NOT NULL, FK → book.id | — |
| recall_body | TEXT | NOT NULL | 今日読んだ内容の想起（自由記述） |
| minutes_spent | INTEGER | NULL | 読書時間（分）。**`reading_log_slot_time` の合計値** |
| current_page | INTEGER | NULL | 現在ページ（任意。進捗スナップショット） |
| created_at | DATETIME | NOT NULL | — |

**制約**：`daily_record_id` と `book_id` の組み合わせは一意とする（`study_log` と同じ制約パターン）。

`study_log` と異なり `cycle_number`・`quality_value` は持たない。品質指標の算出対象ではないためである。`recall_body` は必須とし、`minutes_spent`・`current_page` は任意とする（要件定義書R-65）。

ページに関する列は `current_page` のみとする。「読んだページ数」（旧 `pages_read`）は廃止した（1.1改20）。利用者がその日に読んだページ数を毎日記憶していられず、かつ読書は定量的な進捗管理を行わない目標（R-71）であるため保持する意味がないためである。`current_page` は `book.total_pages` 以下であることをサービス層（`record_service`）で検証する（進捗率が100%を超えないようにするため）。ただし総ページ数を後から現在ページより小さい値へ引き下げる訂正は許容するため（`book_service.update_book`）、既存データが上限を超える状態は成立しうる。この場合の進捗率は算出側で100%にクランプする。

`minutes_spent` は読書もリソース配分の対象となったこと（要件定義書R-64）に伴い追加した。ただし読書は実効速度・完了予測を持たないため、この値は集計・表示・AIへの文脈提供にのみ用い、速度算出には用いない（R-71）。合計値として保持する理由と更新経路の限定は `study_log.minutes_spent` と同じ。

**reading_log_slot_time（読書記録の時間枠別内訳）**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| reading_log_id | INTEGER | NOT NULL, FK → reading_log.id (CASCADE) | — |
| slot_id | INTEGER | NULL, FK → resource_slot.id (SET NULL) | NULL の意味は `study_log_slot_time` と同じ |
| minutes | INTEGER | NOT NULL | その時間枠での読書時間（分）。1以上 |

**制約**：`reading_log_id` と `slot_id` の組み合わせは一意とする。`study_log_slot_time` と同型・同方針。

`study_log` の仕事版。定量実績ではなく、当日の業務内容を自由記述1本で保持する。`reading_log` と同型だが、構造化フィールド（人間関係・成果・学び等をタグ分けした個別列）は持たない（要件定義書6.11本文、実際の内容はAIが日次記録の積み上げから解釈する設計のため）。

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| daily_record_id | INTEGER | NOT NULL, FK → daily_record.id (CASCADE) | — |
| work_assignment_id | INTEGER | NOT NULL, FK → work_assignment.id | — |
| body | TEXT | NOT NULL | 当日の業務内容（自由記述） |
| created_at | DATETIME | NOT NULL | — |

**制約**：`work_assignment_id` と `daily_record_id` の組み合わせは一意とする（`study_log`・`reading_log` と同じ制約パターン）。

`reading_log` と異なり `current_page` に相当する数値項目も持たない。日次報告での入力は自由記述1本のみとし、数値実績の入力は必須としない（要件定義書R-75）。

**chat_message（AI対話）**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| id | INTEGER | PK | — |
| daily_record_id | INTEGER | NOT NULL, FK → daily_record.id | — |
| goal_id | INTEGER | NULL, FK → goal.id（ondelete=CASCADE） | 対話の宛先目標。Phase26で追加（1.1改18） |
| purpose | TEXT | NOT NULL, DEFAULT 'DAILY_FEEDBACK' | AiPurpose |
| role | TEXT | NOT NULL | ChatRole |
| content | TEXT | NOT NULL | 発言内容 |
| sequence | INTEGER | NOT NULL | 会話内の順序（用途を問わずdaily_record全体で採番を共有し、表示順を一貫させる） |
| created_at | DATETIME | NOT NULL | — |

`purpose`はPhase16（読書AI連携）で追加した。同一`daily_record`に資格試験（DAILY_FEEDBACK）と読書（DAILY_FEEDBACK_READING）の対話が混在しうるため、対話履歴（`{{conversation_history}}`）への注入時にpurposeで絞り込み、用途間の文脈混入を防ぐ。既存行は`DAILY_FEEDBACK`として遡及設定する（読書機能導入前は他の用途が無かったため）。

`goal_id`はPhase26（1.1改18）で追加した。導入前は同一カテゴリの目標が2件以上同時進行していても、日次フィードバックはカテゴリ単位で1本の会話を共有していた（`ai_conversation.goal_id=NULL`、未決事項L-07で意図的な設計と位置づけていた）が、分析タブ「成長記述」で全目標の応答が混在する不具合を契機に目標単位分離へ方針転換した。移行前の行は`goal_id=NULL`のまま引き継ぐ（`daily_message`のc7d391a6f0e5マイグレーションと同じ安全弁、どの目標宛てか技術的に判別不能なため）。NULLの行は分析タブ「成長記述」で「未割り当て」として表示し、利用者がプルダウンから目標を手動で割り当てられる（`purpose`に対応するカテゴリと異なる目標への割り当ては拒否）。

**週次要約の材料としての参照（S08 G5、2026-10-20合意）**：role=USERの行は、週次要約生成時に`{{week_chat}}`（ロジック・プロンプト編17.3・17.11・17.12）の材料としても参照される。role=ASSISTANTの行・goal_id=NULLの行（移行前のレガシー行）は対象外。本表の列構成自体は変更しない（既存列のみで実装、新規列・新規テーブル不要）。

**5.6 振り返り（テーマ累積）（1.1（改31））**

| テーブル | 役割 | 主な制約 |
|---|---|---|
| recap_entry | 分類対象とした1件の報告への参照（本文は複製しない）。source_kind（DIARY／READING）・source_id・record_date・classified_at | (source_kind, source_id)で一意。goal_idに索引。goal削除でCASCADE |
| recap_theme | goal単位のテーマと累積本文（name・body）。テーマ名は同一goal内で一意（name最大100文字） | (goal_id, name)で一意。goal削除でCASCADE |
| recap_theme_link | テーマと報告の対応（1報告が複数テーマに属しうる） | (theme_id, entry_id)で一意。theme・entryの削除でCASCADE |

既存の`diary_learned`・`diary_body`（日記）と`recall_body`（想起記録）を参照し、本文は複製しない。資格試験の振り返り本文は`diary_learned`を優先し、未入力の旧データだけ`diary_body`を使う（両者の優先順位はモデル層の`diary_text_expr`に1か所集約）。

ナレッジエクスポート（7.1）では、テーマを`recap_themes`（name・body・entries）として出力する。匿名化版では出力しない（日記本文と同様）。

するため、スキーマ変更は発生しない。詳細はロジック・プロンプト編15.4を参照。

| business_summary | TEXT | NULL | 業務内容（案件内容）の要約。WORKかつperiod_type非NULLの行でのみ使用。AI生成、レビュー画面で編集可 |
| achievement_score | INTEGER | NULL | 目標の達成度（1〜5、ロジック・プロンプト編17.9の判定基準）。WORKの月次報告・半期評価でのみ使用。比較対象となる`target_goal_text`が無い初回はNULLのまま |
| achievement_reflection | TEXT | NULL | 達成状況と進捗に関する振り返り。WORKかつperiod_type非NULLの行でのみ使用。AI生成、レビュー画面で編集可 |
| next_goal_text | TEXT | NULL | 来期への目標提案。WORKかつperiod_type非NULLの行でのみ使用。AI生成後、レビュー画面で利用者が編集できる。この値が次期生成時にそのまま次の行の`target_goal_text`として複製される |
| report_notes | TEXT | NULL | 報告・連絡事項。WORKの月次報告でのみ使用（半期評価では対象外。要件定義書R-79）。特に無ければ空文字 |
| edited_at | DATETIME | NULL | 利用者が生成後にレビュー画面で内容を編集した日時。NULL＝AI生成のまま未編集 |
| generated_at | DATETIME | NOT NULL | 生成日時 |

EXAM・READINGでは、再生成を許容するため goal に対して複数レコードを持てる構造とする（最新のものを既定で表示、匿名化版は別レコード）。

**読書目標での流用**：新規テーブルを設けず、本テーブルをそのまま「読了レポート」として用いる（`goal.category=READING`）。生成契機・匿名化・再生成の仕組みは資格試験の総括レポートと共通。内容の違いはプロンプト（AiPurpose.GOAL_RETROSPECTIVE_READING、ロジック・プロンプト編17.7）にのみ起因する。`period_type`以下の追加列はNULLのまま用いない。

**仕事目標での流用（period_type以下の追加列）**：仕事目標も新規テーブルを設けず、本テーブルを「月次報告」「半期評価」の双方に流用する（`goal.category=WORK`）。読書との違いは、クローズ時の1回きりの生成ではなく、案件が進行中の間、月次・半期という周期で生成し続ける点にある（要件定義書6.11「定期報告型」）。同一goalに対し`period_type`／`period_key`の異なる複数レコードが並存する（例：2026-08分の月次報告、2026-09分の月次報告、2026-H1の半期評価が同一goalに同時に存在しうる）。

**WORKの行は、EXAM／READINGと異なり「1期間につき1行のみ」を保つ**（`is_anonymized=false`の行に限る。匿名化版は別途、エクスポート時に都度生成する）。月次報告は監査目的の履歴ではなく随時修正しうる実務文書であるという性質上、再生成・利用者による編集のいずれも既存行への上書き（`target_goal_text`以下の構造化列を更新し、そこから`body`を再組み立てし、`edited_at`を編集時のみ設定）として扱い、EXAM／READINGのように新規レコードを追加しない。これによりアプリ側は常に「そのgoalのその期間の行は高々1件」を前提にでき、`goal_id`・`period_type`・`period_key`・`is_anonymized`の組み合わせで一意に1行を特定できる。
**報告月（派生値）**：`reporting_period_key`は保存せず、`period_key`の翌月として応答時に導出する（月次報告のみ。半期評価はnull）。対象月の翌月を報告月とすることは要件定義書R-78に従う。`period_key`が変われば報告月も連動するため、列として保存すると不整合の原因になる（CLAUDE.mdの派生値は保存禁止）。

**制約**：`goal_id` と `period_type` と `period_key` と `is_anonymized` の組み合わせは、WORKでは常に一意（アプリケーション層でupsertとして扱う）。EXAM／READINGでは`period_type`・`period_key`が共にNULLであるため、この組み合わせは目標ごとに複数行が該当し、一意制約の対象外とする（従来どおり無制限に再生成できる）。

**「最新の総括レポートを取得する」ロジックの拡張**：既存の`get_latest_retrospective`（goal_idと`is_anonymized`のみで絞り込み、`generated_at`降順で先頭を返す実装）は、`period_type`／`period_key`の指定がある場合はその条件でも絞り込めるよう拡張する（例：「このgoalの2026-09分の月次報告」を取得する用途。WORKでは該当行が高々1件のため実質的に完全一致の取得となる）。指定がない場合は従来どおり`period_type IS NULL`のレコード（EXAM総括レポート・READING読了レポート）を対象とする。実装はPhase22（仕事AI連携）で行う。
