## 11. 判定ロジック

### 11.1 警告判定（NT-01）

```
baseline(m) = plan_baseline のうち material_id = m かつ
              effective_from ≤ T を満たすレコードの中で
              effective_from が最大のもの

条件： quota(m, T) / baseline_daily_quota(baseline(m))
       ≥ 設定値 threshold.warning_ratio（初期値 1.20）
```

`type(T)` が PLAN でない日は判定しない。バッファ日にはノルマが存在しないためである。

### 11.2 強制リプラン判定（NT-02）

```
条件： overrun_days(m) > 設定値 threshold.replan_overrun_days（初期値 3）
```

`speed_eff(m)` が算出不能な場合は判定しない。

### 11.3 二段階構成の意図

| 段階 | 検知対象 | 意味 |
| --- | --- | --- |
| 警告（NT-01） | ノルマの上昇率 | ペースの乱れ。まだ挽回可能な段階 |
| 強制リプラン（NT-02） | 完了予測日の超過 | 合格可能性の毀損。計画の修正が必要 |

警告は「遅れている」ことを、強制リプランは「このままでは間に合わない」ことを示す。前者はバナー表示にとどめ、後者はモーダルで目標編集画面へ誘導する。

実効速度が向上すれば、負債があっても強制リプランは発火しない。逆に毎日ノルマを達成していても、初期の総量見積もりが甘ければ発火する。判定基準を「合格に間に合うか」に置いているためである。

### 11.4 締切超過判定（NT-06）

```
条件： T > D(m) かつ R(m) > 0 かつ material.is_active = true
```
