## 21. 読書目標の扱い

### 21.1 適用範囲

本文書の第3〜14章は、`goal.category = EXAM`（資格試験）の目標を対象とした算出ロジックである。`category = READING`（読書）の目標には適用しない（要件定義書R-71、仕様書6.10）。読書目標が用いる算出ロジックは本章にまとめる。

第3章（1日の境界時刻の解決）は日次記録全体に関わる共通基盤であり、読書目標にもそのまま適用する。「今日」の判定は `GET /records/today` に一元化されており、読書に限って例外を設けない。

第15章（週次要約の生成）の対象判定（15.2手順3「その週にstudy_logが1件以上存在する目標を対象に生成」）は、当初読書目標にはstudy_logが存在しないため自動的に対象外だったが、L-11（2026-09-16、21.4参照）で読書用週次要約（17.11）を新設し、`weekly_summary_service.py`の`_CategorySpec`によりカテゴリ別の対象判定（読書はreading_logの有無）を注入する形へ一般化した。読書目標も週次要約の対象に含まれる。

**資格試験用AI機能との切り分け**：日次報告フィードバック（17.2 DAILY_FEEDBACK）・今日の一言（17.4 DAILY_MESSAGE）が対象とする「進行中の目標」は、`ai_context_exam.list_active_exam_goals`によりEXAMのみへ限定する（Phase15で対応）。限定しない場合、`{{goal_summary}}`に読書目標が「試験科目未登録」という誤った文脈で混入するためであり、読書用のDAILY_FEEDBACK_READING（17.6）が別途存在する以上、DAILY_FEEDBACK・DAILY_MESSAGEは恒常的にEXAM専用として扱う（読書用の「今日の一言」相当機能は設けない設計、要件定義書6.10）。**この「DAILY_MESSAGEはEXAM専用」という方針は、2026-09-03の仕事目標追加により見直された。仕事目標はDAILY_MESSAGEの対象に含める（要件定義書R-77）。詳細は22.1参照。**

`POST /goals/{id}/retrospective`（`retrospective_service.generate_retrospective`）はPhase16で `goal.category` に応じてGOAL_RETROSPECTIVE（17.5）／GOAL_RETROSPECTIVE_READING（17.7）へ分岐する実装とした。Phase15時点で暫定的に設けていた「READING目標への呼び出しをVALIDATION_ERRORで拒否するガード」はこの分岐に置き換えて解消済みである（書籍が未登録のREADING目標に対する呼び出しのみ、引き続きVALIDATION_ERRORとする）。

**対話履歴の分離（chat_message.purpose、Phase16）**：資格試験（DAILY_FEEDBACK）と読書（DAILY_FEEDBACK_READING）の対話は、同一日の同一`daily_record`に混在しうる。会話自体はAiPurpose／ConversationScopeが異なるため`ai_conversation`側では自然に分離されるが、`chat_message`はdaily_record単位のフラットな一覧であるため、`purpose`列（データ構造編5.4）を追加し、対話履歴（`{{conversation_history}}`）への注入時にpurposeで絞り込むことで、用途間の文脈混入を防いでいる。AI対話の実行エンドポイントも`POST /records/{date}/chat`（資格試験）と`POST /records/{date}/reading-chat`（読書）に分離した（データ構造編6.2「AI対話エンドポイントの分離について」）。

### 21.2 読書進捗（BookRead）の算出

教材の派生値（総作業量・現在周回・残量・進捗率）が独立エンドポイントではなく`MaterialRead`に
埋め込まれているのと同じ方針で、書籍の派生値も独立エンドポイントを設けず`BookRead`
（`GET /goals/{id}`、`PATCH /books/{id}`等の応答）に埋め込む（データ構造編6.2、Phase15実装）。

```
remaining_days = book.due_date − T

last_reading_date = MAX(daily_record.record_date)
                     （対象bookのreading_logが存在する daily_record のうち）

current_streak = 21.3で定義する

page_progress（current_page が一度でも入力されている場合のみ）：
    current_page = 直近の reading_log.current_page（NULLでない最新値）
    progress_rate = MIN(current_page / total_pages, 1.0)
```

`total_pages` は必須（データ構造編5.3、要件定義書R-70改訂）のため、進捗率が算出できないのは
現在ページが一度も入力されていない場合だけである（1.1改15。従来は「総ページ数が設定されて
いる場合のみ」という条件だった）。

進捗率は100%を上限とする。総ページ数を後から現在ページより小さい値へ引き下げる訂正を許容
しているため `current_page > total_pages` が成立しうるが、進捗率が100%を超えて表示される
ことは許されないためである。

日次ノルマ・実効速度・完了予測日・締切との乖離（第7〜10章）は算出しない。

### 21.3 連続記録日数（読書版）

```
T から遡り、対象bookのreading_logが存在する日が連続する日数。
```

13.4（連続報告日数）と異なり、バッファ日・除外日による中断除外を行わない。読書は日種別（第4章）による計画運用の対象外であり、資格試験の計画運用と独立させるためである（要件定義書R-64）。

### 21.4 想起記録の時系列注入

日次報告フィードバック（17.6の`{{recent_recalls}}`）および読了レポート（17.7の`{{reading_logs}}`）に注入する想起記録は、対象bookに属する `reading_log` を `record_date` の昇順で連結する。L-11（2026-09-16）までは週次要約による圧縮（第15章）を経由しなかった（読書目標が週次要約を持たなかったため）が、読書用週次要約（17.11）の新設により、両者とも「既に要約済みの週は圧縮表現、それ以外は生ログ」という構成に変わった。

**{{weekly_summaries}}との境界解決（L-11、2026-09-16是正）**：両者とも`ai_context_common.resolve_weekly_compressed_period(session, goal, period_start, period_end, limit=...)`で「[period_start, period_end]にフル収容される週次要約」を列挙し（週境界とperiod_start・period_endが一致しない場合や、間に未生成の週＝欠けがあっても、該当しない週を個別に除外するだけで残りは正しく圧縮対象になる。旧実装は「period_startから連続する週のみ」を要求しており、period_startが月曜と一致しない実運用ではほぼ発動しないバグだった）、返り値`covered_ranges`（圧縮対象となった各週の期間）を使って生ログ側から同じ日付を`ai_context_common.exclude_covered_dates`で除外する（二重注入の回避）。呼び出し方が用途ごとに異なる。

- `{{recent_recalls}}`（日次報告フィードバック、17.6）：`period_start=goal.start_date`（目標開始日まで遡る）、`period_end=today-1`、`limit=summary.inject_weeks`（既定4）を指定する。直近 `ai.reading_recall_recent_days`（既定14）日の窓の内側・外側を問わず、period_end側に近い（新しい）週から`limit`件までを圧縮対象とする（窓の外側の過去の経緯も要約で反映し続けつつ、窓の内側についても要約済みならプロンプトの文字数を減らせる。旧実装はperiod_startを窓の開始日に固定していたため、窓の外側の週次要約が過去の経緯として反映されず、また窓の内側は常に生ログのままでプロンプトが縮まらなかった）。
- `{{reading_logs}}`（読了レポート、17.7）：`period_start=book.start_date`、`period_end=today`、`limit`は指定しない（対象期間全体を漏れなく圧縮反映することが目的のため、件数上限を設けない）。

両者で生ログ（除外後）の注入範囲が異なる。

| 用途 | 生ログの注入範囲 |
| --- | --- |
| `{{recent_recalls}}`（17.6） | 直近 `ai.reading_recall_recent_days`（既定14）日分のうち、`{{weekly_summaries}}`で圧縮済みの日付を除いたもの |
| `{{reading_logs}}`（17.7） | 読書期間全体のうち、`{{weekly_summaries}}`で圧縮済みの日付を除いたもの |

`{{recent_recalls}}`は対象日（today）自身を含まない、直近`ai.reading_recall_recent_days`日分（today-recent_days〜today-1）とする（2026-09-15是正。todayの想起は`{{today_recall}}`で別途渡すため、含めるとreading_feedback_serviceの下書き値と二重にプロンプトへ注入されていた実運用の不具合があった）。

閾値を超える場合は、`{{weekly_summaries}}`（古い週から）→`{{recent_recalls}}`／`{{reading_logs}}`（古い日から）→（日次報告フィードバックのみ）当日対話（古い往復から）の順に縮退する（16.5の4段階とは別の仕組み。`prompt_builder.build_with_degradable_entries`、DAILY_FEEDBACK_WORKの22.4と共通）。それでも超える場合は末尾切り詰めのフェイルセーフに入る。読了レポートは目標のクローズ時に1回きり生成されるため実測でのリスク検証はまだで、対象外リスクはL-01と同様に未解消。
