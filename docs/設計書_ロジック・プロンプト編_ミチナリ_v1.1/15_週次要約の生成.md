## 15. 週次要約の生成

### 15.1 週の定義

月曜日を週の開始日、日曜日を終了日とする。

### 15.2 生成判定

アプリケーション起動時に以下を評価する。

```
手順1：直近の完了週を求める
       last_sunday = T 以前で最も近い日曜日
                     （T が日曜の場合は T 自身）

手順2：遡及対象の週を列挙する
       全目標中、最も早い実質開始日（goal.start_date。読書目標は
       goal.start_dateとは独立に変更できるbook.start_dateを用いる）の週から
       last_sundayまでの全週のうち、完了しているが weekly_summary が
       未生成の週を抽出する（G3、2026-10-18。固定の週数で検索窓を打ち切る
       旧方式は、その週数を超えてアプリを起動しなかった期間の週が
       その後も永久に要約されない不具合があった）

手順3：抽出された各週について、
       その週に実績（資格試験はstudy_log、読書はreading_log、
       仕事はwork_log）が1件以上存在する目標を対象に生成する
       （カテゴリ横断、21.1・22.1参照。L-11以降は3カテゴリいずれも対象）

手順4：手順2で抽出した週は新しい週が先頭の順に並ぶ。生成は呼び出し間隔の
       下限（既定2秒）を守って逐次実行し、1回の起動では
       summary.retroactive_max_per_run（初期値10）件までとする。
       新しい週ほど日次報告フィードバックへの圧縮効果が大きいため、
       新しい週から優先して生成する。上限を超えた古い週は未生成のまま
       残り、次回以降の起動で引き続き抽出・生成される

手順5：生成済みの週であっても、その週に属する実績（study_log・reading_log・
       work_log）・日記（daily_goal_diary）が事後に作成・更新された場合、
       その週のweekly_summary（非匿名化版・匿名化版の両方）を削除し
       未生成の状態へ戻す（15.4、G4）。次回以降の起動で手順1〜4により
       再生成される
```

**設計意図**

「日曜日に必ずアプリを起動するとは限らない」という前提に立つ。生成判定を起動時の遡及方式とすることで、バックグラウンドジョブを持たないローカル環境でも確実に生成される。

遡及範囲を目標開始日まで広げる一方、1回の起動で生成する件数に上限を設けるのは、長期間の未起動後に大量のAI呼び出しが一度に発生し起動が長時間化することを防ぐためである（G3）。

### 15.3 対話への注入

日次報告のプロンプトには、目標開始日（読書はbook.start_date）から対象日の前日までの全期間のうち、生成済みの週次要約を古い順に含める（S04、2026-10-17。件数・週数の上限は設けない。旧`summary.inject_weeks`は廃止）。全期間の日記原文は含めない。

### 15.4 無効化（修正時の再生成、G4）

`register_progress`（進捗のみ登録）はバックデート制限を持たず、確定済み（REPORTED）でなければ
過去のどの日付の実績も追記・修正できる。このため、週が完了した後（手順1〜4で週次要約が
既に生成された後）に、その週に属する実績や日記が事後に修正されることがある。その場合に
古い週次要約が使われ続けないよう、修正が反映された時点で即座に無効化する（起動時の
遡及生成を待たない）。

```
対象：study_log・reading_log・work_log・daily_goal_diaryの作成・更新
      （資格試験・読書・仕事の3カテゴリ共通、各カテゴリのupsert処理の最後で実行）

処理：対象レコードが属する週（月曜開始）について、その目標のweekly_summaryを
      非匿名化版・匿名化版とも削除する（is_anonymizedを問わない全件削除）

削除後：15.2の「未生成」と区別しない（weekly_summaryの行が存在しないことをもって
        「未生成」と判定する既存の仕組みをそのまま再利用するため、専用の
        無効化フラグ・スキーマ変更は設けない）。次回起動時の手順1〜4で
        再生成されるまでは、17.3〜17.10の各プロンプトはその週を生ログのまま
        注入する（resolve_weekly_compressed_periodが該当週をcovered_rangesに
        含めなくなるため、既存の安全側フォールバックがそのまま働く）
```

匿名化版も同時に削除するのは、匿名化版のみを基準に回す`regenerate_all_weekly_summaries_
anonymized`（17.4・データ構造編7.3）が非匿名化版の存在を基準に対象週を決めるため、
非匿名化版だけ削除すると匿名化版が古い内容のまま取り残されるおそれがあるためである
（開発Todo S06）。

目標・教材・本・案件の削除は本節の対象外である。実績が残る教材・本・案件は単独削除が
拒否され（データ構造編6.2）、目標削除時はweekly_summaryも含め関連データが一括で
削除される（goal_service.delete_goal）ため、無効化の仕組みが無くても不整合は生じない。
