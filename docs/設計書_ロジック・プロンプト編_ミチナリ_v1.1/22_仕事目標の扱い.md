## 22. 仕事目標の扱い

### 22.1 適用範囲

本文書の第3〜14章は、`goal.category = EXAM`（資格試験）の目標を対象とした算出ロジックである。`category = WORK`（仕事）の目標には適用しない（要件定義書R-74、仕様書6.11）。仕事目標が用いる算出ロジックは本章にまとめる。

第3章（1日の境界時刻の解決）は日次記録全体に関わる共通基盤であり、仕事目標にもそのまま適用する。

第15章（週次要約の生成）の対象判定（15.2手順3）は、当初仕事目標にはstudy_logが存在しないため自動的に対象外だったが、読書目標と同じ理由・同じL-11の一般化（21.1参照）により、仕事用週次要約（17.12、対象判定はwork_logの有無）が対象に含まれる。

**資格試験用AI機能との切り分け（DAILY_FEEDBACK）**：日次報告フィードバック（17.2 DAILY_FEEDBACK）が対象とする「進行中の目標」は、読書と同じく`ai_context_exam.list_active_exam_goals`によりEXAMのみへ限定する。仕事目標には別途DAILY_FEEDBACK_WORK（17.8）が存在するため、DAILY_FEEDBACKは引き続きEXAM専用として扱う（読書と同じ理由、21.1参照）。

**今日の一言（DAILY_MESSAGE）への対応 ※読書との重要な相違点**：読書目標は「今日の一言」の対象外である（21.1、要件定義書1.1（改2）時点の設計判断。build_goal_summaryがEXAM前提のコンテキストを組み立てるため、READINGを混ぜると「試験科目未登録」という誤った文脈が生成されてしまうことが理由）。仕事目標はこれと異なり、要件定義書R-77により**今日の一言の対象に含める**。理由は利用者からの明示的な要求（「日々の業務内容や努力を誉めるような機能が欲しい」）であり、日次のAIフィードバック（DAILY_FEEDBACK_WORK、17.8）とは別に、起動時の短い労いの一言を仕事目標にも提示する需要があるためである。これにより「今日の一言の対象＝EXAM及びWORK、READINGのみ除外」という設計に変わる。

対応として、`ai_context_exam.list_active_exam_goals`（EXAMのみを返す）とは別に、DAILY_MESSAGEが対象とする「進行中の目標」を求める関数（例：`list_daily_message_target_goals`。EXAM及びWORKを返し、READINGのみ除外する）を新設する。DAILY_MESSAGEのAiPurpose・prompt_template（17.4）は1つのまま維持し、テンプレート本文・変数自体は変更しない。かわりに`{{goal_summary}}`・`{{progress_summary}}`・`{{recent_activity}}`を組み立てる変数ビルダーの内部を`goal.category`により分岐させる。EXAM用のビルダー（科目構成・教材別進捗率が前提）はWORK目標にはそのまま使えないため、WORK用の変数ビルダーを別途新設する必要がある。WORK用の`{{goal_summary}}`・`{{progress_summary}}`は、22.2で算出する経過日数・直近記録日・連続記録日数・直近の月次報告有無を用いて組み立てる（日次ノルマ・進捗率に相当する定量指標を仕事目標は持たないため）。

`POST /goals/{id}/retrospective`（`retrospective_service.generate_retrospective`）はWORK目標に対してVALIDATION_ERRORで拒否する。読書がPhase15時点で経由した「暫定的な拒否ガード」（Phase16のGOAL_RETROSPECTIVE_READING実装により解消済み）とは異なり、仕事目標では月次報告・半期評価という別エンドポイント（`POST /goals/{id}/monthly-report`・`POST /goals/{id}/semiannual-review`、データ構造編6.2）を新設するため、この拒否は暫定ではなく恒久的な仕様である（`/retrospective`はクローズ時1回のレポートを前提とした設計であり、周期的に生成し続けるWORKの月次・半期報告とは呼び出しの意味が異なるため統合しない）。

**対話履歴の分離（chat_message.purpose）**：資格試験（DAILY_FEEDBACK）と仕事（DAILY_FEEDBACK_WORK）の対話は、同一日の同一`daily_record`に混在しうる。読書と同じ仕組み（`purpose`列、データ構造編5.4）により、対話履歴（`{{conversation_history}}`）への注入時にpurposeで絞り込み、用途間の文脈混入を防ぐ。AI対話の実行エンドポイントも`POST /records/{date}/work-chat`（DAILY_FEEDBACK_WORK）として、`/chat`・`/reading-chat`と分離する（データ構造編6.2）。

### 22.2 仕事進捗（WorkAssignmentRead）の算出

書籍の派生値（21.2）と同じ方針で、案件情報の派生値も独立エンドポイントを設けず`WorkAssignmentRead`（`GET /goals/{id}`等の応答）に埋め込む（都度算出、保存しない）。

```
elapsed_days = T − work_assignment.start_date

last_work_date = MAX(daily_record.record_date)
                  （対象work_assignmentのwork_logが存在する daily_record のうち）

current_streak = 22.3で定義する

has_recent_monthly_report = 直近の月（前月または当月）を対象期間とする
    goal_retrospective（period_type=MONTHLY）が生成済みか
```

日次ノルマ・実効速度・完了予測日・締切との乖離（第7〜10章）は算出しない。書籍と異なり`work_assignment`は読了目標日に相当する`due_date`を持たないため（データ構造編5.3「work_assignment（案件情報）」参照）、残日数（remaining_days）に相当する指標も算出しない。

### 22.3 連続記録日数（仕事版）

```
T から遡り、対象work_assignmentのwork_logが存在する日が連続する日数。
```

21.3（連続記録日数・読書版）と同じ理由により、バッファ日・除外日による中断除外を行わない。仕事目標は日種別（第4章）による計画運用の対象外であり、資格試験の計画運用と独立させるためである（要件定義書R-74）。

### 22.4 業務記録の時系列注入

日次報告フィードバック（17.8の`{{recent_work_logs}}`）、月次報告（17.9の`{{month_logs}}`）、半期評価（17.10の`{{period_logs}}`）に注入する業務記録は、対象work_assignmentに属する `work_log` を `record_date` の昇順で連結する。L-11（2026-09-16）までは週次要約による圧縮（第15章）を経由しなかった（仕事目標が週次要約を持たなかったため、読書と同じ理由。21.4参照）が、仕事用週次要約（17.12）の新設により、三者とも「既に要約済みの週は圧縮表現、それ以外は生ログ」という構成に変わった。

**{{weekly_summaries}}との境界解決（L-11、2026-09-16是正）**：読書（21.4）と同じ`resolve_weekly_compressed_period`＋`exclude_covered_dates`の仕組みを用いる。呼び出し方が用途ごとに異なる。

- `{{recent_work_logs}}`（日次報告フィードバック、17.8）：`period_start=goal.start_date`（目標開始日まで遡る）、`period_end=today-1`、`limit=summary.inject_weeks`（既定4）を指定する。直近 `ai.work_recent_log_days`（既定14）日の窓の内側・外側を問わず、period_end側に近い週から`limit`件までを圧縮対象とする（理由は読書の21.4と同じ）。
- `{{month_logs}}`・`{{period_logs}}`（月次報告・半期評価、17.9・17.10）：`period_start=date_from`（対象月・対象半期の初日）、`period_end=date_to`、`limit`は指定しない（対象期間全体を漏れなく圧縮反映することが目的のため）。半期評価は最大6ヶ月分の生ログ注入となるため、この置き換えの効果が最も大きい（改17時点で識別した「古い日から削るだけでは対象期間の前半の実績が人事評価から漏れる」副作用への根本対応、L-01と同様の未解消リスクではなく解消済み）。

三者で生ログ（除外後）の注入範囲が異なる。

| 用途 | 生ログの注入範囲 |
| --- | --- |
| `{{recent_work_logs}}`（17.8） | 直近 `ai.work_recent_log_days`（既定14）日分のうち、`{{weekly_summaries}}`で圧縮済みの日付を除いたもの |
| `{{month_logs}}`（17.9） | 対象月のうち、`{{weekly_summaries}}`で圧縮済みの日付を除いたもの |
| `{{period_logs}}`（17.10） | 対象半期のうち、`{{weekly_summaries}}`で圧縮済みの日付を除いたもの。月次報告のロールアップ（生成済みのgoal_retrospective本文）ではなく、日々のwork_logを直接参照する方針（読書のgoal_retrospective（17.7）と同じく、利用者が明示的に選択した設計。要件定義書6.11本文）は変わらない |

`{{recent_work_logs}}`は対象日（today）自身を含まない、直近`ai.work_recent_log_days`日分（today-recent_days〜today-1）とする（2026-09-15是正。理由・窓の定義は読書の`{{recent_recalls}}`（21.4）と同じ）。

閾値を超える場合の縮退順序は21.4と同じ（`{{weekly_summaries}}`古い週から→生ログ古い日から→当日対話古い往復から→末尾切り詰め）。実運用で直近14日分の業務記録だけで閾値の9割近くに達する例を確認しており、この安全弁（改17時点で先行導入済み）は週次要約導入後も引き続き有効に働く。

### 22.5 期間判定（月次・半期）

**月次報告の対象期間**

`period_key`は暦月（`"YYYY-MM"`）とする。**`period`クエリパラメータ省略時は前月を既定値とする**（2026-09-04改訂。「提出対象年月」は常に提出月の前月であり、当月はまだ終わっていないため対象としない。要件定義書R-78「提出対象年月」の定義）。前月の`period_key`は単純な月繰り下げとする（1月の前月は前年12月、`"YYYY-01"`の前月は`"(YYYY-1)-12"`）。

**報告月の定義**（2026-10-05追加）：報告月は対象月の翌月とする（`report_period_key = period_key の翌月`、12月の翌月は翌年1月）。提出対象年月が生成月の前月であるため（要件定義書R-78）、対象月2026-09の報告は報告月2026-10となる。報告月は`goal_retrospective`に保存せず、応答時に`work_report_service.reporting_period_key`で導出する。半期評価には報告月を設けない（`null`を返す）。

**半期の区分**

会社の人事評価サイクル（3月に目標設定・8月に評価、9月に目標設定・翌2月に評価）に合わせ、以下のとおり区切る。一般的な暦半期（1〜6月／7〜12月）とも、会計年度の上期・下期（4〜9月／10〜3月）とも異なる点に注意する（要件定義書R-79）。

```
H1 = 3月1日 〜 8月31日
H2 = 9月1日 〜 翌年2月末日（閏年は2月29日、平年は2月28日）
```

対象日 T から `period_key` を算出する規則は以下のとおり。

```
Tの月が3〜8月のとき   → f"{T.year}-H1"
Tの月が9〜12月のとき  → f"{T.year}-H2"
Tの月が1〜2月のとき   → f"{T.year - 1}-H2"
```

前半期の`period_key`（当該半期の直前の半期）は以下のとおり。

```
対象が "Y-H1" のとき → f"{Y - 1}-H2"
対象が "Y-H2" のとき → f"{Y}-H1"
```

`period`クエリパラメータ省略時は、Tが属する半期を既定値とする。進行中の半期についても、月次報告と同様にドラフトの生成・再生成を許容する（要件定義書R-79「再生成を許容する」）。

### 22.6 月次報告・半期評価の出力フォーマットの組み立てと解析

要件定義書R-82（生成結果を人が確認・修正できること）を実現するため、`goal_retrospective.body`はAIが自由書式で書く1つの文章ではなく、**アプリケーション層が構造化列から一定のテンプレートで機械的に組み立てる**（データ構造編5.4参照）。

**生成時の処理手順**

```
手順1：対象期間（period_key）の直前期間（前月／前半期）の行を取得する
       存在すれば next_goal_text を今回の target_goal_text として複製する
       存在しなければ target_goal_text に固定文言
       「（前月／前半期の記録が無いため、今回は目標との比較を行いません）」を設定する

手順2：17.9／17.10の変数を組み立て、AIへ送信する

手順3：AI応答を見出し文字列（17.9は5節、17.10は4節）で分割する
       各節の内容を対応する列（business_summary、achievement_score、
       achievement_reflection、next_goal_text、report_notes）に格納する
       「達成度」節が半角数字1〜5のいずれでもない場合
       （「対象外」を含む）、achievement_score列はNULLのままとする

手順4：見出しが1つでも検出できなかった場合、当該項目は空文字のまま
       レコードを保存する（生成自体は失敗させない。AI応答全文は
       既存のai_logに記録済みのため、内容自体は失われない）

手順5：target_goal_text・business_summary・achievement_score・
       achievement_reflection・next_goal_text・report_notesを
       下記テンプレートで結合し、bodyへ格納する

手順6：goal_id・period_type・period_keyの一意な行として保存する
       （既存の行があれば上書き。データ構造編5.4「WORKでの流用」）
```

**bodyの組み立てテンプレート（月次報告）**

```
# 月次報告（{{target_month}}）

## 業務内容（案件内容）
{{business_summary}}

## 当月の目標
{{target_goal_text}}

## 目標がどの程度達成されたか
{{achievement_score}}

## 目標の達成状況と進捗に関する振り返り
{{achievement_reflection}}

## 来月の目標
{{next_goal_text}}

## 報告・連絡事項
{{report_notes}}
```

半期評価は見出し・変数名を「対象半期」「当該半期の目標」「次半期の目標」に読み替え、「報告・連絡事項」の節を持たない（要件定義書R-79）。

**利用者による編集（PATCH、要件定義書R-82・R-83）**：レビュー画面での編集は、`target_goal_text`・`achievement_score`・`business_summary`・`achievement_reflection`・`next_goal_text`・`report_notes`の各列を個別に更新可能とし、保存のたびに手順5のテンプレート結合を再実行して`body`を更新する（`body`を直接自由編集させることはしない。列と本文の不整合を防ぐため）。前期の記録が無い場合の手動シード（R-83）は、`target_goal_text`列のみを利用者が直接入力し、他の列は空のまま行を作成する。

### 22.7 チームメンバー・AI評価レポートの扱い（要件定義書R-93〜R-96、2026-09-23）

**同意ゲートの実装方針**：`work_member.characteristics`（特徴・性格）を非空の値で保存する処理（作成・更新の双方）は、必ずサービス層（`work_member_service._apply_characteristics`）で`consent_confirmed`引数の真偽を検証し、偽であれば`ConsentRequiredError`を送出する。フロントエンドのチェックボックス非活性化はUXの補助に過ぎず、サービス層の検証を回避できない（データ構造編6.1「サービス層でのHTTP例外の送出」禁止と対になる、ドメイン検証の一元化）。値が変わらない再保存であっても`consent_confirmed=true`を要求する（保守的な設計。本アプリが第三者のPIIを扱う初のフィールドであるため）。`characteristics`を空文字/NULLへ戻す保存は同意確認を要求せず、`consent_confirmed_at`もNULLへ戻す（存在しない内容に対する確認済み表示を残さないため）。

**評価レポートの生成契機・グレイン**：`work_evaluation_service.generate_evaluation_report`は、①`work_assignment.role == EVALUATOR`であること、②指定された`work_member`が当該`work_assignment`に所属すること、の2点を検証したうえで17.13のプロンプトを構築する。月次報告・半期評価（22.5〜22.6）が「案件×期間」のグレインで`goal_retrospective`へ1期間1行のupsertを行うのに対し、評価レポートは「案件×メンバー」のグレインであり、かつ生成のたびに新規行（`work_evaluation_report`）を追加する（upsertしない）。これは、月次報告・半期評価が「今月の報告」という単一の成果物を更新し続ける性質を持つのに対し、メンバー評価は「いつ・どの考慮事項で評価したか」という生成時点ごとの記録そのものに価値があるためである。

**会話の分離**：`ai_conversation.ensure_conversation`は`scope=EVALUATION_REPORT_WORK`・`scope_key=str(member.id)`で会話を分離する。月次報告・半期評価の`scope_key=period_key`（期間ごとに会話を分離）と対称的に、評価レポートは対象メンバーごとに会話を分離する（同一メンバーへの再生成は同じ会話を再利用し、異なるメンバーは別会話とすることで、他メンバーの記録がプロンプト文脈へ暗黙に混入することを避ける）。

**入力データの技術的制約**：`{{feedback_history}}`に`ai_log`ではなく`chat_message`を用いる根拠は17.13に記載のとおり。加えて、`work_log`・`chat_message`のいずれも「案件（goal）単位」の記録であり「メンバー単位」ではない（要件定義書R-93の技術検証で、日次報告の単位を目標単位のまま変更しないことを明示的に確認済み）。そのため、特定メンバーに関する記述の判別は構造的な絞り込みではなく、AIがプロンプト中の氏名・イニシャルの言及から解釈する方式に依存する。この精度限界は設計上受容している（利用者が確認・修正するレビュー画面を経由するため、要件定義書R-96）。
