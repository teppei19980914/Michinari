## 27. 1年前の今日の算出ロジック

開発Todo「1年前の今日」v1.0、要件定義書R-148〜R-153。毎日同じ形の画面だけでは予想外の楽しさがないため、過去の同じ日の記録をダッシュボードにときどき表示する。AIは使わず、既存データの読み取りのみで完結する。表示するか否か・どの記録を選ぶかは、サーバーの論理日（`goal_service.resolve_today`）から完全に決定的（同じ日に何度呼んでも同じ結果）に算出し、新規テーブルへの保存は行わない（CLAUDE.md「日次ノルマ・残量・現在周回の保存」禁止と同じ、都度算出の考え方）。

### 27.1 候補日の算出（「何か月前」の月差分計算）

候補は`app_setting`（`on_this_day.candidate_months_ago`、既定`1,6,12`）の各値（何か月前か）について、`on_this_day_service.subtract_months(today, months)`で算出する。

```
subtract_months(base, months):
    total_months = base.month - 1 - months
    year = base.year + total_months // 12
    month = total_months % 12 + 1
    day = min(base.day, その年月の最終日)
    return date(year, month, day)
```

対象月にその日が存在しない場合（うるう年の2/29、各月末日）は、その月の最終日にクランプする（例：3/31の1ヶ月前は2/28または2/29）。`dateutil`等の新規依存ライブラリは追加しない（CLAUDE.md「新しい依存ライブラリは原則追加しない」）。

### 27.2 表示するか否かの決定的判定

`on_this_day.show_probability`（既定0.3）に対し、以下の決定的な値で判定する。

```
_deterministic_unit_value(seed) = int.from_bytes(sha256(seed).digest()[:8], "big") / 2**64  # [0, 1)
resolve_show_today(today, probability) = _deterministic_unit_value(f"on_this_day:show:{today}") < probability
```

Python組込みの`hash()`は`PYTHONHASHSEED`によりプロセスごとに値が変わるため使用できない。`hashlib.sha256`は入力が同じなら常に同じ値を返すため、「同じ日に何度呼んでも同じ結果」（R-149の受け入れ基準）を満たせる。`on_this_day.enabled`がfalseの間は、この判定を行わず常に非表示とする。

### 27.3 対象とする記録

資格試験の日記（`DailyGoalDiary`、`diary_text_expr()`と同じ優先順：`diary_learned`優先、無ければ`diary_body`）・読書の想起記録（`ReadingLog.recall_body`）・仕事の業務記録（`WorkLog.body`）を対象とする。本文が空文字・NULLの行は対象外（表示する抜粋が無いため）。進捗のみ登録（R-17、数値のみ）は本文列を持たないため自然に除外される。

削除済みの目標は、目標の完全削除（`goal_service.delete_goal`）でカスケード削除されDBに残らないため、追加の除外フィルタなしで対象外となる（R-151）。アーカイブ済み・クローズ済みの目標は論理フラグ（`archived_at`・`status`）のみで物理データが残るため、対象に含める。

### 27.4 複数候補がヒットした場合の決定的選定

候補日3件程度×3カテゴリで複数件ヒットした場合、以下の決定的タイブレークで1件を選ぶ。

```
_select_candidate(today, candidates) = min(candidates, key=lambda c:
    _deterministic_unit_value(f"on_this_day:pick:{today}:{c.record_date}:{c.category}:{c.goal_id}"))
```

`months_ago`は、選ばれた`record_date`と一致する候補月数のうち最小の値を採用する（複数の月数が偶然同じ日付を指す場合の決定的タイブレーク）。

### 27.5 性能設計

候補日（既定3件）をまとめて`DailyRecord.record_date.in_(candidates)`で1クエリにし、カテゴリごとに1クエリ（計3クエリ）で完結させる（N+1回避、`app/api/dashboard.py`の`_build_goal_card_and_stats`と同じ「事前にまとめて取得する」設計パターン）。`GET /dashboard`の初期表示2秒以内の性能要件（11章）に実質影響しない。

### 27.6 脅威モデル（STRIDE）

本機能は`GET /dashboard`の既存レスポンスへ`on_this_day`フィールドを1件追加するのみで、新規エンドポイント・新規書き込みは発生しない。

| 脅威 | カテゴリ | 対策 |
| --- | --- | --- |
| 削除済み目標の記録が誤って表示される | 情報漏洩 | カスケード削除により物理的にDBへ残らないことをテストで保証 |
| 他の目標・無関係なgoal_idが混入する表示 | 情報漏洩 | 3カテゴリのJOINはいずれも`daily_record_id`→本文テーブル→`goal_id`の一意な経路のみを辿り、クライアントからの入力は受け付けない |
| 候補日計算のロジックエラーによる将来日・不正な日付の参照 | 改ざん | `subtract_months`はサーバーの論理日のみを基準にし、結果は常に過去日であることをテストで保証 |
| 追加クエリによるダッシュボード応答遅延 | サービス拒否 | 候補日のまとめ取得1クエリ＋カテゴリごとの3クエリに限定（27.5） |
| なりすまし・否認 | － | ローカル単一利用者アプリのため対象外（既存の目標CRUDと同様の前提） |
