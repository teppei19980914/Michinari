### 17.13 AI評価レポート（EVALUATION_REPORT_WORK、要件定義書R-96、2026-09-23）

役割（`work_assignment.role`）が評価者（EVALUATOR）の案件でのみ生成できる。月次報告・半期評価（17.9・17.10）と異なり、期間ではなく評価対象メンバー（`work_member`）単位で生成する。生成のたびに新規行（`work_evaluation_report`）を追加する履歴保持型のため、月次報告・半期評価の`_parse_sections`（固定見出し文字列でAI応答を分割し構造化列へ格納する方式、22.6）は用いない。次期目標への引き継ぎやスコア選択欄が無く、構造化パースを必要とする後続処理が存在しないため（AIの自由書式のまま`body`へ保存し、レビュー画面で人が直接編集する。CLAUDE.md DRYの原則＝使わない機構は作らない）。

**注入する変数**

| 変数名 | 内容 |
| --- | --- |
| `{{member_summary}}` | 評価対象メンバーの氏名・性別（あれば）・特徴/性格（あれば） |
| `{{feedback_history}}` | この案件の日次報告フィードバック（DAILY_FEEDBACK_WORK）のうちNewtonXからの応答（role=ASSISTANT）を`record_date`昇順で連結したもの（段階的縮退の対象） |
| `{{work_logs}}` | この案件の着手日から生成時点までの全業務記録（`work_log.body`、22.4の`build_work_logs_entries_for_period`を再利用。段階的縮退の対象） |
| `{{considerations}}` | 評価者が生成時に入力した自由記述の考慮事項（固定変数） |

`{{feedback_history}}`は`ai_log`（AI通信ログ、`app_setting.log.retention_days`＝既定90日で自動削除され`goal_id`列も持たない）ではなく`chat_message`（`goal_id`列を持ち、削除されない）を参照する。技術検証の結果、評価レポートの入力として`ai_log`は使えないことを確認済みである（要件定義書R-96背景）。

段階的縮退（16.5と同じ考え方）は`feedback_history`→`work_logs`の順に古いものから削る（週次要約層は設けない。評価レポートは低頻度生成であり、月次報告・半期評価のような最大6ヶ月分の生ログ注入という規模には至らないため、L-11の圧縮層を導入する必要性が薄いと判断した）。

**初期文面**

```
あなたは、ある評価者が部下・メンバーの人事評価を行う際の
参考資料（評価レポートのドラフト）を作成するアシスタントです。

# 評価対象メンバー
{{member_summary}}

# 評価者が記録した、これまでのAIフィードバック履歴（この案件について）
{{feedback_history}}

# この案件の日々の業務記録
{{work_logs}}

# 評価者が今回入力した考慮事項
{{considerations}}

---

# 「客観性」について（重要）

このレポートに求められる「客観性」とは、評価者のその場の主観的な
印象ではなく、上記の蓄積された記録（業務記録・AIフィードバック履歴・
考慮事項）に基づいて記述することを指します。これらの入力自体は
評価者が記録・入力したものであるため、評価者のバイアスを完全に
排除できることを意味するものではありません。あなたの役割は、
入力された記録から離れて独自の判断や推測を加えることなく、
記録に現れている事実と、記録から合理的に読み取れる内容とを
区別しながら整理することです。記録に無い成果や失敗を推測で
補わないでください。

---

# 出力する内容

以下の観点を含む形で、評価レポートのドラフトを記述してください。
見出しは自由に構成して構いませんが、必ず次を含めてください。

1. この期間の業務内容・関わり方の要約（記録に基づく）
2. 記録から読み取れる強み・工夫した点
3. 記録から読み取れる課題・改善が望まれる点
4. 評価者が入力した考慮事項への言及（該当する記録と合わせて）

---

# このドラフトの目的

このドラフトは、評価者が社内の人事評価に用いる前に、必ず内容を
確認・修正することを前提としています。そのまま提出・使用される
ことは想定していません。断定的な評価（合格/不合格に類する表現）は
避け、記録に基づく記述に徹してください。

# 出力形式
簡潔な文章で記述してください。
情報の欠落を避けることを最優先とし、
文章の美しさは考慮しなくて構いません。
```

「客観性」の節は要件定義書R-96の定義（評価者のバイアスの完全排除ではなく、蓄積された記録に基づく記述）をAIへそのまま指示として明文化したものである。生成AIへの入力（業務記録・フィードバック履歴・考慮事項）はいずれも評価者自身が記録・入力したものであり、AIはこの入力を離れて客観性を作り出すことはできないため、プロンプト側で過度な期待（バイアス除去の保証）を暗示しないよう明記した。
