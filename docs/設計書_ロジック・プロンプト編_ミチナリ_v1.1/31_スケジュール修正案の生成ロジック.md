## 31. スケジュール修正案の生成ロジック（1.1改77、単位5）

本章は開発Todo_スケジュール・ガントチャート_v1.1 第13章（AIによるスケジュール修正案）・単位5独自の`開発Todo_スケジュール・ガントチャート_単位5_v1.0.md`を設計として固定する。遅れの判定・目標の期限解決・AI呼び出し・応答の検証・保存と置き換え・判断の実体は`schedule_revision_service.py`に集約する（CLAUDE.md DRYの原則）。

### 31.1 遅れの判定（AIを使わない、13.2）

遅れはAIに判断させず、システムが機械的に判定する。`schedule_service.compute_delay_kind(item, today)`（単位5で新設、ガントの遅れの印〈D-17・D-18〉と同じ判定関数を共用）が、未着手・進行中の行についてのみ以下を順に判定する。

1. 本日が予定終了日を過ぎている → `END_DELAY`（終了の遅れ）
2. 未着手かつ本日が予定開始日を過ぎている → `START_DELAY`（開始の遅れ）
3. いずれにも該当しない、または完了・中止の行 → `None`（遅れなし）

この判定関数は2つの経路で共有する。①確定APIの応答へ追加する`schedule_revision_candidates`（`list_revision_candidate_goal_ids`、ACTIVEな目標のうち遅れのある行を1件以上持ち、かつ同じ報告対象日にAUTO生成済みでない目標のID一覧）。②`generate_proposal`のAUTO判定自体（遅れのある行が1件も無ければAIを呼ばず`None`を返す、D-54）。

### 31.2 目標の期限解決（D-62）

`resolve_goal_due_date(goal)`が、既存の締切計算をそのまま使い新しい計算式を書かずに期限を返す。

| 種別 | 期限 |
| --- | --- |
| 資格試験（EXAM） | `material_service.compute_due_date(goal.exam_subjects, goal.start_date)`（紐づく全科目の最も早い有効受験日の前日）。`goal.exam_subjects`が空の場合は算出不能のため「期限なし」とする |
| 読書（READING） | `book.due_date`（NOT NULL、1目標1冊のため常に期限を持つ） |
| 仕事（WORK） | 期限を適用しない（常に`None`） |

算出した期限は、AI応答の検証（31.4のCHANGEブロック制約）と、承認時の制約判定（13.7、ただし利用者が日付を修正して承認する場合は適用しない）の両方で参照する。

### 31.3 AI呼び出し（13.3）

**生成契機**：日次報告の確定後（AUTO、確定処理自体はAI呼び出しを行わず、確定成功後に画面から別途依頼する）、またはスケジュールタブの「AIに修正案を依頼」ボタン（MANUAL、遅れの有無を問わず常に依頼できる、D-58）。

**使い捨て会話**：`AiPurpose.SCHEDULE_REVISION`・`ConversationScope.SCHEDULE_REVISION`を新設し、1回ごとに完結する呼び出しとして会話を継続しない（13.3）。`scope_key=uuid.uuid4().hex`で毎回新しい会話を作り、専用フォルダ（`ai.schedule_revision_folder_name`、既定「ミチナリ_スケジュール修正案」。目標ごとの既定フォルダ`{prefix}_{目標名}`とは分離）に作成し、`ai_orchestration.send_and_log`で送信した直後に`ai_conversation.discard_conversation`で削除する（`finally`節、応答取得の成否にかかわらず実行。`summary_card_service.generate_sentence`・`help_assistant_service`と同型）。専用アシスタント設定`ai.assistant_uid.schedule_revision`（既定値：行ID・日付を機械的に読み取るだけの構造化タスクのため、ヘルプ・目標相談・まとめと同じナレッジを持たない標準モデル）を設定画面から変更できる。

**AI通信とトランザクション（CODING_RULES.md）**：`ensure_conversation`・`send_and_log`を経由し、AI応答を待つ間はDBへ書き込まない。修正案の保存・古い修正案の置き換え（31.6・D-65）は、応答を得た後に`serialize_writes()`内の1トランザクションでコミットする（`test_ai_write_lock.py`と同じ観点のテストを追加）。

**入力構成**（固定変数＋度数制限なしの2段階縮退、`prompt_builder.DegradableFeedbackContext`）

| 区分 | 内容 |
| --- | --- |
| 固定変数 | 本日、目標の種別、目標の期限（31.2、無ければ「なし」）、スケジュール全行（行ID・作業項目・作業内容・予定開始日・予定終了日・状況・実績開始日・実績終了日・遅れの有無を整形した一覧）、直近に却下された修正案（D-64、`schedule.revision.recent_rejections_count`件まで、却下日時の新しい順。作業項目名・却下された変更案・却下理由を含む） |
| 段階1（縮退対象） | 週次要約（`ai_context_common.build_past_record_entries`、古い週から除外） |
| 段階2（縮退対象） | 週次要約がまだ無い過去日の生ログ（カテゴリ別の既存組み立て関数：資格試験=`ai_context_exam.build_recent_study_entries`、読書=`ai_context_reading.build_recent_recalls_entries`、仕事=`ai_context_work.build_recent_work_logs_entries`） |

日次報告文脈の対象期間は`period_start`＝目標の開始日（読書のみ`book.start_date`）、`period_end`＝`today - 1日`とする。当日分はスケジュール行自体（予定日・状況・実績日）に既に反映されているため、日次報告文脈側に当日入力を重複して注入する必要がない（既存の「当日入力は別経路で渡す」方針を、本用途では「スケジュール行自体が当日入力に相当する」形で解釈した、単位5開発Todo2章補足4）。固定変数・段階ともに`ai.max_prompt_chars`を超える場合、段階1→段階2の順で縮退する。

**スケジュール全行自体が上限に収まらない場合の縮退**（開発Todo_スケジュール・ガントチャート_検証修正_v1.0.md 軽微な修正4）：段階1・段階2を0件まで縮退させても超える場合、固定変数のスケジュール全行一覧から完了・中止の行を落として再試行する（`_active_items_for_prompt`）。CHANGE判定は未着手・進行中の行にしか適用されない（31.4）ため、完了・中止の行を落としても生成結果への影響が最も小さい。それでも超える場合は送信せず`ScheduleRevisionPromptTooLongError`とする（24章の目標相談チャットと同じ、固定変数だけで上限を超える場合に到達するフェイルセーフ）。

**プロンプト本文**（`AiPurpose.SCHEDULE_REVISION`、`prompt_template`で編集可能）は、変更できる対象（未着手・進行中の行の予定開始日・予定終了日のみ）、進行中の行は予定終了日のみ変更可、新しい予定日は本日以降かつ開始日≦終了日、期限を超える変更は提案せず「注意」として出力、作業の前後関係は行の並び順・作業項目・作業内容から推測して理由に書く（前後関係専用の列は持たない、D-60）、遅れている行または遅れを招くおそれがある行のみを対象にする、という指示と、31.4の出力形式を定める。

### 31.4 応答の読み取りと検証（13.4・13.5、D-66）

AIの応答は信頼しない入力として扱う（間接プロンプトインジェクション対策、日次報告の日記等を経由して「他の目標の行ID」「完了済み・中止済みの行」「期限を超える日付」「進行中の行の開始日変更」等を指示してくる可能性を想定）。`quiz_generation_service.py`と同じ`===`区切りのブロック形式で解析する（`schedule_revision_block_parsing.parse_response`）。

**ブロック形式**

```
種類: 変更
行ID: <対象の行ID>
予定開始日: <YYYY-MM-DD>
予定終了日: <YYYY-MM-DD>
理由: <1行で、変更の理由>
```

```
種類: 注意
行ID: <対象の行ID>
理由: <1行で、期限内に収まらない理由>
```

```
総評: <全体を通した一言>（任意、無ければ省略可）
```

**ReDoS対策**（quiz_generation_service.py・quiz_block_parsing.pyと同じ多層防御）：フィールドの正規表現は非貪欲（`[^\n]+?`）かつ`re.DOTALL`を使わない。`schedule.revision.max_block_chars`を超える1ブロックは、正規表現マッチの前に文字数で拒否する。行IDは`[0-9]+`の正規表現で数字のみに限定する。

**CHANGEブロックの検証**（`_validate_changes`、不正・制約違反のブロックは個別に捨てる、D-61。他のブロックの処理には影響させない）：行IDが対象の目標に属すること・重複行IDは最初のものだけを使う・状況が未着手または進行中であること・進行中の行は予定開始日を変更しないこと・新しい予定開始日≦予定終了日・新しい予定日が本日以降（未着手は予定開始日も本日以降）・目標に期限がある場合は新しい予定終了日が期限を超えないこと（31.2）・理由が必須かつ`schedule.revision.reason_max_chars`以内・現在の値と少なくとも1項目が異なること、の全てを満たすブロックのみを有効とする。

**WARNINGブロックの検証**（`_validate_warnings`）：行IDが対象の目標に属すること・理由が必須かつ上限文字数以内であることのみを課す（CHANGE向けの状況・日付・期限の制約は適用しない）。

有効な変更・注意のいずれも無い場合は`None`を返す（「修正が必要な行はありませんでした」、画面には何も表示しない）。

### 31.5 承認APIの再検証（13.7、D-59）

承認APIは「変更前の値（`before_planned_start_date`・`before_planned_end_date`・`before_status`）が現在のスケジュール行の値と一致すること」を適用の段階で再検証する（スケジュール画面での同時編集・多重送信への対策）。一致しない行は`blocked_reason="STALE_BEFORE_VALUE"`を付与して`decision`を`PENDING`のまま残し、他の行の処理は継続する（`decide()`は検証を適用より先に全て終え、ステイル判定だけを適用の段階で行う。単位2`save_schedule`と同じ「検証→適用」の2段方式）。

利用者が日付を修正して承認する場合は、第6章の検証ルール（進行中の行は予定開始日を変更不可、予定開始日≦予定終了日、新しい予定日は本日以降）を適用するが、期限（31.2・D-62）は利用者の判断を優先し適用しない（13.7）。**この制約に反する行も、STALE_BEFORE_VALUEと同じく行単位の結果として扱う**（開発Todo_スケジュール・ガントチャート_検証修正_v1.0.md 修正1）：`blocked_reason="INVALID_PLANNED_DATE"`を付与して`decision`を`PENDING`のまま残し、他の行の処理は継続する（この再検証も適用の段階で行い、構造的な不正入力〈存在しない行ID・二重判断等〉への検証とは異なり例外を送出しない）。画面はこの理由を行に表示し、日付を修正すれば再度承認できる（ボタンは無効化しない）。「すべて承認」は、STALE・この行のいずれも対象から除く。

承認すると`schedule_item`へ反映し、1回のdecisions呼び出しで複数行を承認しても`goal_schedule.revision`は1回だけ増やす（単位2・単位4と同じ楽観ロックの単位）。

### 31.6 保存と置き換え（13.6、D-65）

修正案1件（`schedule_revision_proposal`）と、その行（`schedule_revision_proposal_item`、CHANGE/WARNING）を保存する。目標ごとに未判断（PENDING）の修正案は常に1つとし、新しい修正案ができた場合は`_supersede_pending_proposal`が古い修正案を`SUPERSEDED`へ、その未判断の行を`decision=SUPERSEDED`へ遷移させて終了する。予定日の変更履歴は`schedule_revision_proposal_item`自体が兼ねる（既存の`schedule_item_history`〈状況・実績日の履歴〉とは別の関心事のため競合しない）。

### 31.7 脅威モデル（STRIDE、スキル `threat-model` に従う）

**データフロー**：[利用者]→日次報告確定／SC-07→確定APIの応答（`schedule_revision_candidates`）→［利用者の操作または自動］→`POST /goals/{goal_id}/schedule/revision-proposals`（信頼境界）→`schedule_revision_service`→NewtonX（外部AI基盤、信頼境界）→応答の解析・検証→`schedule_revision_proposal`/`_item`（DB）→`POST .../decisions`（信頼境界）→`schedule_item`（予定日の反映）。

| 脅威 | カテゴリ | 対策 | 実装箇所 |
| --- | --- | --- | --- |
| なりすまし | S | 既存の認証機構と同一。新規の認証経路は追加しない（対象外） |  |
| AIの応答の改ざん・不正な指示（他目標の行ID、完了済み・中止済みの行、期限超過、進行中の行の開始日変更） | T | 31.4のブロック単位の全ルールを機械的に検証し、不正なブロックは個別に捨てる。AIの指示を信用せず、システムが決めた制約のみを適用する | `schedule_revision_block_parsing.py`・`schedule_revision_service._validate_changes`/`_validate_warnings` |
| 間接プロンプトインジェクション（日次報告の日記等が週次要約・直近記録経由でプロンプトに注入される） | T | 同上の機械的検証で無力化。日記等の自由入力自体への追加対策は既存方針どおり設けない（出力側の検証で十分、ユーザー指示の重点確認済み） | 同上 |
| 承認APIへの多重送信・同時編集 | T | 「変更前の値が現在の値と一致すること」をAPI側で再検証する（D-59、31.5） | `schedule_revision_service.decide` |
| 他目標の行・修正案への不正アクセス | I | 生成API・判断APIは対象の目標に属する行のみを受け付け、他の目標の存在を推測できるメッセージを返さない（単位2`_check_owned_by_goal`と同じ方針） | `app/api/schedule_revision.py` |
| 日次フィードバック・ナレッジエクスポートへの本機能データの混入 | I | AIへ渡す情報は対象の目標1件分のスケジュール・日次報告文脈のみとし、既存のナレッジエクスポート・日次フィードバックのプロンプトには含めない（D-41改訂） | `schedule_revision_service.py`（独立のプロンプト・会話） |
| 過剰な送信・長大なブロック（DoS） | D | 1ブロックの文字数上限（`schedule.revision.max_block_chars`）、直近の却下件数の上限（`schedule.revision.recent_rejections_count`）、理由・作業内容の文字数上限で対策。自動生成は目標・報告対象日ごとに1回まで（13.2、D-65とは別の制約） | `app_setting`各キー・`schedule_revision_block_parsing.py` |
| 権限昇格（認可境界の回避） | E | 生成（MANUAL）・判断APIは`goal_service.ensure_goal_editable`（CLOSED以外なら操作可）で保護。生成（AUTO）は確定APIからのみ呼ばれ、確定API自体がACTIVE限定のため追加の認可は不要 | `schedule_revision_service.generate_proposal`/`decide` |
| AI通信中の書き込みによる不整合 | E | AI通信中はDBへ書き込まない。修正案の保存は応答を得た後`serialize_writes()`内の1トランザクションでコミットする（`test_ai_write_lock.py`と同じ観点のテスト） | `schedule_revision_service.py` |

対策はすべてMitigate（既存の認可パターン・検証パターンの再利用、新規の攻撃面はAI応答の解析のみで多層防御済み）。受容したリスクなし。

### 31.8 検証の基準

- AIの応答に不正なブロック（他目標の行ID、完了済み・中止済みの行、期限超過、進行中の行の開始日変更、ReDoS誘発パターン）を含めても、個別に捨てられ他の行の処理に影響しないこと。
- AUTOでは遅れのある行が1件も無い目標でAIが呼ばれないこと（D-54）。MANUALでは遅れの有無にかかわらず常に呼ばれること（D-58）。
- AI通信中にDBへ書き込みが発生しないこと（`test_ai_write_lock.py`と同じ観点）。
- 承認時に「変更前の値が現在の値と一致しない」行だけが`STALE_BEFORE_VALUE`となり、他の行の判断には影響しないこと（D-59）。
- 翌日以降に承認する等、承認時の新しい予定日が13.5の制約に反する行だけが`INVALID_PLANNED_DATE`となり、例外を送出せず他の行の判断には影響しないこと（修正1）。
- 新しい修正案の生成により、古い修正案の未判断の行が`SUPERSEDED`となり、目標ごとに未判断の修正案が常に1つであること（D-65）。
