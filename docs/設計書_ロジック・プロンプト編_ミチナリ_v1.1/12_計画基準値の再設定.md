## 12. 計画基準値の再設定

### 12.1 再設定の契機

以下の操作により `plan_baseline` に新しいレコードを追加する。

| 契機 | reason |
| --- | --- |
| 目標の進行中への遷移 | INITIAL |
| リプラン操作の実行 | REPLAN（予約値、下記参照） |
| 受験日の確定日への変更 | EXAM_DATE_FIXED |
| 教材の追加・総量変更・締切変更 | MATERIAL_CHANGED |
| 予定周回数の変更 | CYCLE_CHANGED |

**REPLAN が予約値である理由（1.1（改13））**：仕様書は「リプラン」を独立した操作としては定義していない。警告・強制リプランの条件を満たした場合の導線は、警告バナーおよびモーダル（仕様書6.1・5.3 MD-01）から**目標編集画面へ誘導**し、利用者がそこで教材・予定周回数・受験日を修正することで基準値が再設定される、というものである。したがって実際に記録される reason は MATERIAL_CHANGED・CYCLE_CHANGED・EXAM_DATE_FIXED のいずれかであり、REPLAN が記録される経路は現時点では存在しない。将来「現在の計画をそのまま引き直す」独立操作を設ける場合に備えて enum の値としては残すが、それまでは記録されない予約値として扱う。

### 12.2 記録内容

```
T' = max(T, S(m))

effective_from             = T
baseline_daily_quota       = quota(m, T')（再設定後の値）
remaining_at_baseline      = R(m)
plan_days_at_baseline      = |{ d | T' ≤ d ≤ D(m) かつ type(d) = PLAN }|
planned_cycles_at_baseline = N(m)
reason                     = 上記の契機に対応する値
```

`baseline_daily_quota`・`plan_days_at_baseline` の算出にはいずれも T ではなく `T' = max(T, S(m))`
を起点として用いる（`effective_from` 自体は基準値の検索に使う実際の記録日 T のまま変えない）。
再設定の契機（12.1）はすべてユーザー操作であり、教材の学習期間開始日到来を契機とした自動
再設定は存在しない。そのため T をそのまま用いると、学習期間開始前（T < S(m)）に基準値が
記録された教材は quota(m, T) = 0（7.1のS(m)≤T条件）が基準値として固定されてしまい、開始日を
迎えてペースが乱れても11.1の警告判定条件（`baseline_daily_quota <= 0` の場合は判定しない）
により警告が永久に発火しなくなる。学習期間開始時点で見込まれるノルマを基準値とすることで
これを避ける。`plan_days_at_baseline` も同じ T' を起点にしないと、`baseline_daily_quota ×
plan_days_at_baseline = remaining_at_baseline` という関係が崩れ、リプラン履歴表示・AI向け
状況出力の数値が矛盾するため、両者は同じ起点で揃える。

### 12.3 設計意図

リプラン後は新しい計画が基準となるため、リプラン前の乖離を引きずらない。

基準値を履歴として保持することで、「何回リプランしたか」「各リプラン時点でどの程度の負荷だったか」を後から検証できる。**この履歴は総括レポートにおける最重要の分析材料となる。**
