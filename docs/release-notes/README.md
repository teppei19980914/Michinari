# リリースノート

各バージョンの詳細な変更点を置く。GitHub Releases の本文（要約版）から、ここへリンクしている。

**運用方針（配布前改善S-6 6-6、2026-09-20確定）**：詳細ノート（このディレクトリのファイル）は
**任意**であり、作らなくてもリリース作業は成立する（下記「A方式」）。v1.2.2以降の全バージョン
（`ver1.2.2`〜`ver1.9.0`）は、詳細ノートを作らずGitHub Releases本文のみで運用しており、この
ディレクトリにファイルを追加していない。全変更点はGitHub Releasesの各バージョンのページ
（下表またはリポジトリの[Releases一覧](https://github.com/teppei19980914/Michinari/releases)）
を直接参照する。二層構成（B方式）は、破壊的変更や移行手順など、Release本文の15行に収まらない
分量を書き残したい場合にのみ選択する仕組みとして残す。過去分（v1.2.2〜v1.9.0）を遡って本方式へ
統一する作業は行わない（実施コストに対し、既にGitHub Releases側に全変更点が残っているため得られる
価値が小さいと判断した）。

## 2層構成の理由

Releases 一覧ページは各リリースの本文を全文レンダリングするため、本文が長いと配布zip
（Assets）が画面下へ埋もれ、利用者が目的のバージョンを見つけられなくなる。そこで
**Release 本文には要約のみを置き、全変更点はこのディレクトリのファイルに置く**。

| 層 | 置き場所 | 分量の目安 | 役割 |
| --- | --- | --- | --- |
| 要約 | GitHub Release 本文 | 15行以内 | 一覧でのスキャンとダウンロード導線 |
| 詳細 | `docs/release-notes/v{version}.md` | 制限なし | 全変更点・不具合修正・開発者向け補足 |

## 新しいバージョンを公開する手順

ノートを先に書くか、後から書くかで2通りある。**通常はA**を使う。

### A. 先にパッケージを作り、ノートは後から書く（推奨・半自動）

リリースノートを書く前にパッケージとタグを確定できる。人の作業は「本文を書く」1点だけ。

1. 開発する（`dev/YYYY-MM-DD` ブランチ）
2. `main` へマージする（GitHub 上で PR をマージする）
3. **`backend/release.bat` を実行する**
   - テスト（バックエンド・フロントエンド）が全て通ることを確認する
   - `main` の取得・切り替え・最新化まで自動で行う（ローカルが dev ブランチのままでよい）
   - コンソールでバージョンを尋ねる
   - パッケージ生成 → タグ付与 → zip 添付 → **下書き**リリース作成まで行う
4. GitHub の Releases を開き、下書きの本文（記入用のひな形）をリリースノートへ書き換える
5. 「Publish release」を押す → 配布開始

この方式では `docs/release-notes/v{version}.md` を作らなくてよい。作らない場合、Release
本文は記入用のひな形になる（詳細ノートへのリンクは付かない。ファイルが無い状態でリンク
すると404になるため）。全変更点を残したい場合は、公開後に下記Bの1〜3を行ってファイルを
追加し、このファイルの表へ1行足す。

### B. 先にノートを書いてから公開する（2層構成をそのまま使う）

1. `docs/release-notes/v{version}.md` を作成し、全変更点を書く
2. ファイル冒頭の水平線より前に、要約ブロックを次のマーカーで囲んで置く

   ```markdown
   <!-- summary:start -->
   （ここに要約。15行以内。破壊的変更・移行時の注意は必ずここに残す）
   <!-- summary:end -->
   ```

3. このファイルの表へ1行追加する
4. 1〜3をコミットし、`main` へマージする（本文からのリンク先が `main` を指すため）
5. `backend/scripts/release.py {version}` を実行する（マージ → ビルド → 公開 → 公開後検証）

ノートが存在する場合は、AでもBでも要約ブロックが Release 本文になり、詳細ノートへの
リンクが付く（`publish_release.resolve_release_body` がファイルの有無で自動判定する）。

要約に必ず残すもの: このバージョンで何ができるようになったかの1〜2文、主な変更の箇条書き
3〜6項目、**破壊的変更と移行時の注意**。不具合修正の一覧・開発者向け補足は詳細側へ置く。

タグはビルド元コミットへ付く。`gh` の自動タグ生成には任せず、`ensure_release_tag` が
git 側でタグを作成・push してから `--verify-tag` で公開する（v1.2.1 でタグが配布物と
異なるコミットを指す事故があったため）。公開のタイミングと注意点は
[OPERATIONS.md](../OPERATIONS.md) 7.4 を参照。
