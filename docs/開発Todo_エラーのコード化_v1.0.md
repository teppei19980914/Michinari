**既存の仕組み（流用する）**
- フロントエンドの `api/client.ts` は、エラーの `details[].reason` を `ja.json` の文言に変換する（`reasonMessage`）。`reason` が無い場合は `errors.<code>`、それも無ければ `errors.default`。
- 例外の `reason` はドメイン例外のクラス属性（`services/exceptions.py`）で持つ。
- つまり、**バックエンドは文言を持たず、`reason` のキーだけを返せばよい**。

## 2. 方針

1. サービス層の例外の `message` は、技術者向けの英語の短い説明にする（トーストの「詳細」欄に出る。利用者向けの文言ではない）。
2. 利用者に見せる文言は、`reason` のキーで `ja.json` の `errors.reasons.<キー>` に置く。
3. 既存の `reason` が付いている例外はそのまま流用し、無いものは例外クラス（または `reason`）を追加する。
4. 変換の対応表（例外 → `reason`）は、例外クラスの定義に1か所だけ置く（DRY。`raise` ごとに文字列を書かない）。
5. テストは、日本語の文言の一致ではなく、**例外の型と `reason`** で確認する。
