### Phase 36：リリース前スモークの自動化（任意）

| 項目 | 内容 |
| --- | --- |
| 目的 | 配布パッケージが起動すること、既存データベースが移行できることを1コマンドで確認する |
| 投入文書 | CLAUDE.md、運用設計ルール（OPERATIONS.md 7.4） |

**背景**

`build_package.run_tests()` はバックエンドの `pytest`、フロントエンドの `tsc -b` と `npm test` を実行し、1件でも失敗すればビルドを中止する。一方で「ビルドされた成果物が起動するか」「既存の利用者データベースが移行できるか」は検証していない。`app/main.py` の `_open_browser` と `__main__` ガードは実ブラウザ・実サーバの起動を伴うため `pragma: no cover` としておりユニットテストの対象外であり、`alembic/versions/` の `downgrade()` は実測0%である。

ただし本アプリは単一利用者・ローカル動作であり、マイグレーションの事故は `backup_service` によるバックアップから回復できる。費用対効果から、Phase 33〜35 の完了後に着手する任意フェーズとする。

**実装対象**

- 配布 zip の展開 → 起動 → `/health` 応答 → 主要画面の応答確認 → 終了、までのスモークスクリプト
- Phase 23 で一度実施した「別ポート・独立したSQLiteデータベースでの実APIエンドツーエンドスモーク」を、使い捨てではなく再利用可能なスクリプトとして固定する
- 実データベースの複製に対する `alembic upgrade head` の確認

**完了条件**

- `release.bat` の実行前に1コマンドで流せる

---

**Phase36完了（2026-09-13）。**`backend/scripts/release_smoke.py` と `backend/smoke.bat` を新設した。

- **起動スモーク**：空きポートと一時データベースで uvicorn からアプリを起動し、`/health` に加えてダッシュボード・目標一覧・システム情報の各APIが200を返すことを確認する。`python -m app.main` ではなくuvicorn を直接使うのは、起動ポートが `app_setting` から決まって空きポートを指定できないこと、`__main__` が実ブラウザを開くこと、AI基盤への通信（週次要約の遡及生成）を伴うことを避けるため。スキーマ更新と初期データ投入は lifespan（`bootstrap_database`）で実行されるため、起動経路の検証は成立する
- **移行確認**：`data/michinari.db` の複製に対して `alembic upgrade head` を適用し、行数が減ったテーブルがないことを検証する。元のデータベースは読み取りのみ。既存DBが無い環境では省略し失敗にしない
- **配布パッケージの起動確認（`--package`）**：`dist/` の最新zipを展開し、実際の `Michinari.exe` を起動して同じエンドポイントを確認する。PyInstallerでの同梱物の取り込み漏れ・パス解決まで含めて検証できる。起動ポートは `app_setting.server.port` から決まるため、スモーク側が先にスキーマを作り空きポートを仕込む（初期データ投入は既存キーを上書きしない）。配布物はフロントエンドを同梱しており起動するとブラウザが開くため、既定では実行しない
- **判定ロジックのテスト**：`backend/tests/test_release_smoke.py`（35件）。実プロセスの起動と実HTTP通信はOS・ネットワーク依存が大きいため対象外とし、起動待ち・エンドポイント確認・行数比較・終了コードの判定を検証する。スモーク自身が壊れていると「問題がないから通った」のか「検知できずに通った」のか区別できないため、**問題を検知する側の経路**を重点的に固定した

`build_package.run_smoke()` としてリリースゲートへ組み込み、`run_tests()` の直後に置いた。`release.bat`・`build.bat`・`scripts/release.py` のどの経路からでも必ず通るため、リリース手順は従来の5つのまま変わらず、実行を忘れる余地もない。別手順（`smoke.bat` を先に流す）も検討したが、手順が増えるぶん実行漏れが起きうるため採らなかった。`smoke.bat` は単体で流すための道具として残している。実サーバの起動を伴うため環境要因で失敗しうるが、起動しない配布物を出荷するより望ましいという判断である。

実行結果として、**利用者の実データベースが head より数リビジョン古い状態（`e1f4a9c3b6d8`）にあり、複製への `upgrade head` がデータ欠損なく適用できること**を確認した。これは従来、配布後に利用者の環境で初めて判明していた種類の情報である。あわせて `--package` で最新の配布物（`Michinari-v1.2.2.zip`）を展開・起動し、全マイグレーションの適用と全エンドポイントの応答を確認した。
