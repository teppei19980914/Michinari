### Phase 33：テスト基盤の修復と計測対象の是正

| 項目 | 内容 |
| --- | --- |
| 目的 | 機能していないテストゲートを修復し、判定ロジックを持つのに計測対象外だったファイルを対象へ戻す |
| 投入文書 | CLAUDE.md、運用設計ルール（CODING_RULES.md「テストカバレッジ」、OPERATIONS.md「フロントエンドのテストとカバレッジ」） |

**背景**

2026-09-13にテストカバレッジの全体監査を実施し、以下を実測した。

- バックエンド：`app/` 配下は1091テスト・行/分岐ともカバレッジ100%（未通過ゼロ）。計測範囲外の `scripts/` は59〜95%、`alembic/versions/` は54〜85%（`downgrade()` が未実行）
- フロントエンド：`npm test` は100%を表示するが、これは計測対象を48ファイル・437文へ絞り込んだ中での100%であり、`src/**`（自動生成の型を除く）全体では文33.0%・分岐31.1%・関数27.2%。全分岐1478本のうち1147本（78%）が `.tsx` 側にある

あわせて、ゲート自体が機能していない箇所を2件確認した。

- `settings.json` の Stop Hook「デプロイチェック」はリポジトリルートで `pytest` を実行するが、ルートに `pytest` は PATH 解決されず設定ファイル（`pyproject.toml` 等）も存在しないため、バックエンドのテストが一度も実行されていない
- `auto-commit.sh` はヘッダコメントに「テスト実行（失敗ならスキップ）」と記載しているが、実装にテスト実行は含まれていない

さらに `vite.config.ts` の除外理由のうち2件が実態と異なる。`src/api/**` は「分岐を持たない薄いラッパ」として除外されているが、`api/client.ts` は通信失敗の `NETWORK_ERROR` 変換・204の扱い・エラーコードの既定値・未登録コードのフォールバックという分岐を持つ（実測34.6%）。`src/locales/**` は「定数のみで分岐を持たない」として除外されているが、`locales/t.ts` はキー未解決時のフォールバックと `{{var}}` 置換の分岐を持つ。いずれも全画面のエラー表示・文言表示が通る経路であり、除外したままにする理由がない。

**実装対象**

- `settings.json`：Stop Hook のデプロイチェックを `backend` ディレクトリで、同ディレクトリの仮想環境の Python で実行するよう修正する
- `auto-commit.sh`：ヘッダコメントを実装に合わせる（テストの実行は別 Hook の責務である旨を明記）
- `vite.config.ts`：`api/client.ts` と `locales/t.ts` を計測対象へ戻す。エンドポイント単位のラッパ（`api/goals.ts` 等）は実通信なしでは意味のある検証にならないため除外を維持する
- `api/client.test.ts`・`locales/t.test.ts` を新設し、上記の分岐を網羅する
- `OPERATIONS.md`「フロントエンドのテストとカバレッジ」の除外表を実態へ更新する

**完了条件**

- Stop Hook のログにバックエンドのテスト結果が出力される
- `npm test` が閾値100%を維持したまま、`api/client.ts` と `locales/t.ts` を計測対象に含む
- バックエンド・フロントエンドの既存テストが無改変で成功する
