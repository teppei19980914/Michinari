### Phase 29：算出ロジック・APIのスロット単位化

| 項目 | 内容 |
| --- | --- |
| 目的 | 配分の消費側（割当・必要速度・完了予測）と、配分・実績のAPIをスロット単位へ移行する |
| 投入文書 | CLAUDE.md、運用設計ルール、設計書 データ構造編（1.1改19）、設計書 ロジック・プロンプト編（1.1改14）、仕様書（1.1改18） |

**実装対象**

- `slot_service`：`slot_duration_hours` を `slot_duration_minutes`（整数）へ変更。`allocate_day` の引数を比率からスロット別配分分数へ置換し、戻り値をスロット別・教材別の割当分数に細分化する（日次報告の初期値に用いるため）。必要連続時間の判定を配分時間に対して行う（9.2）
- `allocation_service`（新設）：スロット別配分の取得・一括更新と上限検証。WORK目標に対する更新を拒否する
- `goal_service`：配分検証をスロット単位へ。READING目標への配分拒否ガードを解除し、WORK目標のみ拒否へ変更。`activate_goal`・`resume_goal` の条件をカテゴリ別に整理する（EXAMは配分必須、READINGは任意）
- `resource_service`：`GET /resources/allocation` をスロット単位のレスポンスへ変更。スロットの短縮・削除により超過が生じた場合の警告判定を追加する（保存は拒否しない）
- `record_service`：スロット別の入力を受け取り、合計を `minutes_spent` へ設定する。合計の更新経路をここ1箇所に限定する
- `ai_context_service`・`export_service`・`backup_service`：スロット別内訳の出力と、両スキーマ版数の更新
- 表示用の分→時間換算（小数第2位以下切り捨て）を共通関数へ集約する（フロントエンドと二重実装しないよう、算出はバックエンドで行う）

**Phase 29完了（2026-09-10）。** `allocation_service.py`・`duration.py` を新設し、既存の速度・予測・リプラン判定のテストは無改修で成功した。

**完了条件**

- 実効速度・完了予測日・強制リプラン判定の既存テストが、`minutes_spent` の意味を保つ設計により**実質無改修で成功する**
- スロットごとの配分合計が連続時間を超える更新が `RESOURCE_EXCEEDED` で拒否される
- スロットを短縮・削除しても保存でき、超過が警告として返る。削除したスロットに紐づく過去の実績内訳は `slot_id = NULL` として残り、`minutes_spent` の合計が変わらない
- カバレッジ100%を維持する
