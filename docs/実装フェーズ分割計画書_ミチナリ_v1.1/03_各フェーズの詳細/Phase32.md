### Phase 32：読書のページ項目の見直し

| 項目 | 内容 |
| --- | --- |
| 目的 | 読書の日次報告からページの入力を「現在ページ」1つに絞り、総ページ数を必須化して進捗率を常に提示する |
| 投入文書 | CLAUDE.md、運用設計ルール、要件定義書（1.1改8 R-65・R-66・R-70・R-71）、仕様書（1.1改19 6.2・6.5・6.10・14章）、データ構造編（1.1改20 5.3・5.4・7.1・7.2）、ロジック・プロンプト編（1.1改15 21.2・17.6） |

**背景**

利用者から「毎日読んだページ数を覚えていられない」という申告があった。直前の日次報告の現在ページとの差分から算出する案も検討したが、遡及入力（進捗のみ登録は任意の過去日を許容する）による順序逆転で保存済みの値が陳腐化しうること、初回の基準・読み返しによる負の差分・記録漏れ日の合算・確定済み日の表示値が後から変わることなど、解消すべき論点が多い。読書は記録・活用型の目標であり定量的な進捗管理を行わない（R-71）以上、投下量の指標である「その日に読んだページ数」を保持する必要がないため、項目自体を廃止する方針を採った。

**実装対象**

- マイグレーション `a9e3c5b71d64`：`reading_log.pages_read` の削除、`book.total_pages` のNOT NULL化（NULL行は記録済み`current_page`の最大値、無ければ1で補填）
- `models`／`schemas`：`ReadingLog.pages_read` の削除、`BookCreate.total_pages` の必須化、`BookUpdate` の番兵対象から`total_pages`を除外
- `record_service`：`current_page <= book.total_pages` の検証を追加
- `book_service`：進捗率の算出条件を「現在ページが入力済み」に変更し、上限を100%にクランプ。総ページ数の引き下げ訂正は許容する
- `ai_context_service`：`{{today_recall}}` からページに関する数値の注入を削除
- `analytics_service`／`export_service`／API層：`pages_read` の除外
- フロントエンド：`ReadingLogFields`（読んだページ数欄の削除、現在ページ欄の常時表示）、`readingLogForm`、`ReadingLogSummaryList`、`ReadingLogHistoryTab`、`BookTab`（総ページ数を必須入力へ）、ロケール、`openapi-typescript` による型再生成

**完了条件**

- 総ページ数を未入力のまま書籍を登録しようとすると `VALIDATION_ERROR` で拒否される
- 現在ページに総ページ数を超える値を入力すると拒否され、総ページ数ちょうどは受け付けられる
- 総ページ数を現在ページより小さい値へ引き下げる訂正ができ、そのとき進捗率が100%にクランプされる
- 読書のAIフィードバックのプロンプトにページに関する数値が含まれない
- 既存データ（総ページ数がNULLの書籍、`pages_read`を持つ想起記録）がある状態でマイグレーションを適用でき、行が失われない
- バックエンド・フロントエンドの既存テストが（前提の変更に伴う書き換えを含め）成功する
