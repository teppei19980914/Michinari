## 1. 本文書の目的

実装着手前に確定しておくべき技術選定と、祝日データの取得方針を定める。

これらを未決のまま実装を開始すると、Claude Code が推測で選定し、フェーズをまたいで一貫性が失われる。本文書は各フェーズの投入文書に含める。

---

## 2. 選定方針

| 方針 | 内容 |
| --- | --- |
| 枯れた選択を優先する | 単一利用者の個人ツールであり、長期の保守性が最優先。新しさに価値を置かない |
| 依存を増やさない | 標準機能で足りるものに外部ライブラリを入れない |
| 型の一貫性を保つ | バックエンドの型定義をフロントエンドへ機械的に伝播させる |
| 外部通信を最小化する | AI基盤への呼び出し以外の外部通信を持たない |

## 3. バックエンド

### 3.1 選定一覧

| 分類 | 採用 | 版 | 理由 |
| --- | --- | --- | --- |
| 言語 | Python | 3.12 以上 | AI基盤の開発キットがPython製 |
| パッケージ管理 | uv | 最新 | 高速。ロックファイルによる再現性 |
| Webフレームワーク | FastAPI | 最新 | OpenAPI自動生成。開発キットと同一プロセスで動作 |
| ASGIサーバ | uvicorn | 最新 | FastAPI の標準的な組み合わせ |
| ORM | SQLAlchemy | 2.0系 | 集計クエリの表現力。長期の安定性 |
| マイグレーション | Alembic | 最新 | SQLAlchemy 標準 |
| スキーマ検証 | Pydantic | 2系 | FastAPI 標準 |
| テスト | pytest | 最新 | 標準的選択 |
| テスト補助 | pytest-cov | 最新 | カバレッジ測定 |
| Lint / Format | ruff | 最新 | 単一ツールで両方を担う。設定が単純 |
| 型チェック | mypy | 最新 | サービス層のみ対象とする |
| CSV解析 | 標準 `csv` モジュール | — | 祝日CSVの解析に外部依存は不要 |
| 日付・時刻 | 標準 `datetime` / `zoneinfo` | — | 外部ライブラリ不要 |

**uv を選定する場合の代替**

社内環境で uv が利用できない場合は、`venv` + `pip` + `requirements.txt` に切り替える。この差異は Phase 1 のみに影響し、以降のフェーズには波及しない。

### 3.2 除外した選択肢

| 候補 | 除外理由 |
| --- | --- |
| Prisma Client Python | 開発が終了している |
| SQLModel | 集計クエリで SQLAlchemy の API に降りる必要があり、二重の学習コストが生じる |
| Tortoise ORM | マイグレーションツールの成熟度が Alembic に劣る |
| pandas | 集計はSQLで行う。データ量が小さく、依存を追加する価値がない |
| Celery 等のジョブキュー | 週次要約は起動時の遡及方式で足りる。常駐プロセスを増やさない |

## 4. フロントエンド

### 4.1 選定一覧

| 分類 | 採用 | 版 | 理由 |
| --- | --- | --- | --- |
| 言語 | TypeScript | 5系 | 型の一貫性 |
| ビルド | Vite | 最新 | 標準的選択 |
| UIライブラリ | React | 19系 | 開発者の習熟 |
| CSS | Tailwind CSS | 4系 | 開発者の習熟 |
| UIコンポーネント | shadcn/ui | 最新 | モーダル、タブ、セレクト、ポップオーバーを自作せずに済む。コードを取り込む方式のため依存が残らない |
| アイコン | lucide-react | 最新 | shadcn/ui の標準 |
| ルーティング | React Router | 7系 | 枯れている。画面数13で十分 |
| サーバ状態管理 | TanStack Query | 5系 | キャッシュ、再取得、ローディング状態を一元化 |
| クライアント状態管理 | React 標準（useState / useContext） | — | 4.2を参照 |
| フォーム | React Hook Form | 最新 | 目標編集画面の項目数が多く、再レンダリング制御が有効 |
| フォーム検証 | Zod | 最新 | React Hook Form との統合。バックエンドのPydanticと役割が対応 |
| グラフ | Recharts | 最新 | React親和性。基準線の重畳が標準機能で可能 |
| ガントチャート | 自作（CSS Grid） | — | 4.3を参照 |
| 日付処理 | date-fns | 4系 | 関数単位のインポート。不変。日本語ロケール対応 |
| 型生成 | openapi-typescript | 最新 | 4.4を参照 |
| テスト | Vitest + React Testing Library | 最新 | 4.5を参照 |

### 4.2 クライアント状態管理を導入しない理由

Zustand や Jotai といった状態管理ライブラリは導入しない。

本アプリケーションにおけるグローバル状態は、以下に限られる。

| 状態 | 出所 |
| --- | --- |
| 設定値 | サーバ |
| 認証状態 | サーバ |
| 論理的な本日 | サーバ |
| 進行中の目標一覧 | サーバ |

**すべてサーバ由来であり、TanStack Query のキャッシュがそのまま共有状態として機能する。** 純粋なクライアント状態は、フォームの入力途中の値（React Hook Form が管理）と、モーダルの開閉（各コンポーネントのローカル状態）のみである。

状態管理ライブラリを導入すると、サーバ状態をそちらへ複製する誘惑が生じ、二重管理による不整合を招く。導入しないことが最も安全である。

### 4.3 ガントチャートを自作する理由

専用ライブラリ（dhtmlx-gantt、frappe-gantt 等）は導入しない。

| 観点 | 判断 |
| --- | --- |
| 表示対象 | 1目標あたり数件の教材。行数が極めて少ない |
| 必要機能 | 期間の帯、進捗の塗り分け、本日線、締切マーカーのみ |
| 不要機能 | ドラッグによる編集、依存関係の矢印、階層構造、ズーム |
| ライセンス | 商用ライブラリが多く、個人利用でも確認が必要 |

CSS Grid による実装で十分であり、Tailwind の範囲で完結する。Recharts で無理に横棒グラフとして描くよりも、直接記述するほうが単純になる。

### 4.4 型の共有方針

**フロントエンドのAPI型定義を手書きしない。**

```
FastAPI が生成する OpenAPI スキーマ
        ↓ openapi-typescript
frontend/src/types/api.d.ts（自動生成）
        ↓
APIクライアントおよび各コンポーネント
```

生成コマンドを npm scripts に登録し、バックエンドのスキーマ変更時に再生成する。生成ファイルは編集禁止とし、その旨をファイル冒頭のコメントに明記する。

手書きでの型定義は、バックエンドとの乖離が静かに進行し、実行時エラーとして表面化する。機械生成であれば乖離は型エラーとして即座に検出される。

### 4.5 フロントエンドのテスト方針

**フロントエンドのテストは最小限とする。**

本アプリケーションの中核である算出ロジックはすべてバックエンドのサービス層に存在し、Phase 2 で網羅的にテストされる。フロントエンドの責務は表示と入力に限られる。

テスト対象は以下に限定する。

| 対象 | 理由 |
| --- | --- |
| カレンダーの色分けロジック | 日種別と記録状態の組み合わせが多く、目視確認では漏れる |
| 品質指標の入力形式切替 | 3方式の分岐がある |
| 日付状態による遷移先の判定 | 分岐条件が複雑 |

これ以外は手動確認とする。個人利用ツールに対して網羅的なUIテストを書くことは、投資対効果が見合わない。

### 4.6 除外した選択肢

| 候補 | 除外理由 |
| --- | --- |
| Next.js | サーバサイドレンダリングが不要。ローカルAPIサーバと二重になる |
| Zustand / Jotai | 4.2を参照 |
| Chart.js | React 統合が Recharts に劣る |
| dayjs | date-fns で足りる。プラグイン方式より関数インポートを優先 |
| Material UI / Ant Design | Tailwind との併用が煩雑。デザインの自由度が下がる |
| TanStack Router | React Router で足りる。学習コストを増やさない |

## 5. 日付と時刻の扱い

**この方針は算出ロジック全体に影響するため、実装前に確定させる。**

### 5.1 基本方針

| 対象 | 扱い |
| --- | --- |
| タイムゾーン | Asia/Tokyo に固定する。設定項目としない |
| 論理的な日付（DATE型） | タイムゾーンを持たない純粋な日付として扱う |
| 記録日時（DATETIME型） | UTC の aware datetime として保存し、表示時に Asia/Tokyo へ変換する |
| 論理日の判定 | サーバ側でのみ行う。クライアントは判断しない |

### 5.2 DATE と DATETIME の区別

| 列 | 型 | 扱い |
| --- | --- | --- |
| `daily_record.record_date` | DATE | 論理日。境界時刻を考慮してサーバが決定 |
| `material.start_date` / `due_date` | DATE | 暦日 |
| `exam_subject.exam_date_*` | DATE | 暦日 |
| `load_profile.date_from` / `date_to` | DATE | 暦日 |
| `plan_baseline.effective_from` | DATE | 論理日 |
| `*.created_at` / `updated_at` / `generated_at` | DATETIME | UTC aware |

**DATE 型にタイムゾーンの概念を持ち込まない。** 「2026年10月16日」は世界のどこから見ても同じ日付として扱う。タイムゾーン変換を挟むと、日付が前後にずれる不具合の温床になる。

### 5.3 論理日の一元管理

```
クライアント → GET /api/v1/records/today
             ← { "logical_date": "2026-08-22",
                 "boundary_hour": 4,
                 "record_state": "NONE" }
```

**クライアントは `new Date()` から論理日を判断しない。** 1日の境界時刻の解釈をサーバに一元化する。

この規約を破ると、境界時刻を4時に設定した場合に、画面上の「今日」とサーバが記録する日付が食い違う。深夜の利用時にのみ発生するため、発見が遅れる。

### 5.4 将来のPostgreSQL移行への配慮

DATETIME を UTC で保存することにより、将来 PostgreSQL の `timestamptz` へ移行する際にデータ変換が不要となる。SQLite の段階でローカル時刻の naive datetime を保存すると、移行時に全レコードの変換が必要になる。

## 6. 祝日データの取得方針（未決事項 D-01 の解消）

### 6.1 データソース

内閣府が公開する「国民の祝日」CSVを用いる。

| 項目 | 内容 |
| --- | --- |
| 提供元 | 内閣府 |
| URL | `https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv` |
| ライセンス | <cite index="20-1">デジタル庁のオープンデータカタログ（data.go.jp）に掲載されており、CC-BY と明記されている</cite> |
| 収録範囲 | <cite index="25-1">1955年から翌年分まで</cite> |
| 更新頻度 | 年1回程度 |

### 6.2 自動ダウンロードを採用しない

**設定画面からのCSVファイル手動インポート方式とする。** アプリケーションが直接ダウンロードする実装は行わない。

**理由1：URLの安定性が保証されていない**

<cite index="24-1">2023年に、従来の `syukujitsu.csv` から `shukujitsu.csv` へファイル名が変更された経緯がある（2文字目が y から h へ）。その後、内閣府のページが更新され元のファイル名も再び利用可能になったが、新旧2つのファイルが並存する状態となった。</cite>

年1回しか更新されないデータのために、URL変更で沈黙して壊れる自動処理を実装する価値はない。手動インポートであれば、ファイル名が変わっても利用者が対応できる。

**理由2：外部通信を増やさない**

本アプリケーションの外部通信は、AI基盤への呼び出しのみとする方針である。社内ネットワークから内閣府サイトへのアクセス可否は環境依存であり、実装時点で保証できない。

**理由3：更新頻度に見合わない**

年1回の作業を自動化する投資対効果が低い。設定画面に手順とリンクを表示すれば十分である。

### 6.3 CSV解析の仕様

内閣府のCSVには以下の特性がある。実装時に必ず考慮する。

| 特性 | 対応 |
| --- | --- |
| <cite index="18-1">文字コードが Shift-JIS</cite> | `cp932` でデコードする。`shift_jis` ではなく `cp932` を用いる（機種依存文字への耐性） |
| <cite index="18-1">改行コードが CRLF</cite> | 標準 `csv` モジュールで `newline=''` を指定して開く |
| 1行目がヘッダ | スキップする |
| <cite index="23-1">日付形式が `YYYY/M/D`（ゼロ埋めなし）</cite> | `datetime.strptime(s, "%Y/%m/%d")` で解析可能 |
| <cite index="23-1">「休日」「休日（祝日扱い）」という名称の行が含まれる</cite> | 振替休日等も学習可能日としてはバッファ扱いが妥当なため、そのまま取り込む |

**取り込み処理**

```
手順1：アップロードされたCSVを cp932 でデコードする
手順2：ヘッダ行をスキップし、日付と名称を解析する
手順3：解析できた行の年の範囲を求める
手順4：holiday テーブルから、その年の範囲の既存レコードを削除する
手順5：解析した全行を挿入する
手順6：取り込み件数と対象年の範囲を画面に表示する
```

年の範囲を限定して置換するのは、CSVに含まれない年のデータを誤って削除しないためである。

**エラー処理**

| 事象 | 対応 |
| --- | --- |
| デコード失敗 | 文字コードが異なる旨を表示し、取り込みを中止する |
| 解析できない行 | その行をスキップし、末尾にスキップ件数を報告する |
| 全行が解析不能 | 形式が想定と異なる旨を表示し、取り込みを中止する |

### 6.4 設定画面での表示内容

| 項目 | 内容 |
| --- | --- |
| 取込済みの祝日件数と年範囲 | 表示のみ |
| 最終取込日時 | 表示のみ |
| データソースの案内 | 内閣府のページへのリンクと、CSVの取得手順 |
| ファイル選択 | CSVファイルのアップロード |
| 手動追加 | 個別の日付を祝日として追加する（社内の特別休日等への対応） |

手動追加を用意するのは、会社の創立記念日など、国民の祝日ではないが学習リソースに影響する休日に対応するためである。ただしこれはカレンダーの日種別個別指定でも代替できるため、優先度は低い。

### 6.5 初期データ

アプリケーションに初期の祝日データを同梱しない。初回起動時、祝日が未取込である旨を設定画面に表示する。

祝日が未取込の状態でも、曜日別の日種別既定値により動作する。祝日が計画日として扱われるだけであり、致命的な不具合にはならない。

## 7. コード規約の補足

CLAUDE.md および運用設計ルールに加え、本アプリケーション固有の規約を以下に定める。

### 7.1 禁止事項

| 禁止 | 理由 |
| --- | --- |
| コンポーネント内への文字列リテラルの直接記述 | ロケールファイルへ外部化する |
| ソースコードへの閾値・パラメータの直接記述 | `app_setting` へ外部化する |
| ソースコードへのプロンプト文面の埋め込み | `prompt_template` へ外部化する |
| フロントエンドのAPI型の手書き | 自動生成する |
| クライアント側での論理日の判断 | サーバから取得する |
| 日次ノルマ・残量・現在周回の保存 | 都度算出する |
| サービス層でのHTTP例外の送出 | ドメイン例外を送出し、API層で変換する |
| ブラウザ記憶領域への認証情報の保持 | サーバ側にのみ保持する |

### 7.2 命名規則

| 対象 | 規則 | 例 |
| --- | --- | --- |
| テーブル名 | 単数形スネークケース | `daily_record` |
| 列名 | スネークケース | `amount_completed` |
| APIパス | 複数形ケバブケース | `/api/v1/load-profiles` |
| Pythonモジュール | スネークケース | `quota_service.py` |
| Reactコンポーネント | パスカルケース | `DailyReportForm.tsx` |
| ロケールキー | ドット区切り | `dashboard.todayQuota.title` |
| 設定キー | ドット区切り | `threshold.warning_ratio` |

### 7.3 例外設計

```
services 層：ドメイン例外を定義し送出する
             （ImmutableRecordError、ResourceExceededError 等）
                    ↓
api 層　　　：例外ハンドラでAPIエラーコードへ変換する
                    ↓
クライアント：エラーコードに対応するロケール文言を表示する
```

エラーメッセージをサーバ側で日本語生成しない。エラーコードのみを返し、文言はロケールファイルで管理する。これにより表示言語の切替に対応できる。
